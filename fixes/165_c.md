### 165-C-2 — Re-emit into an existing dir never reconciles the file SET: stale files (shrunk tree, removed spec) survive and can wedge `repair` forever; the "nothing was merged or appended" warning is false

- **file:line**: `scripts/rapidtool-cli.mjs:676-697` (preExisting snapshot + warning text) and `src/lib/headless.ts:1018-1039` (`emitProject` writes only `result.files`); amplification in `src/lib/compile-check.server.ts:307-330` (`walkSpecFiles` runs EVERY `tests/*.spec.ts` on disk) and `src/lib/headless.ts:1736-1748` (`applySynthesizedTreeToDir` never deletes).
- **BUG**: a second `emit` over a non-empty dir replaces whole files but never removes files the previous emit produced that the new scaffold no longer emits (e.g. a `generatedTree` that shrank from 3 rows to 1, or a tree that stopped producing `tests/foo.spec.ts`). CLI line 697 tells the caller "its files were overwritten in place (…nothing was merged or appended)" and README-cli.md (Emit section) repeats it — false when survivors exist. The stale survivors are not inert: `walkSpecFiles` re-runs ANY surviving `tests/*.spec.ts` on every later `tree-run`/`repair`/`emit --run`, and a stale red spec (importing a deleted module, asserting a removed contract) is unrepairable by the repair lane — `repairTreeDir` only writes rows present in the ledger and only changed files (`applySynthesizedTreeToDir`), so the stale file is re-run red each cycle until budget exhaustion → `RT_E_REPAIR_FAILED` on a tree the agent cannot fix through the documented seam.
- **WHY**: emit-then-iterate is the documented loop (tree-run/repair exist to serve it); a file-set that can only grow is a silent accumulation bug that eventually fails every later tree verdict.
- **FIX**: in the CLI `emit` arm, snapshot the dir's file list (rel paths + FNV-1a hashes) BEFORE writing (already readdir'd for `preExisting`); after `emitProject`, compute survivors = pre-existing files under the scaffold-owned roots (`tests/`, `src/`) absent from `res.files` whose hash is UNCHANGED since the snapshot (scaffold leftovers, not agent edits) → `rmSync` them and report `payload.stale = {removed:[…]}`; files the agent edited (hash differs from snapshot) are never deleted — report them as `payload.staleSurvivors` with a warning. Reword line 697 to state the reconciliation honestly. (Deleting only byte-identical-to-pre-snapshot leftovers keeps the "never clobber agent edits" rule of the repair lane.)
- **TEST**: emit a 2-row-tree project to a fresh dir (files A,B + spec S); shrink the project to 1 row and re-emit; assert B and S are gone from disk, `stale.removed` lists them, and a follow-up `tree-run` on a deliberately stale-red S is now green. Second case: touch S (agent edit) between emits ⇒ S survives and is listed under `staleSurvivors`, never deleted.

### 165-C-3 — `emitProject.moduleEmbedded` is `true` whenever `generatedSource` is empty (chunked-tree mode): `.includes("")` matches every file body

- **file:line**: `src/lib/headless.ts:1031` (`const moduleEmbedded = result.files.some((f) => f.body.includes(project.generatedSource ?? ""));`), surfaced at `scripts/rapidtool-cli.mjs:691` and documented in README-cli.md Emit section (`"moduleEmbedded": true|false`).
- **BUG**: for a chunked-tree synthesis (P6 >8 signatures: `generatedTree` non-empty, `generatedSource` `""`), `(project.generatedSource ?? "")` is `""` and `"".includes(...)` — i.e. `body.includes("")` — is `true` for every file, so `moduleEmbedded: true` whenever at least one file was emitted, even though NO module was embedded (the tree mode embeds tree files, not a generated module — scaffold.ts:994 `generated` empty ⇒ host path not emitted, `:1005-1006` `hostOk` false). The inverse (module present but a body not containing it) cannot happen either, so the flag carries no information and actively misleads: an AI-agent consumer of the emit envelope (and of `emit --run` chains) believes the single-module `generatedSource` is inside the scaffold when only the tree is.
- **WHY**: the flag is the only machine signal distinguishing "module embedded" from "tree assembled" on the envelope; a constant-`true` in tree mode makes that signal worthless exactly on the path (large-keyed P6) where it matters.
- **FIX**: guard on the source being non-empty: `const src = project.generatedSource ?? ""; const moduleEmbedded = src.trim().length > 0 && result.files.some((f) => f.body.includes(src));` (empty source ⇒ `false`). Optionally rename semantics in the emit comment block (`:1009-1017`) to "the scaffold hosts the generatedSource module verbatim".
- **TEST**: `emitProject` on a project with `generatedTree: [2 rows]`, `generatedSource: ""` ⇒ `moduleEmbedded === false` (currently `true`); same project with a real `generatedSource` that the host file contains verbatim ⇒ `true`; a non-empty source NOT present in any body ⇒ `false`.

### 165-C-4 — Exit-taxonomy drift: internal failures in the emit-era verbs exit 1 (usage class) instead of 4 (internal), unlike their own README contract and sibling verbs

- **file:line**: catch blocks at `scripts/rapidtool-cli.mjs:742-746` (emit), `:941-947` (vault), `:960-964` (search), `:1089-1094` (design), `:1124-1129` (diagram), `:1168-1172` (harvest), `:1193-1197` (swarm), `:1243-1247` (bench), `:1339-1343` (knowledge), `:1660-1664` (lesson), `:1742-1749` (wild), `:1857-1863` (deepen) — all `respond({…errCode(err, "RT_E_INTERNAL")…}, 1)` — vs siblings that correctly exit 4: check `:1064-1073`, tree-run `:809-818`, repair `:914-923`, chat `:1790-1805`, verify `:1035-1042`, doctor `:1875-1884`, diagnose `:1937-1945`, and main's outer handler `:1953-1961`. README-cli.md states the contract repeatedly ("internal error → exit 4 (`RT_E_INTERNAL`)", e.g. Check section; repair section "internal throw → exit 4").
- **BUG**: `emit` shares the SAME compile-check/treeRun seams as the `check` and `tree-run` verbs, which exit 4 on an internal throw; when the seam throws inside `emit` (e.g. `mkdirSync` on a path whose parent is an existing file → ENOTDIR/EEXIST, runner spawn failure), `emit` exits 1 — byte-indistinguishable from a usage error or a red tree. An agent chaining verbs cannot tell "my invocation was wrong" from "the tool exploded" without guessing, which is precisely the 0/1/3/4 taxonomy's purpose.
- **WHY**: exit 1 is the taxonomy's usage/validation class (README); internal crashes must be 4 so agents can retry-vs-repair correctly.
- **FIX**: change the twelve catch sites above to `respond(…, 4)` (they already default the code to `RT_E_INTERNAL` via `errCode`); keep the handled-envelope `ok:false` paths (e.g. emit `--check`/`--run` red results, pre-flight refusals) at exit 1.
- **TEST**: `emit --project <ok.json> --out <path-under-an-existing-FILE>` → mkdir/write throws inside the try; assert exit code 4 and `code:"RT_E_INTERNAL"` on stdout (currently exit 1). Same assertion for one representative of each verb class (e.g. `vault`, `diagram`) with an unwritable target.

### 165-C-6 — `wild --steps 0` runs the DEFAULT 24 steps (0 is falsy), and any non-numeric/out-of-range `--steps` silently runs the default — with no validation anywhere

### 165-C-7 — Files an agent ADDS to the emitted dir are invisible to the ledger (`importTreeDir` iterates only known rows) and are silently dropped by the next `emit`

- **file:line**: `src/lib/headless.ts:1557-1625` (`importTreeDir` — loops `for (const row of tree)`, no dir scan for unknown files), result type `:1532-1546` (no `added` list), `:1706-1751` (`applySynthesizedTreeToDir` — writes ledger rows only), `:1018-1039` (`emitProject` — writes `result.files`, i.e. ledger rows); CLI dirDirty `scripts/rapidtool-cli.mjs:770-785` (only `changed/unchanged/missing/refused`, no `added`); contrast `src/lib/compile-check.server.ts:307-330` (`walkSpecFiles` runs ANY `tests/*.spec.ts` found on disk, ledger or not).
- **BUG**: the repair/emit→edit→re-emit loop's stated contract is "the dir is the artifact, the project JSON is the ledger — the ledger absorbs the dir edits" (rapidtool-cli.mjs:822-837). But the ONLY dir→ledger direction (`importTreeDir`) maps existing ledger rows to disk files; a genuinely NEW file the agent adds under `tests/` or `src/` (a new spec, a new util) is never read into `project.generatedTree`. Consequences: (1) `tree-run` and repair cycle verdicts DO execute the added spec (`walkSpecFiles`), so an added-but-red spec can exhaust repair budget with no repair path (same wedge as 165-C-2); (2) an added file that makes the tree green is not in the ledger, and the next `emit` (fresh dir or after cleanup) writes only ledger rows — the agent's addition silently vanishes from the artifact with no warning anywhere (no `added` telemetry exists).
- **WHY**: the seam is advertised as the continuation point for hand-edited artifacts; additions are the most natural edit, and both directions (loss on re-emit, unrepairable red) are silent.
- **FIX**: extend `importTreeDir` to also scan the dir for tree-eligible files (paths passing `repairTreePathRefusal`, headless.ts:1512-1530) that have NO ledger row: report them as `added: string[]` (+ a `generatedTree:added:<path>` warning naming the loss-on-re-emit consequence). Surface `added` in the `repair`/`tree-run` envelopes (CLI `:776-782`, `:858-865`) and in `ImportTreeDirResult`. Optional hardening: refuse repair convergence (or require a flag) while `added` files exist that are red.
- **TEST**: dir with ledger rows + one extra `tests/extra.spec.ts`; `importTreeDir` ⇒ `added: ["tests/extra.spec.ts"]` (today `[]`/absent), envelope carries the warning; after a subsequent `emit` to a fresh dir, assert the extra file is reported as dropped rather than silently absent.

### 165-C-8 — `repair`/`tree-run` import telemetry mixes counts and arrays in one envelope: `imported` is a count, `changed` is an ARRAY, `unchanged` is a count, `missing`/`refused` are arrays

- **file:line**: `scripts/rapidtool-cli.mjs:858-865` (repair `importSummary`: `imported: res.import.imported.length`, `changed: res.import.changed`, `unchanged: res.import.unchanged.length`, `missing: res.import.missing`, `refused: res.import.refused`, `warnings: res.import.warnings`) and `:776-782` (tree-run `dirDirty`: `changed: imp.changed`, `unchanged: imp.unchanged.length`, `missing: imp.missing`, `refused: imp.refused`, `warnings: imp.warnings`).
- **BUG**: within one JSON object the same semantic field is sometimes a number and sometimes a string array: `changed`/`missing`/`refused` are path arrays while `imported`/`unchanged` are counts (and `imported` counts BOTH changed and unchanged — headless.ts:1607-1608 pushes to either bucket then unconditionally to `imported`). The CLI is explicitly a machine contract ("every subcommand prints a single JSON object … parseable by an AI agent", rapidtool-cli.mjs:5-10); a consumer cannot verify `changed + unchanged + missing === imported` without a type check on every field, and any agent that treats `changed` as a count (as its sibling `unchanged` is) will mis-size budget/repair decisions.
- **WHY**: shape drift between sibling fields in the same envelope is the class of bug that silently corrupts downstream logic (sums, comparisons) rather than failing loudly.
- **FIX**: normalize the envelopes to one convention — e.g. counts everywhere plus explicit `changedPaths`/`missingPaths`/`refusedPaths` lists, or arrays everywhere (`imported: string[]`, `unchanged: string[]`). Pick counts + `*Paths` suffix lists, and update the repair README-cli envelope description to match.
- **TEST**: script-level test asserting `typeof summary.imported === "number" && typeof summary.changed === "number" && typeof summary.changedPaths === "object"` on a fake `ImportTreeDirResult` with 1 changed + 1 unchanged row; same for the tree-run `dirDirty` shape. (Today `changed` is an array.)
