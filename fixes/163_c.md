## 1. Findings (file:line + what is missing / wrong)

### F1 — Behavioral-repair gap: CONFIRMED for the tree path; the single-module path has a partial loop that trees never get

- Every bounded repair prompt in the codegen surface fixes **shape only**: envelope-parse repair
  `p6SynthesisRepairPrompt` (codegen.server.ts:205), export-binding repair (:220), soft-forbidden
  repair (:239), missing-signature repair (:255), brief-vocabulary repair (:319). None can carry a
  behavioral assertion delta (a fixture case that executed and returned the wrong value).
- The ONLY behavioral fail→patch→rerun loop in the product is `verifyAndFixServer`
  (verify.server.ts:712-830): failing machine-run case ids + details feed a patch re-prompt
  (:795-808, "Failing cases: … · Do not weaken the cases; fix the source") and the machine re-runs
  ≤ `maxIterations`. Its cases are **LLM-authored boolean expressions** generated from
  source+brief (`generateCases` :740, A7-oracle-seeded). It runs **only on the ≤8-signature
  single-module path** (codegen step 4, codegen.server.ts:1295-1317).
- The chunked-tree repair path's only failure context is the treeRun tail threaded as
  `deps.treeFailure` (codegen.server.ts:197-202 `repairTreeFailureTail`; headless.ts:1446) — but
  `treeRunFailureTail` (headless.ts:1184-1194) can name only the top-level error / first failing
  spec file / entry verdict, and `tapFailureTail` (compile-check.server.ts:415-441) **deliberately
  strips the assertion diff**: `actual:`/`expected:`/`operator:`/`code:` lines are filtered out at
  compile-check.server.ts:433. A behavioral failure therefore reaches the next synthesis cycle as
  `test "X" failed · <message>` **without the expected-vs-actual delta**, and the next cycle is a
  whole-tree regeneration through the same shape-repair prompt set.
- **Missing:** any path that feeds a failing fixture/test case (id + given + expected + actual +
  bounded traceback) back into a repair prompt, at tree level or module level. Phase A as written
  (162 A6) makes a red fixture suite a journey *outcome* (`failed`) — it never specifies the
  fixture-failure **repair** loop (re-synthesize against the delta, bounded, re-run). With no
  fixtures landed yet (`acceptanceFixtures` appears nowhere under `src/`), the gap is currently
  latent but certain: the first fixture-red keyed run will have no repair path and will simply
  exhaust budget.

### F2 — Tree-verify reconciliation: the tree lane verifies LOAD + NAMES, not behavior, and the "tested" mint can fire before the behavioral gate

- Single module: in-synthesis machine verify + repair (codegen.server.ts:1295-1317); red ⇒ coded
  refusal (`codeForVerifyStatus` :907); `lastTest:"tested"` minted at synthesis.
- Chunked tree: **no machine verify at synthesis** — deliberate and documented
  (codegen.server.ts:1339-1341, :1353-1355, :1541-1544): "the tree machine-run is the tree-run
  lane's step". The lane = `driveP6Journey` (headless.ts:1314-1464) / `repairTreeDir` (:1753+) /
  run-eval: emit → `treeRun(dir)` (compile-check.server.ts:604-627) → `mintTreeRunTested`
  (codegen.server.ts:1654-1693) → honest gate.
- `treeRun` DOES execute real `node --test` specs, including scaffold-emitted
  `tests/oracle.spec.ts` (scaffold.ts:1028+). **But in TREE mode that spec only** (i) imports the
  entry namespace and asserts it loads with ≥1 export (scaffold.ts:1096-1101), (ii) runs
  capability-presence rows (readFileSync name scans), and (iii) asserts template-host behavior only
  when the single-module host is emitted. **It never executes the tree's functions against
  input→output expectations.** A7 oracle rows seed LLM case generation ONLY in the single-module
  verify path (dod.ts:714 `oracleToCaseSeeds` → verify.server.ts generateCases). A chunked tree
  whose exports compute garbage keeps `treeRun` green.
- `mintTreeRunTested`'s honesty gate is "≥1 spec ran AND ≥1 assertion executed"
  (codegen.server.ts:1620-1635) — satisfied by the entry-load smoke test (assert.ok/equal,
  scaffold.ts:1096-1101) — so a tree can be stamped `tested` (and thus satisfy DoD `p6-verified`,
  dod.ts:337-355) with **zero behavioral check of its functions**. Phase A (A2 fixtures spec / A3
  dataEntry / A4 behavioral) is exactly the missing reconciliation and is confirmed NOT landed.
- **Ordering bug for Phase A:** `driveP6Journey` mints the tested-stamp BEFORE reading the gate
  verdict (headless.ts:1402 `applyTreeRunTestedMint` → :1406 recordGate → :1416 gate check). Once
  A6 keys `p6-verified` on the behavioral pass, a fixtures-red run will mint
  `lastTest:"tested"` on a FAILED project. The plan must reorder or condition the mint.

### F3 — Crash/resume: phase-granular replay only; intra-journey state is in-memory and dies with the process

- Ledger semantics: the project JSON is saved **once per CLI invocation** (rapidtool-cli.mjs:412,
  after `runUntilGate` returns). `hydrateProject` (engine.ts:1967+) repairs schema drift, drops
  broken `generatedTree` rows with the `generatedTree:dropped`/`treeRepaired` tokens
  (engine.ts:2170-2255), force-stops orphan wild runs (engine.ts:1940 `hydrateWildRun`; :1934 "the
  driver loop is a session artifact and dies with the session"). Resume = re-invoke `run`/`gate`:
  `advanceOnce` (headless.ts:401-447) re-runs the current non-complete phase from scratch.
- **Crash mid-phase loses everything since the last save** — including an in-flight P6 journey's
  cycles: the journey loop's cycle counter, per-cycle synthesis results, and the stamped
  `p6.tree.failure` logs (:1212-1217, :1447) live only on the in-memory project; a process death
  mid-journey restarts at cycle 1 with a fresh budget and no memory of the spent cycles' tails.
- Explicit resume exists ONLY for wild-mode runs (`wild --start|--pause|--resume|--stop`,
  rapidtool-cli.mjs:1673-1714; store.ts:991-1103 pause/auto-expiry/runRef epoch stability). The
  13-phase governed run and the P6 journey have **no checkpoint/resume/rollback**; the only
  recovery verbs are `retry` for blocked/rejected phases (:521) and H4 corrupt-persistence
  recovery (store.ts:795-829). No intra-phase checkpointing anywhere.

### F4 — Lesson store: read-back EXISTS (two advisory seams) but the code-writing prompts, the codegen verify lessons, and the kill-criterion are unwired — 162 C1 is half-stale

- Writers are real: engine L1 vague-brief (engine.ts:489-583) and L2 template-emission
  (:1350-1395), headless L2-on-refusal (:535-572) + run-summary (:605), report-intake L2
  (:345-371), harvest (:674+), verify L3/L4 via `applyVerifyOutcome` (verify.ts:196-228),
  knowledge.ts class rows + manual rows.
- Read-back exists in exactly TWO advisory-prose places: (1) the P0 reframe HITL prompt
  (engine.ts:590-622), (2) the P6 **brief-expansion** prompt (codegen.server.ts:1113-1124 →
  `expandBrief` lessons param, prompt-engine.ts:167-204). So "write-only" (162 C1) is stale for
  those seams — but **the actual code-writing prompts carry zero lesson context**: the synthesis
  user prompt (`p6SynthesisChunkUserPrompt` codegen.server.ts:1392 / the single-module synthesis
  prompt) and EVERY repair re-prompt (:204-331) never receive `selectLessons` output.
- **Verify L3/L4 rows are dropped on the engine's own keyed path:** verify.server.ts mints
  `outcome.lesson` (:56-59, :756/:775/:791/:828) but codegen — the caller on the keyed P6
  single-module path (codegen.server.ts:821, :1314) — never appends `outcome.lesson` to
  `project.memory`; only the client `applyVerifyOutcome` (store `verify` verb / console) persists
  them (verify.ts:199-207). The most valuable failure lessons (machine-run failed N iterations,
  with evidence) never reach memory during synthesis.
- Kill-criterion machinery EXISTS (K-tier: `LESSON_RETIRE_COUNTER=3` knowledge.ts:596,
  `bumpCounterEvidence` :545, retire-excluded reads :389-390/:477-478) but only a **human** CLI
  bump feeds it (rapidtool-cli.mjs:1627, `lesson` family). No automatic falsification: nothing
  bumps a lesson when a later run fails in the exact class the lesson names; C2's eval-delta
  promotion gate is absent; and the memory caps (verify.ts:207 `slice(-80)`; codegen.server.ts:1576
  `.slice(0, 80)` on memory) silently evict older lessons.

### F5 — Error-code parity: registry is self-consistent; new-verb codes are unregistered except verify-kind (test will NOT break — but implementers will invent codes)

- `ERROR_CODES` (19 codes, errors.ts:23-44) and `ERROR_CODE_DOC` (:191-287) are exactly
  key-parallel; errors.test.ts:233-262 auto-enforces "doc entry per code, no orphans, one-line
  meaning + agentAction". Parity breaks only if a code is added to one side without the other — a
  new VERB cannot break it. `RT_E_VERIFY_KIND_FAILED` is pre-registered (:44/:282) for 162 B1's
  `emit --verify-kind`, which itself is **not yet implemented** (only the scaffold comment
  scaffold.ts:465 + the registry entry exist). `RT_E_TREE_RUN_FAILED` (:42/:272) and
  `RT_E_REPAIR_FAILED` (:43/:277) cover the tree-run/repair verbs 1:1.
- No `fixtures`/`corpus`/`eval` verb exists (33 `case "…"` in rapidtool-cli.mjs — none of the
  three) and no `RT_E_FIXTURE*`/`RT_E_CORPUS*`/`RT_E_EVAL*` codes are registered. Phase A5/E2
  implementers would otherwise mint ad-hoc codes; the registry edit is a 2-place change
  (ERROR_CODES list + ERROR_CODE_DOC entry) and must land in the SAME patch as each verb.

## 2. Ranked plan-patch additions for fixes/162 (merge-ready; apply in order)

### R1 — [CRITICAL, after Phase A] Behavioral repair loop: fixture-failure feedback into a bounded tree-repair cycle
- **Add to:** 162 Phase A (new A7 after A6) and Phase C loop section.
- **What:** (a) a new repair-prompt class `p6SynthesisFixtureRepairPrompt(failures)` in
  codegen.server.ts (~:331) that receives, per failing approved fixture case: `id`, `given`
  (JSON, capped), `expected` descriptor, `actual` (capped ~300 chars each), and a bounded
  traceback tail — the shape-repair families stay as-is for their classes; (b) stop stripping the
  diff: add a sibling of `tapFailureTail` (compile-check.server.ts:415-441) that extracts the
  FIRST ≤2 failing `node:test` assertion rows WITH expected/actual (each capped), used only for
  fixture-era spec failures (compile-error tails keep today's stripped form); (c) the journey
  (headless.ts:1387-1449) routes a fixtures-red verdict into the fixture repair prompt on the next
  cycle instead of the generic whole-tree re-synthesis, then re-emits + re-runs; budget-exhausted
  ⇒ honest `failed` naming the cases (A6 stays).
- **Why:** F1. Field pattern: validation failures must become *structured feedback* for the next
  pass, not a dead end (OpenAI repair-loops cookbook; Reflexion's verbal-reflection-on-failure).
- **Bugs:** cap every delta field (hostile/large actual values); never weaken or rewrite the
  approved fixtures in a repair prompt ("Do not weaken the cases; fix the source" —
  verify.server.ts:804 parity); no-fixture runs keep byte-identical prompts.

### R2 — [CRITICAL, with A6] Fix the mint-before-gate ordering in driveP6Journey
- **Add to:** 162 A6.
- **What:** in headless.ts:1402-1416, move `applyTreeRunTestedMint` AFTER the gate verdict (or
  gate the mint on `gate.passed === true` AND — when approved fixtures exist — fixture-spec
  green). A failed journey must never carry `lastTest:"tested"`.
- **Why:** F2 ordering bug: once A6 keys p6-verified on the behavioral pass, the current order
  stamps "tested" (dod.ts:337 probe green) on a project the journey then FAILS.
- **Done ==:** a fixtures-red journey returns `failed` with NO `tested` stamp; the green path
  mints exactly once, after gate.passed.

### R3 — [HIGH, with A4] Upgrade `mintTreeRunTested`'s honesty gate for fixture-era trees
- **Add to:** 162 A4/A6.
- **What:** in codegen.server.ts:1620-1635/1654-1693, when the project carries ≥1 approved
  `acceptanceFixtures` case, "executed" requires the `tests/brief.spec.ts` row (A2's emitted
  fixture spec) to have run ≥1 assertion green; the entry-load smoke assertion
  (scaffold.ts:1096-1101) alone must NOT satisfy the mint once fixtures exist.
- **Why:** F2 — today a load-only smoke test can mint "tested" for a tree whose functions are
  never behaviorally executed; that is exactly what Phase A exists to end.
- **Done ==:** fixture-era tree with red fixtures is never minted; no-fixture trees keep today's
  behavior byte-for-byte.

### R4 — [HIGH] Chunked-tree machine-verify statement in the plan (reconciliation, one paragraph in 162 §2 Phase A preamble)
- **Add to:** 162 §2 intro / Phase A gate text.
- **What:** state explicitly: single-module behavioral verify = LLM-self-authored expressions,
  seeded + pinned by A7 rows (overfitting liability, 162 §0.2); chunked-tree verify = `treeRun`
  over emitted specs, which until A2 lands checks LOAD + NAMES only. The approved-fixture spec is
  the ONLY behavioral oracle for trees; until A2, a tree's `tested` stamp means "compiles, loads,
  self/presence specs pass" — never "functions are correct". This prevents a future reader from
  over-reading `p6-verified`.
- **Why:** F2; honesty contract (declare-or-strike).

### R5 — [HIGH] Journey checkpoint/resume (crash-recovery for the 100%-AI loop)
- **Add to:** 162 Phase C (new C0, before C1) or Phase A6 note.
- **What:** (a) persist after EVERY journey cycle: the journey already stamps `p6.tree.failure`
  logs on the in-memory project (headless.ts:1212-1217, :1447) — make the run loop save the
  ledger after each cycle/phase boundary (rapidtool-cli.mjs:412 currently saves once per
  invocation), so a crash loses ≤1 cycle; (b) add a durable cycle checkpoint
  (`p6.journey.checkpoint` log or a small `journeyState {cycle, budget, treeFailureTail,
  refusal}` field on Project) and let `driveP6Journey`/`repairTreeDir` accept a
  `resumeFrom`-style context so a re-invocation continues at the recorded cycle with the prior
  tails instead of restarting at cycle 1; (c) wild-mode `--resume` (rapidtool-cli.mjs:1673-1714)
  is the existing pattern to mirror; governed `run`/`gate` re-entry semantics stay as-is
  (phase-granular replay via headless.ts:401-447).
- **Why:** F3. Field pattern: checkpoints are the standard fault-tolerance mechanism for
  resumable/interrupted agent runs (LangGraph checkpointer; Claude Code session resume restores
  conversation + state).
- **Bugs:** checkpoint writes must be atomic with the ledger save (H39 whole-project commit rule,
  store.ts:240-241); never resume past a sealed/complete phase; keep keyless/no-op paths
  byte-identical.

- **Why:** F4. Field pattern: memory only helps when retrieved at the point of action, evaluated,

## 3. Cited sources (all fetched 2026-09-08)

1. **OpenAI Developers — Cookbook: "Build iterative repair loops with Codex"** —
   https://developers.openai.com/cookbook/examples/codex/build_iterative_repair_loops_with_codex
   (markdown endpoint fetched). Used for R1: the review → repair → validate closed loop; "any
   remaining issues become the next repair input"; "validation returns the remaining delta for
   the next pass"; "failures become structured feedback instead of a dead end"; validation may be
   execution, a unit test, policy check or human approval; structured (schema'd) handoffs between
   phases. (Note: the older cookbook.openai.com path 404s — the cookbook now lives on
   developers.openai.com.)
2. **OpenAI Developers — Cookbook: "Build an Agent Improvement Loop with Traces, Evals, and
   Codex"** — https://developers.openai.com/cookbook/examples/agents_sdk/agent_improvement_loop
   (markdown endpoint fetched). Used for R6: traces + human/model feedback → generated evals →
   eval gate → harness change set for the agent to implement; start with a reviewed loop (human
   approves the diff) and deepen automation as the eval gate becomes trusted — the C2 promotion
   gate's field pattern.
3. **Shinn et al., "Reflexion: Language Agents with Verbal Reinforcement Learning"** — arXiv
   arXiv:2303.11366 (abstract fetched). Used for R1/R6: agents "verbally reflect on task feedback
   signals, then maintain their own reflective text in an episodic memory buffer to induce better
   decision-making in subsequent trials"; 91% pass@1 on HumanEval; supports scalar/free-form and
   external/internal feedback signals — the design basis for fixture-failure text entering both
   the repair prompt and the lesson store.
4. **LangGraph — Persistence concepts** — https://docs.langchain.com/oss/python/langgraph/persistence
   (fetched; the langchain-ai.github.io URL redirects here). Used for R5: checkpointers persist
   thread/graph state for "resume after an interruption, recover from a failure", HITL flows and
   fault tolerance; a Store keeps durable knowledge across threads; in-RAM checkpointers lose
   state on restart (persistent checkpointer for production); prune checkpoints with a retention
   policy (R5's ledger-save discipline + log caps).
5. **Claude Code — Sessions (resume)** — https://code.claude.com/docs/en/sessions (fetched; the
   former /docs/en/resume URL 404s). Used for R5: a session "stores it locally as you work, so
   you can resume where you left off"; a resumed session restores the conversation AND the state
   saved in it (model/agent/permission/active goal), while some launch flags are not restored —
   the "what survives a resume" checklist for the journey checkpoint field design.
