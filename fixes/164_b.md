## 2. Findings — the surface through an agent's eyes

### 2a. What is HARD for an AI agent to read/operate today (each verified in source)

1. **The primary verbs carry no affordance disclosure.** `Execute P<n>` (C:1794-1806), `Run to next
   gate` (C:1807-1819), `Run module (bounded)` (C:1821-1829), Approve (C:2734-2742), Retry
   (C:1753-1764), and Oracle `Run machine verify` (C:4599-4607) have **no `title=`, no hint, no
   "what does this do / when is it enabled" text**. Only Reject gets an `aria-label` that doubles as
   validation state (C:2747-2751), and Spawn-crew (C:1847) / Wild (C:451-455) / Theme (C:957) are the
   exceptions that prove the inconsistency. A human or agent must infer Execute-vs-Run-to-next-gate
   semantics from the kbd legend (C:2004-2024) or open the Guide. NN/g rule 5: tooltips must be
   **consistent** or they are never discovered (S4).
2. **No machine-readable status summary anywhere.** Status is scattered across: header chips
   (domain, llmStatus, research, sandbox, ≈tok — C:1640-1670), the phase-title block
   (C:1733-1739), StatusBadges per phase (C:329-394), a sealed/delivery banner (C:1777-1791), the
   `done/N sealed · pct` rail caption (C:2470-2472), and the lastTest mono line (C:2069-2077). There
   is **no single parseable line** (phase X/N, gate pass/fail, lastTest label, keyed-vs-floor,
   fixtures pending/approved) and **no `data-*` attribute** an agent can read from the DOM. An
   operator must stitch ≥5 regions to answer "where is this run, and is it healthy?".
3. **Gate status is not on the rail.** `PhaseProgressRail` segments (C:2474-2522) carry only
   phase-status color + `title="${code} · ${title} · ${label}"` (C:2507) — **no gate pass/fail, no
   unmet-count** — even though `rec.gate` (passed/unmet/evidenceHash) is rendered two clicks deeper
   in `PhaseRecordView` (C:5116-5128) and the census ("Sealed with N failed gates") exists at
   C:1780-1784. The most decision-relevant fact (did the DoD gate actually pass?) is invisible at a
   glance.
4. **The in-app guide is prose-only and omits the operator contract.** `GuideDialog` (C:5408-5422)
   renders `GUIDE_SECTIONS` (C:886-907) — five static title/body paragraphs (what it is, honesty
   contract, how to use a project, feed results back, what it is not). Missing: the **verb list with
   gate semantics**, the **12-char rejection rule** (only in HitlDock live counter C:2711-2721), the
   **RT_E exit-code pointer**, **keyed-vs-keyless behavior** (partially in section 2 body), and any
   **context-aware "what can I do right now"** (blocked→Retry, hitl→Approve/Reject, ready→Execute,
   running→wait). It is a summary of AGENT_GUIDE.md (footnote C:5418), not an operator cheat-sheet.
   AGENTS.md is the repo contract (agents.md S3: a *predictable, dedicated* place for agent
   instructions) — but nothing in-app tells the *console* operator those verbs.
5. **Error codes reach the UI only on the chat/wild/telemetry paths.** RT_E codes render in chat
   rows (C:4365-4379 normalize + render), in the wild-stale message (C:663), and as a code chip in
   the runtime ring (C:3268). The **main run-error alert renders prose only**
   (`{error}` in an `rt-alert-err` — C:2059-2063), because the primary store envelopes return
   `{ok:false; error:string}` with **no code field** (S:37 — only WildRunResult has `code?: ErrorCode`
   at S:69). So the alert cannot show `RT_E_*`, cannot link to `ERROR_CODE_DOC`'s ready-made
   `agentAction` line (E:191), and an agent watching the DOM cannot branch on a machine value.
6. **Packet view is rendered-markdown only; no raw/log view, no search.** The Agent-packet tab
   (C:2247-2274) is a `term-frame` (C:2250-2266) with a `MarkdownBody` render — scrollable
   (`max-h-[460px]`), but there is **no raw-toggle** (an agent wanting the exact bytes must copy from
   rendered text), **no in-packet search**, and the "empty" line is a bare instruction (C:2269-2272).
   The Runtime-log tab (C:3201-3282) shows the **global** telemetry ring only — `project.logs`
   (`JsonLog[]`, T:299 — autopilot.gate_denied etc., consumed at C:2784-2789) has **no per-project
   events view** at all.
7. **A long keyed synthesis looks hung.** During `Execute`, the only cues are the button label flip
   to "Running…" (C:1805), a spinner (C:1800-1804), a tiny pulsing mono "running…" (C:1830-1838) and
   `aria-busy` on the section (C:1720). There is **no elapsed clock, no sub-step feed, no
   progress** — with `stream:false` hardcoded (162 D3) a 1–3 min synthesis is visually
   indistinguishable from a dead tab. Wild mode has the live strip (`WildConsole` C:489+, polling
   feed C:499+) — the plain run has nothing comparable.
8. **Empty/loading copy is uneven.** Good: runtime ring empty state explains *why* it is empty
   ("Honest silence…" C:3251-3255), artifact-filter empty names the filter (C:2239-2243). Thin:
   packet empty (C:2269-2272), Oracle no-run copy (C:4586-4592), verify-not-configured note
   (C:4537-4539). None of the empty states say **what to do next**.

### 2b. What a 10/10 operator surface needs (the bar this wave targets)

- Every verb discloses itself before the click (hover + focus + SR), consistently (S4).
- One glance line: `phase X/13 · gate pass · lastTest tested · keyed · fixtures 3/3` — human-readable
  **and** DOM-parseable (`data-rt-*`) **and** present as a single mono string an agent can regex
  (Claude Code's statusline precedent: a persistent, at-a-glance machine-fed status row — S1).
- Gate pass/fail rides on the phase rail where the eye already tracks progress.
- Errors carry `RT_E_*` with meaning + agent action (E already documents both — surface it).
- A raw packet/events view: terminal-style, searchable, copyable (the "packet view" taste).
- Busy states that prove liveness (clock + incremental activity rows), honest empty states that name
  the next action.
- Guide = operator cheat-sheet (verbs, gates, codes, honesty), context-aware first pane.

## 4. U-01 — Hover/focus tooltips on every primary verb

**What.** Consistent affordance disclosure on the run-loop verbs and the header/dock actions that
lack it. Each button gets: (a) a `title=` (native tooltip — hover **and** long-press/touch; already
the file's idiom, 35 uses), (b) `aria-label` or visually-hidden companion text only where the visible
label is ambiguous, and (c) where a click can be blocked, the *disable reason* in the title (NN/g:
tooltips must say something the label does not — S4 rule 2; keyboard users must reach them — S4 rule
3; MDN: `title` = advisory info — S5).

**Why.** The verbs Execute-vs-Run-to-next-gate-vs-Run-module and Approve-with-force-override are the
entire product's controls, and they are the least self-describing controls on screen (2a.1). One
shared hint map kills the inconsistency that makes tooltips undiscoverable (S4 rule 5).

**Where (all in C).** Execute (C:1794-1806), Run-to-next-gate (C:1807-1819), Run module
(C:1821-1829), Retry phase with notes (C:1753-1764), HitlDock Approve (C:2734-2742) + Reject
(C:2743-2756), Copy agent packet (C:1857-1864), Copy phase handoff (C:1865-1872), Download packet
(C:1883-1890), Export (C:1891-1898), Copy JSON (C:1899-1906), Clone (C:1873-1882), Ingest report
(C:1907-1913), Archive (C:1924-1930), Run machine verify (C:4599-4607), Export software (C:5254-5262),
retry-blocked guidance (C:2806+).

**How to wire.**
1. New module-level `const VERB_HINTS: Record<string,string>` near GUIDE_SECTIONS (C:886) — exact
   strings in §7.1. Apply as `title={VERB_HINTS.execute}` on each button.
2. Where a button is currently disabled with no explanation (Approve when `needsOverride` — C:2737;
   Reject when note < 12 — C:2746), compose the title dynamically:
   `title={noteTooShort ? "Disabled — rejection note must be ≥12 characters" : VERB_HINTS.reject}`
   (mirror of the existing aria-label pattern at C:2747-2751, which stays).
3. Optional richness (only if a follow-up wave wants styled tooltips): `@radix-ui/react-tooltip`
   **is already installed** (P) — wrap the shared hint in a `Hint` component that renders Radix
   Tooltip for hover + focus, with `aria-describedby`; native `title` remains the zero-risk default
   and both can coexist (Radix Tooltip does not suppress `title` unless configured).
4. Do **not** put hint text only in `title` for buttons whose visible label is already exact
   (e.g. "Copy agent packet") — those get a *consequence* hint instead ("copies the compiled packet
   markdown — paste into your coding agent"), per S4 rule 2.

**How to test (bug-test).**
- New colocated pure test for the hint map (or a snapshot-ish test): every key referenced by a
  rendered button exists; every hint is ≥ 1 clause that names the *effect*, not just restating the
  label ("no-op hint" regression pin — asserts `hint !== label` for the verbs list).
- Console bug-test: mount RunScreen with a project in `ready` state; assert Execute/Run-to-gate
  buttons carry `title` and that the disabled-Approve case (failed P6 sandbox, forceHuman) carries
  the override reason; keyboard: `Tab` to Approve → `aria-label`/`title` reachable (native title is
  announced by some SRs; the sr-only companion at C:2757-2761 covers the rest).
- Regression pins: Wild toggle title (C:451-455), Spawn-crew title (C:1847), ThemeToggle title
  (C:957) must remain byte-identical (do not "normalize" existing good hints).

## 5. U-02 — Machine-readable one-glance status line (+ rail gate badges)

**What.** Under the project title block (next to the lastTest line, C:2069-2077), render one mono
line in the format §7.3, backed by a new pure helper, AND stamp the same facts as `data-rt-*`
attributes on the status container so any agent can read the DOM once. Add gate pass/fail + unmet
count to each `PhaseProgressRail` segment's `title` and aria-label (C:2507-2508).

**Why.** 2a.2/2a.3: an agent today must merge 5+ regions to answer "where is the run, is the gate
healthy, did the last test pass, am I keyed, are fixtures approved?" Claude Code's statusline
(S1) shows the pattern that wins: one persistent row, fed by machine state, that renders "context
window, costs, git" — the equivalent here is pipeline state. DOM `data-*` makes it scriptable
without a screenshot or OCR.

**Where.** C — header block after C:2077 (reuse the mono `text-xs` style of C:2069-2077); rail
segments C:2507-2508; helper can live in C above RunScreen or — better — a new client-safe pure
module `src/lib/run-status.ts` (mirrors house pattern: pure + colocated `*.test.ts`, append to the
explicit npm-test `.ts` list per AGENTS.md + 162 §8.2 — the list is explicit, not globbed).

**How to wire.**
1. `src/lib/run-status.ts` (new): `summarizeRun(project: Project): RunSummaryLine` with fields:
   - `phase: \`${currentPhase+1}/${PHASES.length}\`` (from `project.currentPhase`, T:277);
   - `gate: "pass" | "fail" | "pending" | "n/a"` — current phase record's `gate.passed`
     (absent → "pending"; complete-with-failed-gate census → "fail", mirror of C:1780-1784);
   - `lastTest: "tested" | "self-test" | "real-run" | "untagged" | "none"` from
     `project.lastTest.label` (T:332) via the existing `LAST_TEST_LABEL_TEXT` map (C:135);
   - `mode: "keyed" | "keyless"` — honest derivation today: `llmStatus.configured` (global chip,
     C:1642) AND the project shows keyed evidence (`lastTest.label === "tested"` or a provenance
     row, T:103/E-18); when 162 A4/B2 land producer stamps / `synthesisSucceeded`, switch the
     source to those (documented hook, absence-tolerant);
   - `fixtures: "3/3 approved" | "pending" | "—"` reading the **additive** `acceptanceFixtures`
     field 162 A1 adds (render `—` when the field is absent so the line is byte-stable pre-A5);
   - `unmet: number` of open gate's unmet criteria when gate is pending/fail.
   Returns the formatted string **and** the raw field map (one function, two shapes — string for
   humans/terminal, map for `data-*`).
2. Render: `<p data-rt-run={line} data-rt-phase={…} data-rt-gate={…} data-rt-lasttest={…}
   data-rt-mode={…} data-rt-fixtures={…} role="status" aria-live="polite">` — aria-live so a
   watching agent (or SR) hears gate flips; the mono string is inside the element for regex
   capture. One component `<RunStatusLine project={project}/>`.
3. Rail: extend the segment `title` (C:2507) to
   `` `${p.code} · ${p.title} · ${label} · gate ${rec.gate ? (rec.gate.passed ? "pass" : `FAIL (${rec.gate.unmet.length} unmet)`) : "pending"}` `` and add a tiny ✓/✕ glyph (aria-hidden) on
   complete segments — no layout shift (absolute top-right of the segment or the existing lblTone
   color classes, C:2482-2501).
4. Enforce-DoD state is already a sidebar toggle (C:5201); include `enforce: on|advisory` in the
   line when it differs from default (keyed default = on, 162 §8.6).

**How to test.**
- Pure unit tests (new `run-status.test.ts`, appended to npm-test list): fixture projects
  (ready/blocked/hitl/complete-failed-gate/keyless/keyed-with-tested) → exact expected line
  strings; absence of `acceptanceFixtures` → `fixtures —` (pin: no A5 field yet = stable output);
  a complete project with a failed gate → `gate fail` naming the census (pins fixes/133 behavior
  C:1780-1784 so the line can never contradict the banner).
- Console bug-test: mount each fixture project; assert the container's `data-rt-gate` etc. equal
  the helper's map; assert the rail segment for a rejected phase carries `gate FAIL` text; assert
  no `title`/glyph change when `rec.gate` is undefined (locked phase — no crash).
- A11y pin: `aria-live="polite"` present; status changes (approve → next phase) update the line
  within one store tick.

## 8. U-05 — Error-code surfacing on the main run alert

**What.** The run-loop failure alert (C:2059-2063) renders an RT_E code chip when the failure
envelope carries one, with the `meaning` + `agentAction` from `ERROR_CODE_DOC` (E:191) as the
chip's `title` — plus an expandable "what an agent should do" line. Today the primary envelopes
cannot carry a code (S:37), so this wave also makes the code field additive on those returns.

**Why.** 2a.5. E already defines the full contract — `codeError`/`classifyError` builders and a
per-code `agentAction` line telling an AI agent what to do — and the chat path already renders
codes (C:4365-4379). The main path (execute/approve/reject/retry/verify) drops the machine value at
the store boundary; the UI then cannot branch, and neither can an agent watching the DOM. The
honesty contract (AGENTS.md rule 4: every surfaced failure carries its RT_E code) is met in the
CLI and chat but **not** on the console's primary alert.

**How to wire.**
1. Store (S): add `code?: ErrorCode` to the prose-only failure shapes at S:37/S:73/S:143 — additive,
   absence = today's behavior (byte-parity for existing consumers; no renames). Populate at the
   throw/return sites with `classifyError(err, "RT_E_INTERNAL")` (E:120) where an `Error` is being
   stringified today (e.g. S:851/S:886). ApproveResult keeps `{ok:false; error; code?}` — no
