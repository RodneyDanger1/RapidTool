## 1. 167-C-1 — `run.finish(accepted)` semantics: a governed run has NO single terminal acceptance; status "complete", exit code, and evidence are written by different code and CAN disagree

- **WHAT (the missing safeguard):** SSSF runner.py:114-142 defines one terminal writer:
  `finish(accepted)` = `phases_ok AND accepted`, and ONE call settles the db row, the banner, and the
  exit code "so the three cannot disagree." Its docstring names the exact bug class it replaced: a
  `succeeded` property that, being a property with side effects, wrote session status + banner BEFORE
  the caller's `and test.passed` was evaluated — a run whose suite never passed was recorded green in
  the db, on the terminal, and in the UI while exiting 1. **RapidTool has the same split-brain today:**
  the *phase bookkeeping* terminal (`project.status === "complete"`, flipped as phases complete,
  engine.ts:1537-1542 / approveHitl and the drain) is one question; the *acceptance* question (every
  recorded DoD gate green — `sealHonesty`, engine.ts:1183+) is a separate flag computed after the fact;
  the *exit code* is a third site (CLI). Evidence they disagree today: `run`/`gate` SAVES the
  `status:"complete"` project to disk at rapidtool-cli.mjs:412 and only THEN computes
  `sealed.sealedWithFailures` (:421-422) and exits 1 `RT_E_GATES_FAILED` (:426-440). The saved project
  JSON says "complete"; the exit says failed; the UI rail and any agent that reads
  `.rapidtool/project.json` without parsing the CLI envelope sees a completed run. 165-C-1 (repair
  converges on red gate), 164-F2 (`executeAsync` returns ok:true on a hard-DoD block) and 163-C 9.6
  (tested minted before gate read) are the same class leaking in three more seams. SSSF's "test phase
  ran a red suite → PHASE succeeded, RUN not accepted" maps 1:1 onto RapidTool's "phase record complete
  with a red gate → phase bookkeeping done, run NOT accepted" — except RapidTool never records the
  second half as a first-class project field.

- **WHY:** every consumer that keys on `project.status` (console rail, import/hydrate, summary, agents
  chaining `run` → `emit`) can be told "complete" by a run the exit code calls failed. The honesty
  contract's own rule — "a red-gate complete seal exits 1 (`sealedWithFailures:true`)" — only holds for
  consumers of the CLI envelope, not for consumers of the persisted project. Phase A (162) makes this
  worse: A6 keys journey/DoD on the fixture pass; without one acceptance writer, "fixtures red but
  phases complete" will mint yet another partial green (the A6 "never mint tested on failed fixtures"
  rule needs a home that one writer owns).

- **WHERE:** (1) new pure `src/lib/dod.ts` or engine helper `runAcceptance(p): {accepted: boolean;
  reasons: string[]}` = phases all complete AND `sealHonesty(p).clean` AND (Phase A, additive) approved
  fixtures absent-or-green; (2) the terminal writers that must call it: `headless.ts` runUntilGate
  terminal branch (:582-629 — move the outcome/`sealedWithFailures` derivation BEFORE the project is
  returned so the returned project already carries the verdict), `engine.ts` `wildFinalize` (:3444-3455,
  which today stamps `status:"complete"` + "all 13 phases sealed" without consulting `sealHonesty`),
  and the CLI `run`/`gate` arm rapidtool-cli.mjs:404-453 (compute acceptance BEFORE `saveProject` at
  :412, save the verdict on the project, exit from the same object); (3) an additive
  `Project.acceptance?: {accepted: boolean; reasons: string[]; decidedAt: number}` field in types.ts
  (+ hydrate + io sanitizer mirror of the `generatedTree` pattern — additive, default ABSENCE so
  legacy/keyless byte-parity pins hold; io.ts:45-283 pattern).

- **HOW TO CODE:** `runAcceptance(p)` is pure and tiny: `complete = p.status === "complete"` (or all
  13 phase records complete — pick the existing terminal predicate runUntilGate uses at :512),
  `clean = sealHonesty(p).clean`, reasons = the `failedGates(p)` census when not clean + a
  fixture-gate clause (Phase A: when `acceptanceFixtures` has ≥1 approved entry, require the runner's
  fixture TAP green — dod.ts `p6-verified` :337-355 already shows the "read the runner, never re-scan
  source" idiom). One writer `finalizeRun(p, opts)` stamps `acceptance` + the terminal log
  (`delivery.complete` stays; when `accepted:false` the log level is warn and the census is named —
  today's :582-604 warn becomes the acceptance reason, not a separate side channel). CLI arm: reorder
  to `const fin = finalizeRun(res.project); saveProject(path, fin.project); respond(..., fin.accepted
  ? 0 : 1)` — exit code derives from the SAME object that was saved. The `parked → 2` branch is
  untouched (not a terminal state).

- **HOW TO TEST:** (a) unit: a project whose 13 records are complete with one recorded
  `gate.passed:false` → `runAcceptance` returns `accepted:false` naming P<id>(unmet) — today no field
  exists to assert; (b) CLI: `gate` a complete-with-red-gate project → the SAVED JSON carries
  `acceptance.accepted:false` (today it saves bare `status:"complete"`), exit 1 unchanged (parity);
  (c) clean drain → `acceptance.accepted:true`, exit 0 byte-identical envelope (parity pin); (d)
  legacy payloads (no field) serialize identically — absence, not `false`; (e) Phase-A hook: approved
  fixtures present + spec red → `accepted:false` naming the cases (this is the assertion 162-A6 wants
  but currently has no single field to write).

## 2. 167-C-2 — Kill-honesty: no terminal writer fires on SIGTERM/SIGINT; a killed run's project and trace can read "in flight"/"complete" forever (SSSF `_finalize_when_killed`)

- **WHAT:** SSSF session.py:21-36 installs SIGTERM/SIGINT handlers that (a) write
  `session_finish(adw_id, ok=False)` — closing its own trace + process rows — and (b) re-raise as
  SystemExit so the phase context manager records the in-flight phase as FAILED on the way out. Its
  docstring: "just `kill` … would leave the session reading `running` forever … the trace would claim
  work is in flight that is already dead." RapidTool's CLI (rapidtool-cli.mjs) has no signal handler;
  a kill mid-`run`/`gate`/`repair`/P6 journey leaves the project JSON at its last per-invocation save
  (163-C 9.7 P1 already logged the crash/resume half: "Project JSON saved once per CLI invocation; P6
  journey cycles are in-memory") and the NDJSON session rows never receive a terminal event — a
  consumer of `<dir>/.rapidtool/logs` cannot distinguish "killed" from "still running" except by
  absence of a row.

- **WHY:** kill is a normal operating event for a long keyed run (240s timeouts, budget cycles, agent
  Ctrl+C); without a kill-time terminal stamp the evidence trail lies in the same direction every
  other fix in this dossier fights: toward "green / in-flight" instead of "failed/aborted". This is the
  crash half of the run.finish discipline (167-C-1): ONE terminal writer, invoked on the normal end
  AND on the signal path.

- **WHERE:** `scripts/rapidtool-cli.mjs` main() (the outer handler at :1953-1961 is the natural
  place to install handlers next to), plus the runtime-log appender seam
  `src/lib/runtime-log.server.ts:110+` (`appendRtEvent`-style writer already exists) and a `RtEvent`
  `scope`/event value like `run.aborted` (schema `makeCliRow` :65-90 is additive-safe). Fold the
  per-cycle checkpoint recommendation into 163-C 9.7 P1 (already in the plan queue) — this finding
  supplies the *signal-side* writer that checkpointing lacks.

- **HOW TO CODE:** mirror SSSF session.py: in the CLI, before dispatching a verb that mutates a
  project, install `process.on("SIGTERM"/"SIGINT")` handlers that (1) stamp one NDJSON row
  (`level:"error"`, `event:"run.aborted"`, `code:"RT_E_INTERNAL"`, message naming the verb + pid —
  reuse `makeCliRow`), (2) when a project path is mid-invocation and the project was already loaded,
  append a capped `aborted` log entry to the in-memory project and `saveProject` it (atomic
  write-then-rename already exists, headless.ts:77-93) so the on-disk project never claims a state
  past the last completed phase, then (3) exit `128 + signum` (SSSF convention). Never install in the
  library/engine layer — CLI-process concern only (browser/store concurrency rules untouched).

- **HOW TO TEST:** spawn the CLI `gate` verb on a project parked at an `awaiting_hitl` gate (or a
  fake long sleep via a stub verb in the test), send SIGTERM mid-invocation → assert (a) exit code is
  130/143-class, (b) `.rapidtool/logs/rapidtool.ndjson` gained exactly one `run.aborted` row naming
  the verb, (c) the saved project JSON's last log entry is `aborted` and `currentPhase` is unchanged
  from the last completed phase (no fabricated advance). Second: kill a plain `summary` (read-only)
  verb → NO aborted row on the project (read-only verbs must not stamp). Use the child-process test
  pattern of exec.test.ts (spawn + signal), never an in-process handler test.

## 3. 167-C-3 — Rerunnable evidence: no per-LLM-call prompt→response record exists; the attempt journal deliberately excludes the prompt (gpt-engineer memory logs / SSSF prompt-save + raw envelope)

- **WHAT:** both factories persist the actual conversation per step. gpt-engineer `memory.log`s the
  full message list per step to disk (CODE_GEN/ENTRYPOINT/IMPROVE/DEBUG logs; steps.py:148, :201,
  :308-311, :358-359) with archive rotation (cli main.py:501); SSSF saves the RENDERED system.md +
  user.md before every agent call (agents.py:91-92) and persists every envelope — including INVALID
  attempts as the raw tail (`_persist_envelope`, agents.py:290-300: `json.dumps({"raw":
  raw[-2000:]})`) — so a failed run is re-runnable and reviewable from disk alone. RapidTool's closest
  artifact is the `p6.synthesis.attempt` journal (codegen.server.ts:844-900), which records
  chunk/attempt/timeoutMs/outcome/refusal-first-160-chars and whose own comment states the design
  limit: "**Additive context only: no prompt**, refusal string or terminal event changes." Artifacts
  carry FNV-1a evidence hashes and NDJSON CLI rows carry `ctx`/`payload` (runtime-log.server.ts:65-90)
  — but nowhere on disk is the ordered pair "what we asked the model (full prompt) → what it returned
  (full text)" for a keyed synthesis/repair/verify call. An operator cannot re-run a failed synthesis
  from evidence, cannot audit what a refusal actually refused beyond 160 chars, and cannot diff two
  attempts' prompts (the fixes/153 rotating-failure-class hunt had to be re-derived from code).

- **WHY:** "rerunnable evidence" is the operational half of artifact provenance (162-B2 stamps who
  produced; this stamps what was asked and what came back). Every honest-repair and lesson loop
  (162-C1 read-back, 9.5 expected-vs-actual delta) is only as good as the recorded exchange. It is
  also the cheapest safeguard to add because the appender machinery exists.

- **WHERE:** new writer beside `src/lib/runtime-log.server.ts` (reuse `makeCliRow`/rotation/
  `sanitizeRtEvent` — NDJSON, bounded, off the project JSON so NO byte-parity pin on project/log
  arrays moves); a `recordLlmExchange` seam injected through the existing deps objects that already
  carry the `complete`/`onAttempt` seams: codegen.server.ts `P6SynthesisDeps.complete`
  (:1208 attempt wrapper is the model-call choke point — single-module AND chunked paths), the repair
  re-prompt sites (:204-331), verify.server.ts `generateCases`, and crew/chat if trivial. Keyed runs
  only; keyless/floor paths write nothing (parity).

- **HOW TO CODE:** one NDJSON row per model call: `{schema_version, ts, host:"cli", sessionId/runRef,
  scope:"llm", event:"llm.exchange", phase, step (e.g. "p6.chunk2.attempt1" | "repair" | "verify"),
  promptChars, promptHead: prompt.slice(0,2000), responseHead: text.slice(0,4000), outcome,
  refusalText (full, not 160), usage:{promptTokens,completionTokens}}`. Heads, not full bodies —
  rerunnable triage + audit without unbounded disk (full bodies remain in artifacts when the parse
  succeeded). Rotation already caps at LOG_KEEP files. Add the 162 §13.8 no-secret advisory scan
  (flag `sk-`/`api_key`/long-digit/email in the row) — do NOT redact silently, surface at diagnose
  time. Prompt text may contain the brief's PII — this is exactly why it is a NEW bounded store under
  `.rapidtool/logs/`, not an addition to project JSON.

- **HOW TO TEST:** (a) a keyed synthesize (injected fake `complete`) fires one `llm.exchange` row per
  attempt incl. repair attempts, each with promptHead/responseHead + usage; (b) keyless path writes
  zero rows; (c) rotation: fill past the byte cap → `.1`/`.2` appear, oldest dropped, appender never
  throws (mirror runtime-log rotation tests); (d) byte-parity: project JSON `logs` array for the same
  run is byte-identical with the seam on vs off (the record lives only in the NDJSON store); (e) the
  refusal row carries FULL refusal text (regression for the 160-char slice limitation).

## 4. 167-C-4 — Config/args fail-fast: collect-ALL-problems + option-conflict preflight before side effects (SSSF `agents.validate` / gpt-engineer mode-conflict exit)

- **WHAT:** SSSF `agents.validate(cfg, REQUIRED_AGENTS)` (agents.py:52-73) is the pattern: an ADW
  declares its required agents, and validation runs BEFORE anything spawns, collecting EVERY problem
  (unknown agent, unimplemented coding_agent, missing prompt file, unresolvable model) into one list
  and raising SystemExit with the full report — the caller fixes all of them in one pass, never
  whack-a-mole. gpt-engineer cli main.py:443-445 is the option-conflict variant: `if improve_mode and
  (clarify_mode or lite_mode): error + exit(1)` BEFORE loading env, constructing the AI, or touching
  the project dir. RapidTool's import-side validation is strong (io.ts:45-283 coerce-or-drop +
  shape-validation fail-fast at :283; and this session VERIFIED `headless.loadProject`
  headless.ts:65-72 delegates to `io.importProject`, which RESOLVES the 164-A weaker/verify item
  "confirm the CLI file loader shares the same validation" — it does). What is missing is the CLI
  ARG-SET preflight: validation is per-verb, first-error-wins (`respond(...,"RT_E_VALIDATION",1)` at
  each arm), and silent-fallback classes exist (165-C-5 `deepen --phase <garbage>` deepens
  currentPhase; 165-C-6 `wild --steps 0` runs the default 24 — both already filed; they are SYMPTOMS
  of no up-front arg validation). No verb reports "these 3 flags are wrong" in one response.

- **WHY:** an agent chaining verbs pays one round-trip per bad flag (first-error-wins), and the
  silent-fallback class mutates the WRONG phase/state with exit 0 — the most expensive failure mode in
  the taxonomy. The fix is mechanical and kills 165-C-5/6's whole class rather than patching verbs one
  at a time.

- **WHERE:** a shared preflight helper next to the arg parsing in `scripts/rapidtool-cli.mjs`
  (parseArgs region before the `case` dispatch at :351), invoked per verb with a tiny declarative
  spec: `preflight(spec, args)` where spec = expected type/range/enum per flag + conflict pairs.

- **HOW TO CODE:** pure helper `validateArgs(spec, rawArgs) → {ok:true} | {ok:false, problems:
  string[]}` (mirror SSSF: accumulate, don't throw on first). Spec entries: `{flag:"phase", test: v =>
  /^\d+$/.test(v) && +v in {0..12}, message: name the user's value}`; conflicts:
  `{flags:["a","b"], message}`. Each verb's `case` calls it FIRST (before `loadProjectFor`, before any
  fs write); on `ok:false` respond once with the FULL problem list, exit 1. Port the existing
  hand-rolled checks (repair `--budget` :850-851, emit `--out`, tree-run `--dir`, wild `--steps`) onto
  the spec so behavior is unchanged but aggregated.

- **HOW TO TEST:** (a) `deepen --phase seven --live` (two bad flags) → exit 1 with BOTH problems in
  one envelope (today: first error only, and `--phase seven` today silently deepens currentPhase —
  assert project file byte-unchanged); (b) `wild --steps 0` → exit 1 RT_E_VALIDATION naming 0
  (regression for 165-C-6); (c) conflict pair on the verb that will carry one (e.g. when Phase A adds
  `emit --verify-kind` + `--no-verify` style combos) → exit 1 before any dir write (gpt-engineer
  pattern: assert the target dir is untouched); (d) existing green CLI tests byte-identical (spec
  port must not reorder/rename envelopes).

## 5. 167-C-5 — Real per-step usage metering: the client returns usage but every call site drops it; M8 keys on synthetic bench (162-B3 remaining work, re-anchored)

- **WHAT:** both factories meter real usage per step: gpt-engineer `TokenUsageLog.update_log` runs
  after EVERY model call with the step name and prints the run total at the end (token_usage.py:
  193-207; ai.py:245; cli main.py:552-557); SSSF accumulates every send — including JSON-fix and gate
  retries — into the phase/run totals and emits `agent_end` events carrying PHASE totals (not the last
  send's) with the cost in the console banner (agents.py:134-135, :208-213 — its comment: "a retried
  phase paid for every attempt"). RapidTool's client already returns usage on the ok path
  (deepseek.server.ts ok-return carries `usage:{promptTokens,completionTokens}` — 162 §12 #3
  verified), and `LlmResult` types it (llm.ts:18-23) — but THIS session's grep shows no consumer:
  codegen.server.ts never reads `.usage`, headless.ts/store.ts have no accumulation field, and
  `bench.ts` remains honestly synthetic (`estimate:true`, bench.ts:2-35, ESTIMATE_DISCLAIMER). So
  162-B3's remaining work is exactly: accumulate + ledger + M8 + run-eval evidence — and 167-C-3's
  `llm.exchange` row is the natural per-step ledger row (one write serves rerunnable evidence AND
  metering).

- **WHY:** "bounded" (M8) and any cost claim are only truthful against measured usage; today the only
  machine-readable usage is synthetic estimates labeled as such, and the real numbers the API returns
  are discarded. Retried/refused attempts are the expensive ones (a failing tree = 3× pro calls,
  164-A F6) — exactly the usage an operator needs to see.

- **WHERE:** (1) codegen synthesis/repair call sites that own `LlmResult` (the `complete` seam and
  `attemptObservedComplete` wrapper codegen.server.ts:900-920 are the choke points); (2) additive
  `Project.runUsage?: {promptTokens; completionTokens; estimatedCostUsd?; model}` (+ hydrate + io
  sanitizer, absence-default) OR the NDJSON `llm.exchange` row of 167-C-3 — recommend BOTH fields on
  the NDJSON row and a single accumulated run total on the project for M8; (3) maker-score.ts M8 +
  run-eval.mjs read the accumulated real usage when present, bench.ts stays the labeled-estimate
  fallback (its own honesty contract).

- **HOW TO CODE:** extend the attempt journal accumulator to sum usage alongside attempt events
  (pure: `addUsage(acc, res.usage)`), thread the sum to the terminal P6 log path (the same
  `pushAttemptLog`/ride-onto-project region :920-940), write the NDJSON row per 167-C-3 with usage
  fields, and store the run total additively on the project at `finalizeRun` time (167-C-1 writer —
  the two findings compose). M8: when `project.runUsage` exists, cite it; else cite bench with its
  existing estimate label. Never invent usage where the client returned none (absent ≠ 0).

- **HOW TO TEST:** (a) inject fake `complete` returning usage on attempts 1-3 (2 failures + success)
  → run total = sum of all three (regression for "retried phase paid for every attempt"); (b) a
  refused run (no ok-path usage) → no `runUsage` field minted (absence, not 0) and M8 evidence cites
  bench labeled estimate; (c) unit: `addUsage` pure accumulator with the byte-parity absence default;
  (d) run-eval: a keyed run's results.json M8 row carries real `promptTokens`/`completionTokens`.

## 6. 167-C-6 — Run-start idempotence marker + join-or-create evidence dir (SSSF pinned `adw_id` analog) — small

- **WHAT:** SSSF `session.ensure(cfg, adw_id)` (session.py:38-50) pins-or-creates the run id: a
  pinned id JOINS the existing session (continuing the phase sequence and the agent context map,
  runner.py:52-58 `max_phase_seq`) — re-running the same workflow over the same work is a first-class,
  detectable continuation, and every trace row is keyed by that id. RapidTool keys CLI evidence rows
  by a per-invocation `sessionId` and persists per project dir, but has no run-level id stamped on the
  PROJECT at run start: a re-run of the same project is only distinguishable by log timestamps, and
  163-C 9.7 (per-cycle checkpoint/resume) + 165-C-2 (emit dir never reconciles) show re-runs are where
  state wedges. Small, additive transfer: mint `runRef` at run start, stamp it on the project
  (`Project.lastRunRef?: string` additive), carry it on every NDJSON row (the field already exists on
  RtEvent, runtime-log.server.ts:65-90, `runRef` — but is seeded from where? verify the CLI seeds it
  per run; if unseeded today, this finding names the gap), and have `run`/`gate`/`repair` refuse-or-
  loudly-continue when the on-disk `lastRunRef` row shows the previous invocation died without a
