## 1. Code-grounded assessment: the slice is mechanically sound and semantically empty

Bottom line first: every machine check on the LLM artifact's path to "tested" verifies **shape, identifier presence,
compile-parity, or scaffold stub-truth**; the one real behavioral executor (`runCases`) is **LLM-authored, A7-unseeded,
single-module-only**, and too narrow to express I/O equality or rejection semantics. Nothing executes the produced
artifact against a brief-derived expectation. The slice's honesty mechanisms (loud refusals, honest partials, honest
skips, mint gates) are real — which is exactly why the ledger correctly records an all-refused, stub-green, sealed run.

### 1.1 codegen.server.ts — the ask is an envelope of names, not behavior; the chunked path has no behavioral gate

- **The prompt carries prose requirements, never examples.** `p6SynthesisChunkUserPrompt` (codegen.server.ts:373-425)
  renders BRIEF → REQUIREMENTS (394-395) → TYPE SIGNATURES (397-398) → NEGATIVE CONSTRAINTS (400-401) → EDGE CASES
  (403-404) → EARLIER-FILES context (406-423). Requirements are one-sentence prose with a "// req-N" comment ask
  (394). There is **no example input → expected output anywhere** — confirmed by reading the full builder. `reqTrace`
  (envelope parse, 579-584; type, 548-552) maps `req-N → exported NAME`; nothing in the envelope can express
  "createProperty({address}) returns {id, history: []}". Confirms 155_structural §4.
- **Deterministic validation is shape-only.** `validateSynthesisModule` (661-702): non-empty, ≤60k chars, no fences,
  no forbidden primitives, claimed exports bound (`declaredNames` regex scan 614-624), signature names present in the
  exports list. `briefFitSatisfied` (709-714) = ≥ half of brief nouns as sub-identifiers. A module whose bodies are
  `throw new Error("todo")` passes all of it. Confirms 155_structural §4.
- **The single-module path is the only behavioral path, and it is legacy-only.** ≤8-signature, kind-absent projects
  route to `synthesizeSingleModule` (1156-1158 → 1176-1326), which runs `verify(source, brief, {maxIterations: 3})`
  (1300) — the LLM-authored-case runner of §1.3. **Every declared kind ("app"/"tool"/"game") and every >8-signature
  spec routes to `synthesizeChunkedTree` (1160), which by design runs NO machine verify** (comment 1339-1341: "No
  machine verify here — per-file deterministic validation is the mechanical floor; the tree machine-run is the tree-run
  lane's step"); per-chunk acceptance is envelope-parse + shape validation + export injection only (`synthesizeChunkEnvelope`
  1416-1476); the tree-level gate is `briefFitSatisfied` over the assembled entry (1390-1404). Confirms 155_structural §4.
- **The partial-assembly floor leak is real on the chunked path.** `partialTreeRefuse` (1488-1507): when ≥1 chunk was
  accepted it assembles those real files into a runnable `generatedTree` + `generatedSource` (1496-1504) and refuses
  from there. Real LLM files, but a **partial product with no behavioral bar** — a keyed run can then reach treeRun
  with a tree that only ever satisfies shape checks. (P0-3 target; unchanged on disk at study time.)
- **Assembly semantics enable a headless behavioral runner.** `assembleTreeEntry` (516-537) wraps each file in an IIFE
  whose params bind earlier files' exports (`module.exports.<n>` passed as args, 526-528); the entry's export surface
  is the union of per-file `module.exports` writes; the entry string is stored as `generatedSource` and the tree files
  at their own paths. The emitted dir therefore contains an importable `src/generated.ts`-shaped entry (scaffold
  assembly, scaffold.ts:1845-1912). **A fixture spec can `import * as treeModule from <entry>` and call the exports —
  for webapp-kind trees too**, because the entry is plain CJS-exported functions, not DOM code.
- **Synthesis never mints "tested"; the tree-run does — on whatever specs exist.** `treeUpgraded` (1521-1578)
  deliberately leaves `lastTest` untouched; `mintTreeRunTested` (1629-1668) mints only when `treeRunTestedEvidence`
  reports ≥1 spec file pass with ≥1 assertion (1595-1610). Today those assertions are the oracle-spec's stub-truth
  rows (§1.4), so a webapp tree's "tested" mint is stub-certified.

### 1.2 deepseek.server.ts — empty content is diagnosed, never recovered; the fallback ladder is absent

- Call builder (329-338): pro tier sends `thinking:{type:"enabled"}` + `reasoning_effort:"high"` **and** json mode
  (`response_format:{type:"json_object"}`, 336) with the caller's `maxTokens` (codegen passes 32k, codegen.server.ts:105/1190).
  Flash tier disables thinking (334). The empty-content path (377-394) already surfaces `reasoning_content` length +
  `finish_reason:"length"` as a diagnostic and returns `RT_E_LLM_REJECTED`. Confirms 155_structural §4 + 155_web Q4.
- **But there is no recovery.** Transport retry covers only HTTP 429/500/503 + network errors (55, 181-215);
  an AbortError is never retried (197-201); and an empty-content `RT_E_LLM_REJECTED` is **non-transient for
  `synthWithBackoff`** (codegen.server.ts:783-785 retries only `RT_E_LLM_TIMEOUT`; 798 returns immediately otherwise).
  So the exact failure the keyed runs hit ("DeepSeek returned no text content", project.json logs quoted in
  fixes/154) strands the chunk after ONE network attempt with zero thinking-disabled/two-pass retry. The 156-E1 lane
  is in flight (157 §3); §3.A9 below gives the mechanism-level addition.
- Thinking-mode semantics that the fallback must respect (verified this pass against the DeepSeek API docs): without a
  `tools` parameter, `reasoning_content` from earlier turns "does not need to be passed back; even if passed to the
  API, it will be ignored and will not be concatenated into the context" [T3]; thinking mode ignores
  temperature/top_p/presence/frequency penalties [T3]; effort mapping low→low, medium→high, high→high, max→max [T3].

### 1.3 verify.server.ts — the only behavioral runner is model-authored, A7-unseeded, and narrower than I/O equality

- **`generateCases` (512-588) invents the oracle from the artifact it will test.** Prompt = "Write executable
  verification cases for the following source module" (534) + anti-vacuity grounding line (527-532, brief ≤800 chars +
  source ≤6000 chars) + explicit instruction NOT to test rejection paths ("the harness cannot catch thrown errors",
  539-541). One bounded repair retry for malformed JSON (560-576). Anti-vacuity = `oracleBriefGrounded` (487-510):
  at least one brief noun or contract function name appears as an identifier in the cases — **identifier presence
  again**. The A7 rows never reach this prompt: `oracleToCaseSeeds`/`missingOracleCaseIds` exist in dod.ts (714-728)
  with a header comment describing the wiring (706-711) but **no production caller** (grep: dod.ts only, plus
  gates.test.ts). Confirms 155_structural §3's dead E-08 seam.
- **The harness can only evaluate one boolean expression per case, in a `with(exports)` scope.** `buildHarness`
  (335-362): source is compiled once via `new Function` into a CJS `__exports` object (347-349), then each case runs
  `with(exports){ with(__sandbox){ return (E); } }` (355). `sanitizeOracleExpression` (71-196) forbids `;`,
  assignments, arrows, backticks, `function`/`eval`/`require`/`process`/`console`… — a single pure expression per
  case. Consequences: (a) no `assert.deepEqual` against a JSON expectation — expected values must be inlined into a
  `===` expression the model writes; (b) **no rejection/throws assertions** (by prompt rule, 539-541, and by harness
  shape — a throw is caught and reported fail, but the prompt forbids even writing the case); (c) no cross-call
  workflow or state assertion (each expression is one call); (d) `runCases` pass logic is strict and honest —
  exact-id anti-forgery + compile-fail + forged-line detection (422-447), zero cases ⇒ fail (375-377). So the
  machinery is a good *fast steering loop*, but it cannot be the acceptance suite of §2/§3.
- **`verifyAndFixServer` (590-683)**: bounded fail→fix loop ≤5 iterations (595); the repair prompt receives failing
  case text + brief ≤600 + source ≤6000 (652-663) on the **flash tier** (662) and must return a full corrected source;
  pass/fail evidence carries counts; a lesson row is minted per outcome (609, 628, 644, 681). Note the repair prompt
  tells the model what to fix but **not which contract signatures must survive** (`signatureNames` is only used for
  generation grounding, 599) — a repair can silently drop an export; codegen re-validates shape afterward
  (codegen.server.ts:1307-1316) and refuses, but the model never sees that list during repair.

### 1.4 compile-check.server.ts + node-runner.server.ts — real execution exists; its green is stub-truth

- `runNodeBounded` (node-runner.server.ts:115-311) is a genuinely bounded local runner: scratch cwd, scrubbed env,
  maxBuffer 1MB, wall-clock kill with tree-kill + grace timers, honest timeout/signal/exit classification — never a
  fabricated pass. It is "bounded, NOT a security sandbox" (sandbox.ts:88-90) — fine for the in-loop runner, and the
  right host for a fixture spec.
- `treeRun` (compile-check.server.ts:604-627) = per-file parse (`compileCheckDir`, 113-202) + every `tests/*.spec|test`
  file executed as the REAL `node --test` in a bounded child with TAP summary parsing (336-362, 444-491, 614-616) + one
  kind-entry smoke (`resolveEntry` 523-567: **a root index.html ⇒ "UI shell — not executable headless" skip, 527-529**,
  even when `src/generated.ts` exists and is importable; headless kinds resolve package.json main → job-* module →
  generatedSource). `ok` allows the entry skip (623-625). The property-ledger run's mint evidence — "compile 12/12 · 1
  spec file(s) pass · 10 assertion(s) · entry webapp skip" — decomposes to 3 CheckpointStore round-trips + 1 ENDPOINTS
  table + 6 stub-reject/pin rows (155_structural §3/§6, verified against scaffold.ts:986-1328 emit branches this pass).
- **The mint gate therefore certifies whatever spec the scaffold emitted.** `treeRunTestedEvidence` (codegen.server.ts:1595-1610)
  counts any spec file pass + assertions — it cannot distinguish stub-truth from behavioral assertions. Once a brief-fixture
  spec exists in `tests/`, treeRun executes it for free; the missing piece is entirely upstream (fixtures + emitter + gate).

### 1.5 sandbox.ts — the floor is a no-op bookkeeper; identifier probes are the only "coverage"

## 2. What the slice proves about the P0-1 keystone (design constraints any addition must respect)

1. **The entry is importable headless for every kind** (assembleTreeEntry + scaffold assembly, §1.1) — the fixture spec
   needs no DOM, no vite build, and webapp trees can finally be executed at the data layer. P0-2(a)'s "webapp skip" can be
   closed *inside* the spec runner rather than by importing UI shells.
2. **A JSON fixture file + `node --test` spec is the smallest honest oracle** — treeRun already executes any spec under
   `tests/` and mints on its assertions; emitting a fixture spec rewires the mint evidence from stub-truth to behavior
   with no new executor.
3. **The E-08 seam (dod.ts:714-728) is the intended pinning mechanism** — prose-seed + reject-on-missing-id. It must be
   wired for the transitional LLM-case path, but prose rows are too weak to be the acceptance set; the fixture model (§3.A1)
   supersedes them (155_web R1: frozen, producer-independent oracle).
4. **The verify-server boolean harness is a steering signal, not an acceptance suite** (§1.3) — an acceptance suite needs
   `deepEqual` on JSON expectations and `throws` on rejection fixtures, which the harness cannot express and its prompt
   forbids (539-541). Use fixtures for acceptance; keep the harness only where its speed helps the repair loop (155_web R4).
5. **Empty-content refusal is a recoverable, documented provider behavior, currently treated as terminal** (§1.2) — the
   fallback is a provider-call ladder, not a codegen redesign (155_web Q4: raise budget → disable thinking → two-pass → floor).
6. **No-green-without-behavioral-pass must be enforced at the journey return** (§1.6) — converging on a red gate is the
   exact self-referential leak 155 names, and P0-1's fixture green only matters if the journey requires it.

## 3. Ranked, cited PLAN ADDITIONS (advance P0-1; A-numbers stable for cross-reference)

### P0 additions — the keystone itself

**A1 — Fixture-case data model + deterministic drafter, frozen BEFORE synthesis.**
New `Project.briefFixtures` record + pure types: `FixtureCase { id, reqId (req-N | corpus-capability id | orc-id),
target (typeSignature function NAME — known pre-synthesis, ≠ post-hoc reqTrace), input (JSON), expect (JSON | {throws:
{messagePattern}} | {property: <invariant name>}), note? }`. Drafter `draftBriefFixtures(brief, spec, oracle, corpus)`
(reuse `expandBrief`'s flash-tier call + bounded retry pattern, codegen.server.ts:756-768; and the E-08 seed renderer,
dod.ts:714-719, as input lines): LLM drafts candidate cases per requirement/capability/A7 row; a **deterministic
machine shape-gate** (no LLM) then reviews: target ∈ signatureFunctionNames(spec.typeSignatures); input/expect
JSON-serializable with ≥1 concrete literal (a case with zero literals — "returns something ok" — is rejected as
vacuous); rejection rows carry a messagePattern; property rows reference the approved invariant list only. Draft + red
cards out; human approves (A2). Model the data on the corpus example already in 157 §4 P0-1
(`createProperty({address,owner}) ⇒ {id, history:[]}`, `addWorkOrderHours(woId, 3) ⇒ jobCost + payroll accrual`).
*Why:* every benchmark defines correctness as executing the artifact against an oracle the producer never wrote
(HumanEval unit tests; SWE-bench "unseen tests … extracted from the original PR", FAIL_TO_PASS) — and drafting
executable examples from prose is precisely the machine-usable half of example-driven specs ("an example is also a
test … your examples are an executable specification" [S15 in 155]; "acceptance criteria should be executable"
[S17 in 155]; structured role outputs + SOPs that "verify intermediate results and reduce errors" [T1]). A machine can
draft; it cannot certify intent — hence A2.
*Seams:* new pure module beside verify.server.ts; `Project` type (types.ts) + project.json; drafter call in the
liveP6Synthesis step-1 area (codegen.server.ts:1087-1141) so fixtures are frozen before chunking.

**A2 — The one human gate: approve the drafted fixture set (answers the red cards) — placed before the green loop.**
Mirror the existing human-only HITL precedent (codegen.server.ts:1080-1085: `forceHuman` P6 park is never
machine-cleared) and the `lesson accept`-style approval verbs: P6 parks in `awaiting_hitl` at the fixtures stage;
approval writes `Project.briefFixtures` (source:"human-approved", briefHash pinned, approve timestamp/actor) and only
then may synthesis + run-to-green proceed. The approval artifact ships the red-card question list (Example Mapping:
unanswerable questions are first-class red cards [S16 in 155]) and sparse-example risk flags. **No approval ⇒ the
run's verdict class is "self-tested draft", never "functional"** (155_web R2: "acceptance review … BEFORE the green
loop"; the honest boundary — 38.3% underspecified / 61.1% unfair until humans repaired them on SWE-bench Verified
[S28 in 155]). This is the exact "human approve gate" 157 §4 P0-1 step (b), made concrete with a record + a verb + a
park state.

**A3 — Scaffold emits `tests/fixtures.brief.json` + `tests/brief.spec.ts`, the behavioral runner that imports the tree entry and asserts I/O.**
Extend `emitOracleSpec`'s tree section (scaffold.ts:986-1104) or add a sibling emitter for tree+fixture projects:
`tests/brief.spec.ts` does `import * as treeModule from <entry>` (reuse the existing treeEntryOk import machinery,
scaffold.ts:999-1000, 1068-1070) + `import fixtures from "./fixtures.brief.json"`; per case: resolve
`treeModule[case.target]`, run `case.input` (spread or single arg — store the arg shape in the case so the runner is
deterministic), and `assert.deepEqual(actual, case.expect)` — or `assert.throws(fn, case.expect.throws.messagePattern)`
for rejection rows (the orc-c-* constraint rows "403 or 422; no side effect; diagnostic JSON", algorithms.ts:771-778,
become expressible, which the boolean harness cannot do — §1.3). Fixture file carries a pinned content hash asserted by
the spec (byte-parity pin precedent: scaffold.ts:1010-1014) so a repair stage can never edit the oracle in place.
Facts that make this cheap: treeRun already executes every spec under `tests/` (compile-check.server.ts:614-616) with
real `node --test` (336-362); the scaffold's emitted package.json `test` scripts must add the new spec file
(scaffold.ts:474-493 — note bare `node --test` auto-discovers `**/*.test.{cts,mts,ts}` but **not** `*.spec.*` (Node's default `--test` patterns are `**/*.test.*`, `**/*-test.*`, `**/*_test.*`, `**/test-*`, `**/test.*`, `test/**` — plus the strip-types `.ts` variants [T7]), so list files explicitly or rename to `tests/brief.test.ts`); entry imports resolve because the
runner spawns `node --test <abs spec>` and Node resolves spec-relative imports from the file (no node_modules needed —
generated code is import-free by the forbidden-primitive contract — HARD `import`/`eval`/`Function` never repaired, codegen.server.ts:133-155 — and the spec only
imports the entry + node:test + node:assert). Assertions from this spec flow directly into
`treeRunTestedEvidence`/`mintTreeRunTested` (codegen.server.ts:1595-1652) — **the mint evidence rewires from
stub-truth to behavioral counts with no new executor**, and for webapp-kind trees the data layer finally executes
(P0-2(a) closed at the spec level; the index.html entry smoke stays an honest DOM-shell skip, compile-check.server.ts:527-529).
*Why this shape:* "run the artifact against executable tests applied by an external harness" is the operational
definition of functional correctness in every benchmark (HumanEval [S1 in 155]; SWE-bench harness-owned `test_patch`
[S2 in 155]); sandboxed, reproducible execution is the platform property (OpenHands Docker runtime: "execution …
without risking the host system", consistency/reproducibility rationale [T6] — here bounded-runner execution inside
the emitted dir, node-runner.server.ts:115-311).
*Honest modeling constraint (state in the plan):* fixtures assert the **exported function layer** — pure returns plus
throws. Where the brief demands persistence/HTTP (property-ledger "200 + persisted entity"), the expectation must be
written over the returned record + determinism (same input ⇒ same output), because generated code has no storage/HTTP
surface headless; endpoint-level behavior is a later P2-1/vite-build stage (157 §4 P2-1). State this in the fixture
draft prompt so cases never demand an impossible surface (mirrors generateCases' "test ONLY behavior the brief
explicitly requires", verify.server.ts:543-544).

**A4 — Wire the dead E-08 seam: seed `generateCases` with the oracle/fixture rows and pin their ids.**
Two modes. (a) **Fixtures exist (keyed, approved):** the acceptance suite IS the fixture spec (A3); `generateCases`
keeps its role as in-loop steering only (155_web R4) and is additionally seeded so its self-authored cases must
reference fixture ids. (b) **No fixtures yet (advisory/keyless path):** implement the seam dod.ts:706-728 actually
describes — `verifyAndFixServer`/`generateCases` accept a `seeds: string` (rendered by `oracleToCaseSeeds`, dod.ts:714-719)
prepended to the generation prompt (verify.server.ts:533-553) and reject/retry while
`missingOracleCaseIds(returnedIds, oracle)` is non-empty (dod.ts:725-728) — no blind pass on dropped pinned rows.
Because verify.server.ts deliberately avoids importing dod/codegen (its own note at 458-460), pass the rendered seed
string + id list as parameters from the caller (codegen single-module path 1300 and the CLI verify verb,
headless.ts:2040 / verify.ts:42). *Why:* pinning ids and rejecting drops is the operational version of SWE-bench's
"unseen tests … FAIL_TO_PASS/PASS_TO_PASS" accounting [S2 in 155] — a red→green transition per pinned row, never a
count of tests present.

**A5 — Keep the oracle honest: freeze, provenance, overfit guard, hidden canary layer.**
(i) **Freeze:** `briefFixtures` is written once at A2 approval; the emitted spec asserts the fixture hash (A3);
synthesis/verify loops read it frozen; a repair stage may never rewrite it (SWE-bench: harness owns the tests
[S2 in 155]). (ii) **Provenance:** fixture + runner + mint evidence carry producer stamps (human-approved fixtures,
LLM module, deterministic floor) — C2PA-style nutrition label [S26 in 155]; a floor-produced tree is ineligible for
behavioral green (155_web R5; maker-score `synthesisSucceeded` gate extends to the journey outcome). (iii) **Overfit
guard:** auto-generated tests measurably overfit and refinement makes it worse — Claude-3.7 21.8%→25.5%, GPT-4o
33.0%→35.9% with refinement (arXiv 2511.16858 [S4 in 155]). Concrete guardrails: track per-fixture repair-iteration
counts; if code+self-authored-cases iterate jointly > k rounds (k=2), force re-approval of the fixture set; and
**never let the implementation stage add to the acceptance set** (it may generate scratch cases for its own debugging
only, 155_web R4). (iv) **Hidden canary layer:** the drafter (A1) also emits `property`-typed invariants over the
exports (e.g. "createProperty always returns history: [] for a fresh id"); the code never sees them; after the fixture
suite is green the runner executes the property set (property-based testing: human property, machine-generated cases
[QuickCheck S19 in 155]; JS-native instantiation: fast-check "property-based testing for JavaScript and TypeScript …
within any test runner" [T9]) — the deterministic-canary analogue of HVE's embedded detectable hacks [S8 in 155].
(v) **Claim language:** DEPLOY.md + scorecard cite "passes human-approved brief fixtures executed by the harness", or
"self-tested draft" — never "verified" on self-authored tests alone (155_web R2/R5).

### P0-2/P0-3 additions (depend on the fixture runner)

behavioral failure text, not shape text. *Why:* repair must be "grounded in observed behavior, not just what looked

verify by design" hole (1339-1341) without fabricating a pass: the self-run is a steering signal; the acceptance
verdict stays with the emitted fixture suite (A3) — never let the chunk loop grade itself (self-enhancement bias
[S10 in 155]).

**A8 — Aider-style contract map for cross-chunk and repair context.**
Replace/augment the raw earlier-files block in the chunk prompt (codegen.server.ts:406-423) with a distilled
**contract map**: per earlier file — path, exported names, and the type-signature lines it implemented, capped to a
token budget. Rationale: aider sends "a concise map of your whole git repository … the most important classes and
functions along with their types and call signatures" and prunes it with a graph ranking to fit a token budget
