## BOTTOM LINE (read first)

- **The Wild strip and the Wild toggle disagree with the store about what "paused" is, twice over.** The chip's *tone* ternary reads the legacy spelling `wild.run?.paused` (console.tsx:756) while its *text* ternary reads the canonical `wild.run?.pause` (console.tsx:766); the store only ever writes `pause` (store.ts:1022, 1111, 1119; hydrateWildRun engine.ts:1955 normalizes to `pause`). Net: a paused wild run renders the word **PAUSED in a neutral chip** — the intended warn tint is dead code, the strip heading next to it turns warn (console.tsx:746 uses the shared `wildPaused()`), and a legacy `paused:true` payload would render **STOPPED** (165A-1).
- **The Wild toggle is a two-stage enable (mode flag + driver) whose async results are dropped on the floor** — the one place in the app that fire-and-forgets without a `.then`. Enabling on a sealed build silently leaves the toggle ON with an IDLE strip (165A-6); disabling mid-run doesn't stop an in-flight driver, which then re-lands a zombie PAUSED run with a fabricated "step cap reached" log (165A-5). Every other async affordance (resume 702-709, crew, verify) reads its result.
- **Failures travel the success channel at least twice.** A failed "Run module" lands in the green `rt-alert-ok` banner (165A-2); the P6-override store error quotes a checkbox label ("'I reviewed the failure'", store.ts:1474) that does not exist in the UI (console.tsx:2730) and is only reachable via the keyboard `a` shortcut, which bypasses the disabled Approve button (165A-3).
- **State-copy that misstates what just happened**: the strip blames a page reload for an in-session manual Stop (165A-4); the Deepen button announces "live research running" *after* the awaited action has finished (165A-9); "saved HH:MM" stamps page-open time, not a persist (165A-10).
- **Missing loading states**: "Run module (bounded)" — the only OS-process-spawning button — has no busy latch, no spinner, no re-entry guard (165A-8). **Dead affordances**: Ctrl+Shift+C "Copy agent packet" is a Chrome/Edge DevTools-reserved chord (165A-7). **Label vs action**: "Archive" performs a permanent, unrecoverable delete (165A-11).

## Findings

### 165A-1 — Paused wild run renders a neutral "PAUSED" chip; the warn tint is dead code and legacy payloads read "STOPPED"
- **BUG**: console.tsx:756 (chip tone ternary) tests `wild.run?.paused === true` (legacy spelling); console.tsx:766 (chip text ternary) tests `wild.run?.pause === true` (canonical spelling). The store writes **only** `pause` (store.ts:1022 startWildRun, 1111 stopWildRun, 1119 toggleWildPause; hydrateWildRun engine.ts:1955 re-emits `pause`). The type comment (console.tsx:241-243) says both spellings must be honored.
- **WHY it fails**: the two ternaries split the aliases instead of using the shared `wildPaused()` helper (console.tsx:313-315). For a canonical paused run (`pause:true`): text branch hits "PAUSED" but the tone branch falls through to the neutral `border-border text-muted` style — while the strip heading one row above (console.tsx:746) *does* use `wildPaused()` and turns warn. For a legacy `paused:true` payload: `running` computes false (wildPaused true), text branch misses `pause` and falls to `active === true` → **"STOPPED"** — a paused run labelled stopped.
- **FIX**: use `wildPaused(wild.run)` in both ternaries. console.tsx:756 → `: wildPaused(wild.run) ? "border-warn/40 bg-warn/10 text-warn"`; console.tsx:766 → `) : wildPaused(wild.run) ? (`. Delete the now-unreachable `active === true → STOPPED` middle arm (the `wild.run !== null` arm already covers stopped runs).
- **TEST**: unit-test the branch logic is hard without component tests; manual/DOM: start a wild run, press Pause → chip must show PAUSED with warn border/bg (assert class `border-warn/40`); craft a persisted payload with `wildRun:{active:true,paused:true}` (legacy alias only) → hydration must render PAUSED, never STOPPED.

### 165A-2 — "Module run failed" is delivered through the green success banner
- **BUG**: onRunModule (console.tsx:1354-1368) sends the failure copy `"Module run failed — see the "Real module run" artifact for details."` through `setNotice` (1366), and notices render with the success styling `rt-alert-ok` (console.tsx:2064-2068, `<p role="status" aria-live="polite" className="rt-alert rt-alert-ok">`).
- **WHY it fails**: store.runModuleReal returns `{ok:true, result:r}` whenever the bounded run *executed* — even when the module exited non-zero (`r.ok === false`); the store's ok flag only reports dispatch success (store.ts:1355 `return { ok: true, result: r }`). So the console's only failure signal is prose, and it is routed to the same banner used for "Imported…", "Crew run complete…" successes. A red-failure is green-rendered.
- **FIX**: split by outcome. In onRunModule: `if (r && r.ok) setNotice(...); else if (r) setError("Module run failed — see the "Real module run" artifact for details.");` (the `res.ok === false` branch already uses setError, 1358-1360). Optionally add `role="alert"` semantics by reusing the existing error `<p role="alert">` (2059-2063).
- **TEST**: generate a module that exits non-zero, click Run module (bounded) → assert an `.rt-alert-err` (role=alert) element appears with the failure text and no `.rt-alert-ok` appears; exit-0 path still shows the green "Module ran: exit 0 …" notice.

### 165A-3 — P6-override error quotes a checkbox label that does not exist in the UI; the `a` shortcut is the only path that hits it
- **BUG**: store.ts:1474 returns `"Failing sandbox output requires explicit override — tick 'I reviewed the failure'."` — but the actual checkbox reads **"I reviewed the failing sandbox output and approve anyway."** (console.tsx:2730). No string "'I reviewed the failure'" exists anywhere on screen.
- **WHY it fails**: the dock's Approve button is disabled without the override (console.tsx:2737 `disabled={needsOverride && !forceOverride}`), so the store guard is normally unreachable — but the global `a`/`A` approve shortcut (console.tsx:1228-1232) calls `onApprove()` → `approve(id,{force:false})` with no awareness of `needsOverride`, hitting the store guard. The operator gets an error telling them to tick a checkbox whose text they cannot find.
- **FIX**: (a) align the copy — store.ts:1474 → `"Failing sandbox output requires explicit override — tick "I reviewed the failing sandbox output and approve anyway" below."` (or reference "the override checkbox"); (b) better, teach the shortcut the gate: the keydown handler (1228) should no-op with the same hint when `needsOverride` is unmet — simplest is to leave approve to the store but make the error text point at the actual control.
- **TEST**: with a forceHuman P6 gate and `lastTest.ok === false`, press `a` → the red alert text names the checkbox label verbatim (or the shortcut refuses); with the override ticked, `a` approves.

### 165A-4 — After an in-session Stop, the strip blames a page reload that never happened
- **BUG**: console.tsx:820-825 — any `wild.run !== null && active !== true && !paused` state renders: *"Run stopped after reload — the wild driver is a session artifact and cannot resume across page loads…"* This includes an intentional **manual Stop in the current session**: onStop (727-737) calls `stopWildRun` (store.ts:1107-1113, `active:false, stoppedAt:Date.now()`) and the strip immediately shows the reload paragraph.
- **WHY it fails**: the reload-forced stop (hydrateWildRun engine.ts:1960-1963) and the manual stop produce byte-identical store states (`active:false, pause:false, stoppedAt`); the strip never distinguishes them, and `stoppedAt` (stamped by both) is not inspected.
- **FIX**: track the stop origin in the component — `const [stoppedByUser, setStoppedByUser] = useState(false);` set `true` in onStop (731) (and reset when a new run starts / pause toggles); gate the reload paragraph on `!stoppedByUser`. Optionally have stopWildRun persist a stop-reason log (`wild.stop` event already exists in the feed) and read the newest entry instead of a local flag.
- **TEST**: start a wild run, press Stop → assert the reload paragraph is absent (or replaced by the "Wild run stopped." note at 731); reload the page on a stopped run → paragraph still appears (genuine reload case preserved).

### 165A-5 — Toggling Wild OFF mid-run doesn't stop an in-flight driver and leaves a zombie PAUSED run + a false "step cap" log
- **BUG**: the OFF path of WildToggle.flip (console.tsx:426) calls only `setWildMode(id,false)`, which nulls `wildRun` (store.ts:957) — it never calls `stopWildRun`. Meanwhile `startWildRun` was fire-and-forget (console.tsx:433), so a driver may still be mid-step (e.g., awaiting an LLM). The driver loop (store.ts:1067-1090) steps on its **local** `cur` and only re-reads the store via commitWild; the commit's `rebaseUserFields` deliberately does **not** let live `wildRun` win (store.ts:227-231 — engine-owned), so the driver's next commit re-lands a run object. When the mode-off noop finally breaks the loop (`!res.ran`), the tail **unconditionally parks with the cap message**: `wildPause(cur, …, "Wild loop step cap (20) reached — run parked.")` (store.ts:1088-1089), even though the cause was mode-off. End state: `wildMode:false` **with** `wildRun:{active:true,pause:true}` — the strip shows a PAUSED run and a Resume control (console.tsx:782-807, `active===true`), but Resume calls startWildRun which refuses with "Wild Mode is not enabled for this project." (store.ts:981-988).
- **WHY it fails**: two uncoordinated writers (sync setWildMode vs async driver commits); the off-toggle hides all strip controls the moment it nulls wildRun while the driver may still commit one more full phase advance behind it; and the loop's tail conflates "loop ended without progress" with "cap reached".
- **FIX**: (a) in flip(), when disabling and a live run is active, call `stopWildRun(projectId)` before/with `setWildMode(id,false)` and gate on the live state (read `useRapid.getState()` like the pause path does, 685-688); (b) in the store driver loop, distinguish stop causes: after the `break` on `!res.ran`, check `cur.wildMode !== true` → return `{ok:true, stoppedReason:"stopped"}` without the cap park; keep the cap park only for a genuine 20-step exhaustion.
- **TEST**: start a wild run on a keyed build (slow step), toggle Wild OFF mid-step → poll the store: `wildRun` must end `null` (or `active:false`), no `wild.cap` log entry, and no further `currentPhase` advance after the toggle's commit; no Resume control visible after toggle-off.

### 165A-6 — Enabling Wild Mode on a sealed build silently no-ops while the toggle stays ON
- **BUG**: startWildRun returns early for a complete project — `if (p.status === "complete") return { ok: true, ran: 0, stoppedReason: "complete" };` (store.ts:1006) — **before** creating a wildRun. WildToggle.flip (console.tsx:413-441) commits `setWildMode(id,true)` (426), fire-and-forgets startWildRun (433) and never inspects the result (the resume path 702-709 does inspect; flip does not). End state on a sealed build: wildMode ON, wildRun null, the strip (visible via `wild.enabled`, console.tsx:680) shows an **IDLE** chip with "No auto activity yet — wild mode acts silently until the next gate decision." (874) — there will never be another gate decision; the toggle is a permanent dead-on switch with no explanation.
- **WHY it fails**: the two-stage enable (mode flag commit then driver start) drops the driver's result; the honest note for this case exists in the store result but is discarded.
- **FIX**: give flip() the same result handling as the resume branch — `useRapid.getState().startWildRun(projectId).then((res) => { if (!res.ok) { useRapid.getState().setWildMode(projectId, false); setErr(res.error ?? "Wild run did not start."); } else if (res.ran === 0 && res.stoppedReason === "complete") { useRapid.getState().setWildMode(projectId, false); setErr("This build is already complete — there is nothing for wild mode to run."); } }, (e) => { useRapid.getState().setWildMode(projectId, false); setErr(...); })` — mirror the pause/resume `.then` shape already in the file.
- **TEST**: open a P12-complete project, click Wild → toggle must revert to OFF and the error text appear; assert wildMode stays false and no IDLE-forever strip.

### 165A-7 — "Ctrl+Shift+C — Copy agent packet" is a Chrome/Edge DevTools-reserved chord
- **BUG**: the Shortcuts dialog advertises `Ctrl+Shift+C → Copy agent packet` (console.tsx:977) and the keydown handler implements it (console.tsx:1205-1212). In Chrome and Edge — the primary target browsers for this Windows-served app — Ctrl+Shift+C is reserved for DevTools "Inspect element": the browser consumes the chord (opening the element picker) before/regardless of the page handler, so the documented shortcut either never fires or fires *and* pops the DevTools picker.
- **WHY it fails**: reserved browser chrome is being used as an application chord; no unit test can catch it (browser-level), which is exactly why it survived.
- **FIX**: remap to a non-reserved chord — e.g. `Ctrl+Shift+D` (currently unused; no conflicts with the other registered chords Ctrl+G / Ctrl+Shift+Enter / Ctrl+Enter) or `Alt+Shift+C` — and update both the handler matcher (1205) and the SHORTCUTS list (977).
- **TEST**: manual in Chrome/Edge: focus the run screen (not typing), press the new chord → clipboard contains the packet and no DevTools picker opens; the old chord must no longer be advertised.

### 165A-8 — "Run module (bounded)" has no loading state, no disabled guard, and no re-entry latch
- **BUG**: onRunModule (console.tsx:1354-1368) never touches `busyRef` or `busyAction`; the button (console.tsx:1820-1829) has no `disabled` while running and no spinner/label swap. `runModuleReal` (store.ts:1310+) spawns a **real bounded OS process** (node runner) that takes seconds.
- **WHY it fails**: the module-run seam predates the busyAction/busyRef latch (UI-4) that run()/runUntil()/onSpawnCrew all use. Consequences: no visual feedback during the longest non-LLM operation (appears hung); every other run control stays enabled mid-module; repeated clicks queue a second module run through `serialized()` (store.ts:182-199) instead of being ignored.
- **FIX**: (a) extend the busyAction union (console.tsx:1144) with `"module"`; (b) in onRunModule set `busyRef.current = true; setBusyAction("module")` in a try/finally exactly like run() (1301-1314); (c) on the button render a Loader2 + "Running module…" while `busyAction === "module"` and keep `disabled={busyAction !== null}`.
- **TEST**: click Run module twice rapidly on a slow module → exactly one "Real module run" artifact/log lands; button shows spinner + "Running module…" and is disabled until the run resolves; Execute/Run-to-next-gate are disabled concurrently (they already key off `busyAction !== null`).

### 165A-9 — Deepen outcome copy announces "live research running" after the work has already finished
- **BUG**: runDeepen (console.tsx:4974-4987) awaits the store deepen action and then sets `"live research running — the gate re-records when it completes"` (4981). The store action resolves only *after* engine.deepenResearch has appended corpus rows/artifacts and re-recorded the phase gate (store.ts:841-852 → engine.ts:2990-2993 recordGateInto). With no LLM/research backend the engine still resolves (unchanged project, `liveUnavailable` stamped) and the store returns `ok:true` — so the message claims an in-flight process that has already finished, and claims it even when nothing was fetched.
- **WHY it fails**: the copy describes the click-time expectation rather than the settled result; `{ok:true}` from the store does not distinguish "research landed" from "nothing to fetch".
- **FIX**: report the settled state. The component has the project in scope — after `await`, re-read the phase record's gate (or compare artifact count) and branch: gate now passes → `"Live research recorded — the gate verdict above now passes."`; still failed/unmet → `"Live research ran but the gate is still unmet (no findings or no research backend) — see the research rows."`; `!res.ok` → the existing error branch. If a one-line fix is preferred: `"Live research complete — the phase gate was re-recorded; check the verdict above."`
- **TEST**: keyless project with a recorded FAIL gate carrying p7-research unmet, click Run live research (P7) → the outcome line must not contain "running"; a keyed project with TAVILY configured → gate row updates to PASS when findings land.

### 165A-10 — "saved HH:MM" header chip stamps page-open time, not a real persistence
- **BUG**: the last-saved effect (console.tsx:1174-1176) fires on mount — `if (project) setLastSaved(Date.now())` — so the chip (1663-1670, tooltip "Saved to this browser only") shows the *page-open minute* for a build whose last real write may be a day old; it then re-stamps on every project-object change, including changes made by the wild driver or async runs that the operator did not save.
- **WHY it fails**: the indicator is derived from "project reference changed" rather than from an actual persist event; zustand persist writes happen on store `set()` — the mount render is not one.
- **FIX**: skip the first run of the effect (a `useRef` didMount guard) so the chip only appears after a genuine in-session change; optionally gate on an explicit subscription to the persist callback instead of `[project]`.
- **TEST**: persist a build, reload the page → no "saved" chip (or the prior session's stamp); edit notes / run a phase → chip appears/stamps with the current time.

### 165A-11 — "Archive" performs a permanent, unrecoverable delete and the header button carries no title or icon
- **BUG**: the header action labeled **Archive** (console.tsx:1924-1930, text-only, no `title`, no icon) calls `archiveAndHome` → `remove(projectId)` (1585-1588), and store.remove **permanently filters the project out** — `projects: s.projects.filter((p) => p.id !== id)` (store.ts:1565-1569). The confirmation dialog mirrors the label ("Archive {name}?", confirm button "Archive", console.tsx:2030-2053) with the only honest line buried in the description ("…are deleted from this browser", 2034).
- **WHY it fails**: "Archive" conventionally implies reversible retention; the only affordance in the whole surface that deletes a build irreversibly is named like a non-destructive action, and — unlike every sibling action in the row (Copy/Download/Export all carry icons and several carry `title=`) — it gives hover users no hint that it is destructive.
- **FIX**: (a) add an icon + `title="Delete this build permanently — this cannot be undone (no archive or trash)"` to the header button; (b) relabel the dialog title/confirm to "Delete {name}?" / "Delete build" (keeping the description's explicit "deleted from this browser" wording); (c) optional consistency: the HomeScreen empty/return copy and the not-found screen (1279 "This build doesn't exist or was archived.") still say "archived" — align to "deleted".
- **TEST**: hover the header button → tooltip states permanent deletion; click through the dialog → project is gone from the store and the Home list, and no second copy exists anywhere (proves it is a delete, not an archive); visual/a11y: button has an accessible name that includes "Delete".
