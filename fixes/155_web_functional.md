## BOTTOM LINE (read this first)

- **Every credible code benchmark defines functional correctness as: run the artifact against executable tests the model never wrote and never saw, applied by an external harness.** HumanEval: "evaluate the correctness of code samples automatically through unit tests" over "164 original programming problems with unit tests" [S1]. SWE-bench: the model gets issue + repo only; the `test_patch` is "unseen tests … extracted from the original PR" (written by the human maintainer who merged the fix); "a task is considered solved if all tests across FAIL_TO_PASS and PASS_TO_PASS pass", judged by the harness, not the model [S2][S11]. SWE-bench-Live, Terminal-Bench 2.0 and RepoBench follow the same shape [S3][S5][S6]. **The oracle is external, executable, and withheld.**
- **Self-authored tests are a known overfitting liability, now measured, not suspected.** arXiv 2511.16858 ("Investigating Test Overfitting on SWE-bench", Nov 2025): RQ1 "Can LLMs overfit on white-box tests? (Yes, they can and do.)"; refining code against auto-generated tests *raises* the overfitting rate (Claude-3.7-Sonnet 21.8%→25.5%, GPT-4o 33.0%→35.9%); CodeT/Agentless/S*/CodeMonkeys "generate both candidate codes and candidate tests … might suffer from test overfitting but do not study it" [S4].
- **Top tools verify against the USER's oracle, not their own:** Claude Code's official best practice is "give Claude a way to verify its work … a check it can run: tests, a build, a screenshot" and, for a function, *you* supply the acceptance examples in the prompt ("example test cases: user@example.com is true, invalid is false … run the tests after implementing") [S14]. Codex runs "in its own cloud sandbox environment, preloaded with your repository", is told via AGENTS.md "which commands to run for testing", "can iteratively run tests until it receives a passing result", and ships "verifiable evidence … citations of terminal logs and test outputs" for a human who reviews the PR [S12][S13]. OpenHands is a sandboxed-execution platform whose own evaluation runs the official SWE-bench harness [S7]. **Nobody's production loop treats "my tests pass on my code" as the product verdict.**
- **Turning a brief into executable acceptance tests WITHOUT any human is not supported by the evidence.** The oracle needs intent, and intent is underspecified in real briefs: OpenAI's human annotation of SWE-bench flagged **38.3% of instances for underspecified problem statements and 61.1% for unit tests that may unfairly mark valid solutions as incorrect — 68.3% filtered out overall** [S28]. Example-mapping's method exists precisely because a story needs "a conversation to clarify and confirm the acceptance criteria", with unanswered questions captured as red cards [S16]. BDD/Gherkin/QuickCheck all assume a human states the rules/examples/properties; the machine then executes and searches [S15][S17][S19]. **The honest minimal human input for RapidTool is one review-and-approve of the machine-drafted acceptance suite (plus answers to flagged questions) BEFORE the autonomous run-to-green loop may claim "functional".**
- **Honesty plumbing for the fallback path is a solved engineering pattern, not a research gap:** degrade loudly and visibly (circuit breaker trips → errors, not plausible answers, plus a monitor alert [S27]); stamp provenance on every artifact (C2PA's "nutrition label for digital content" [S26]); never let the producer grade itself (LLM-as-judge self-enhancement: GPT-4 favors itself +10%, Claude-v1 +25% [S10]); and keep rerunnable evidence (SWE-bench run-id logs [S11], Codex log/test citations [S12]). **A deterministic floor run that satisfies brief-noun checks is a scaffold, not software: it may ship artifacts, but it can never be graded green (no-green-without-LLM gate), and its artifacts must carry a provenance stamp that says so.**

## Q1 — The oracle problem in synthesis: what functional correctness means in the benchmarks, and why self-authored tests fail it

### Q1.1 Functional correctness = execution against externally-authored tests, applied by a harness

- **HumanEval (Chen et al., OpenAI, 2021)** [S1]: "we focus on the task of generating standalone Python functions from docstrings, and evaluate the correctness of code samples automatically through unit tests … we create a dataset of 164 original programming problems with unit tests." pass@k is defined by *running* those unit tests over sampled completions; the docstring spec is human-written; the test set that scores is the benchmark's, not the model's. This is the canonical definition of functional correctness the whole field inherited.
- **SWE-bench (Jimenez et al., ICLR 2024)** [S2]: task instances = real GitHub issue + repository. Field definitions from the paper's own dataset table (ar5iv full text): `test_patch` is a ".patch-format styled string containing **unseen tests** for checking if a task was solved, extracted from the original PR's code changes" — i.e., the oracle tests are the ones the human maintainer wrote when they fixed the issue. Evaluation: "a prediction .patch must be applied successfully and produce the same result…" and "a task is considered solved if all tests across FAIL_TO_PASS and PASS_TO_PASS pass." Two structural guarantees matter for RapidTool: (a) the tests are **held out** from the model's input entirely; (b) the **harness owns both patches** — a model patch that touched test files could not launder the verdict.
- **SWE-bench-Live (2025)** [S3]: 1,319 tasks from real GitHub issues created **since 2024** (post-training-cutoff → contamination-resistant), 93 repos, per-task Docker images for "reproducible execution"; "fresh, diverse, and executable benchmark grounded in live repository activity". Same oracle model (tests from the real merged PR), with the added property that the issues are newer than the models' training data.
- **Terminal-Bench 2.0 (Merrill et al.)** [S5]: 89 tasks "in computer terminal environments"; "Each task features a unique environment, **human-written solution, and comprehensive tests for verification**" — correctness = the task's own tests pass in the task's own environment (the harness repo's README even instructs running the "oracle" solution 5× to validate a sandbox before trusting scores [S5 README repo]).
- **RepoBench (Liu et al., 2023)** [S6]: repository-level benchmark (Python+Java) measuring retrieval/context/next-line tasks — included here for completeness as the "repository-level" strand, though its original tasks are not execution-graded; the execution-graded, long-context successor (RepoBench-X) is not on arXiv and was not verified this pass, so it is deliberately not cited.

**Operational definition distilled from all five:** *an artifact is functionally correct iff, executed in a real environment with real inputs, it satisfies a test/acceptance set that (1) is executable, (2) was authored independently of the artifact's producer (human maintainer, benchmark author, or — in a factory — a different, frozen stage), and (3) was not visible to the producer during generation.*

### Q1.2 The self-authored-test overfitting failure (the exact failure RapidTool must design against)

- **arXiv 2511.16858v3 — "Investigating Test Overfitting on SWE-bench" (Nov 2025)** [S4] is the first empirical study of test overfitting for LLM issue-resolution. Definitions from the paper text: "Test overfitting happens when an APR workflow generates code that passes white-box tests but fails held-out black-box tests… generated repaired code is too narrow to generalize to held-out black-box tests." (White-box = tests the pipeline itself auto-generates from the issue; black-box = the benchmark's real, hidden tests.)
- Findings (verbatim from ar5iv full text): **RQ1 "Can LLMs overfit on white-box tests? (Yes, they can and do.)"** RQ2: "How does improving code based on white-box tests affect test overfitting? (Overfitting goes up for affected instances.)" RQ3: revealing black-box tests would not vastly raise apparent resolution — i.e., the white-box signal is *not* a good proxy for the real one. Measured overfitting rates (Table 1): Claude-3.7-Sonnet 21.8% without refinement → **25.5% with refinement**; GPT-4o 33.0% → **35.9% with refinement**. The paper also names the systems that co-generate code and tests — CodeT, Agentless, S*, CodeMonkeys — and notes they "might suffer from test overfitting but do not study it" [S4]. (The prior art it builds on: Stroebl et al. showed loop-until-white-box-pass on HumanEval/MBPP overfits — cited inside [S4].)
- **The failure mode in one sentence:** a pipeline that lets the same model write the tests and the code, then iterate code against those tests until green, produces code that is *narrow* — it satisfies the self-authored checks and misses the task. That is precisely "green self-tests" vs "functional software".
- **Counterpoint that actually confirms the rule — DryRUN (arXiv 2604.21598)** [S9]: multi-agent code generation *without* human-authored public tests, using self-synthesized inputs + simulated execution, reaches parity with a test-dependent baseline **as measured on LiveCodeBench v6 hidden tests**. Two takeaways: (1) self-generated tests can be a useful *in-loop steering signal* for well-specified algorithmic tasks; (2) the paper's own success criterion is still the external hidden suite, and it explicitly documents the "overconfidence gap" — frameworks that lean on public/self tests "overfit to basic examples and underperform on hidden test suites". **Self-tests refine; only external tests certify.**
- **Why even good-looking oracles need human repair:** SWE-bench Verified (OpenAI + Princeton) [S28] — professional developers screened every sample: "38.3% of samples were flagged for underspecified problem statements, and 61.1% were flagged for unit tests that may unfairly mark valid solutions as incorrect. Overall, our annotation process resulted in 68.3% of SWE-bench samples being filtered out." Also structural: "the agent … does not have visibility into the tests that it needs to pass." **The benchmark's own oracle (tests extracted from real PRs) was unfair or ambiguous in ~2/3 of cases until humans repaired it. A machine-only factory has no one to do that repair.**

## Q2 — How the top tools verify "does what was asked": they source the oracle from the user, not from themselves

### Q2.1 Claude Code (Anthropic) — the user supplies the check; the agent runs it; the human re-runs it

Anthropic's official best-practices doc (docs.anthropic.com/en/docs/claude-code/best-practices — served content identical to anthropic.com/engineering/claude-code-best-practices) [S14]:

- "**Give Claude a way to verify its work.** Give Claude a check it can run: tests, a build, a screenshot to compare. It's the difference between a session you watch and one you walk away from. Claude stops when the work looks done. **Without a check it can run, 'looks done' is the only signal available, and you become the verification loop.**"
- "The check is anything that returns a signal Claude can read in the conversation: a test suite, a build exit code, a linter, a script that diffs output against a fixture, or a browser screenshot compared against a design."
- Verification criteria are **example-driven specs authored by the human in the prompt**: *Before:* "implement a function that validates email addresses" → *After:* "write a validateEmail function. **example test cases: user@example.com is true, invalid is false, user@.com is false. run the tests after implementing**".
- And the final acceptance is human: "**Run /verify yourself after Claude's check passes** to confirm the change against the running app."
- The /fix-issue style workflow in the same doc orders the loop as: understand issue → implement → "**Write and run tests to verify the fix**" → lint/type check → PR. Oracle = issue text + repo's own checks; tests written by the agent are a *self-check*, the issue + human review is the *verdict*.

### Q2.2 Codex (OpenAI) — sandboxed execution of the repo's own tests, evidence citations, human PR gate

OpenAI's Introducing-Codex engineering post (fetched via reader; direct openai.com fetches 403) [S12]:

- "each task runs in its own cloud sandbox environment, preloaded with your repository"; "Codex can read and edit files, as well as **run commands including test harnesses, linters, and type checkers**"; trained "to … adhere precisely to instructions, and **can iteratively run tests until it receives a passing result**".
- The test commands are user-sourced: "Codex can be guided by **AGENTS.md** files … where you can inform Codex how to navigate your codebase, **which commands to run for testing**, and how best to adhere to your project's standard practices."
- Evidence + human gate: "Codex provides **verifiable evidence of its actions through citations of terminal logs and test outputs**, allowing you to trace each step … You can then **review the results, request further revisions, open a GitHub pull request**, or directly integrate."
- The agent-loop engineering post [S13] describes the mechanism underneath: the shell tool is sandboxed ("the sandbox that applies only to the Codex-provided `shell` tool"), i.e., execution is real and isolated — "designed to produce high-quality, reliable software". Codex's own internal test policy (repo skill file [S29]) even mandates: "Features that change the agent logic MUST add an integration test."

### Q2.3 OpenHands — a platform whose evaluation is the official harness

OpenHands (f.k.a. OpenDevin) paper [S7]: "a platform for the development of powerful and flexible AI agents that interact with the world … by writing code, interacting with a command line … safe interaction with **sandboxed environments for code execution** … and **incorporation of evaluation benchmarks**"; its own evaluation ran "15 challenging tasks, including software engineering (e.g., SWE-BENCH)" — i.e., when OpenHands wants to know whether an agent "did what was asked", it grades on the benchmark's held-out tests, not the agent's.

### Q2.4 The pattern

| Tool | Where the oracle comes from | Who runs it | Who issues the final verdict |
|---|---|---|---|
| Claude Code | User-supplied example criteria + repo tests/build/lint | The agent (loop closes on pass/fail) | Human `/verify` |
| Codex | User's repo + AGENTS.md test commands + task text | Agent in sandbox (logs cited) | Human PR review |
| OpenHands (eval) | Benchmark held-out tests | Harness in sandbox | Harness |
| SWE-bench family | test_patch from human-merged PR, withheld | Docker harness | Harness (human-validated instances) |

**No top tool's shipped-product verdict rests on tests the agent wrote for its own code.** Self-authored tests appear only as an in-loop signal inside a larger loop whose outer oracle is the user's criteria/tests and whose final acceptance is a human.

## Q3 — Executable acceptance criteria: what is machine-usable today, what still requires a human

### Q3.1 The practice is mature and explicitly executable

- **BDD origin (Dan North, 2006)** [S17]: "A story's behaviour is simply its acceptance criteria: if the system fulfils all the acceptance criteria, it's behaving correctly; if it doesn't, it isn't." Section title: "**Acceptance criteria should be executable**". The Given/When/Then template exists so criteria are "loose enough that it wouldn't feel artificial … but structured enough that we could break the story into its constituent fragments and **automate them**."
- **Gherkin/Cucumber (current reference)** [S15]: "Gherkin uses a set of special keywords to give structure and meaning to **executable specifications**." And: "In addition to being a specification and documentation, an example is also a test. **As a whole, your examples are an executable specification of the system.**" (Given = initial context, When = event, Then = expected outcome; each step binds to executable code.)
- **Specification by Example (Adzic, Jolt Award 2012)** [S18]: 50-project case-study research on teams that "design, develop, test and deliver the right software, without defects"; the workshop framing is literally "**Collaborative specifications and tests**" — collaborative because the examples encode business intent.
- **Property-based testing (QuickCheck, Claessen & Hughes 2000)** [S19]: "The programmer provides a **specification of the program, in the form of properties which functions should satisfy**, and QuickCheck then tests that the properties hold in a large number of randomly generated cases." The machine's contribution is exhaustive-ish *search*; the human's contribution is the *invariant*. (Modern tooling: Hypothesis [S20] is the Python instantiation of the same contract.)
- **Example-driven specs are already how benchmarks prompt** [S1]: HumanEval prompts embed human-written `>>>` examples in docstrings as the spec; the hidden tests are the score. So "give examples, run tests" is the field's oldest, most validated spec format — and it is exactly the shape Claude Code's docs recommend to users [S14].

### Q3.2 What is machine-usable today

1. **Drafting the executable suite from a natural-language brief** — Given/When/Then scenarios, concrete input→output examples, and property invariants are all *generatable* by an LLM from a brief; the formats (Gherkin, JSON example tables, property functions) are plain text with an execution binding [S15][S17][S19].
2. **Executing and iterating to green** — running the suite in a sandbox and looping code against failures is exactly what Claude Code's "check it can run" loop and Codex's "iteratively run tests until passing" do [S12][S14].
3. **Machine-checking internal consistency** — example tables can be type/arity-checked; properties can be falsified over generated inputs automatically [S19][S20].

### Q3.3 What still requires a human (the honest boundary)

- **Intent disambiguation.** Example Mapping exists because "before you pull a user story into development, it's crucial to **have a conversation to clarify and confirm the acceptance criteria**" — rules (blue cards), examples (green), and open **questions captured as red cards "that cannot be answered during the session"** [S16]. A machine can *draft* the cards; it cannot *answer* the red ones from the brief alone, because the answer is the requester's intent.
- **Oracle fairness.** Even tests written by human maintainers were "unfair" or the spec "underspecified" in a majority of SWE-bench instances until professional developers repaired them [S28]. A machine-generated acceptance suite has the same risk, with no human to catch it — unless one reviews it.
- **Checks ≠ intent.** Reward hacking is "satisfying a task's checks while violating its intent", and "detection typically relies on human inspection or LLM judges, both of which can be unreliable" — the HVE/HVTB line of work exists precisely because check-passing and intent-satisfaction diverge in machine-detectable ways only when someone *engineers canaries into the environment* [S8].
- **Bottom line for a factory:** *"brief → executable acceptance tests" is machine-draftable but not machine-certifiable.* The machine-usable core (draft scenarios + examples + invariants, run them, iterate to green) is proven technology; the missing piece is one human pass that confirms "these examples capture what I asked for" and answers the red-card questions. That is the minimal human input, and it is small — but it is not zero.

## Q4 — Thinking-model empty content: cross-check of the three candidate fixes (companion: fixes/154_research_web.md Q1)

Cross-checked this pass against primary vendor docs only (issue-level ecosystem evidence was already collected in fixes/154_research_web.md Q1.1–Q1.6 and is not duplicated here). **Conclusion: the collision is vendor-documented on every major stack, and the field's fixes are exactly (a) raise/separate the output budget, (b) disable thinking for structured envelopes, (c) two-pass reason-then-answer — in that order of prevalence.**

- **DeepSeek — JSON Output mode** [S21]: official guide (verbatim): "When using the JSON Output feature, **the API may occasionally return empty content**. We are actively working on optimizing this issue. You can try modifying the prompt to mitigate such problems." Same page: "Set the `max_tokens` parameter reasonably to **prevent the JSON string from being truncated midway**." (The guide's sample code now targets `deepseek-v4-pro` — the same model family RapidTool calls.)
- **DeepSeek — API reference** [S22]: `max_tokens` is "the maximum number of tokens that can be generated in the chat completion" (one shared pool); "the message content may be partially cut off if `finish_reason="length"`"; `finish_reason` values include `length` and `insufficient_system_resource`; `reasoning_content` is defined as "The reasoning contents of the assistant message, **before the final answer**"; JSON mode footgun: you must include the word "json" or the model "may generate an unending stream of whitespace until the generation reaches the token limit" (looks "stuck"). So: **thinking + JSON-mode + a long prompt shares one budget; empty content with everything in `reasoning_content` is the documented signature** (mechanisms A–D of fixes/154).
- **OpenAI — Reasoning guide** [S23] (fetched; docs now describe the gpt-5.x/gpt-6 era): "If the generated tokens reach the context window limit or the `max_output_tokens` value you've set, you'll receive a response with a status of `incomplete` … **This might occur before any visible output tokens are produced**, meaning you could incur costs for input and reasoning tokens without receiving a visible response. … **OpenAI recommends reserving at least 25,000 tokens for reasoning and outputs**." Fix (b) is first-class: `reasoning.effort`/`reasoning_effort` accepts **`none`** ("Latency-critical tasks that do not benefit from any reasoning…"), with gpt-5.5 guidance "trying low to begin with and then moving to none if required".
- **Qwen3 — official blog + docs** [S24][S25]: hybrid thinking is per-request controllable — "This flexibility allows users to **control how much 'thinking' the model performs based on the task at hand**. For example, harder problems can be tackled with extended reasoning, while easier ones can be answered directly without delay"; API docs show `enable_thinking: False` as the structured/tool path ("It is advised… `enable_thinking`: False # default to True"), and warn that with reasoning models, stopword-based ReAct templates are unsafe because "the model may output stopwords in the thought section" — i.e., thinking contaminates structured/tool output parsing.
- **Field fixes, with doc evidence:**
  - **(a) Raise / split the output budget** — OpenAI ≥25k reasoning+output buffer [S23]; DeepSeek `max_tokens` truncation note + `finish_reason:"length"` [S22][S21].
  - **(b) Disable thinking for structured envelopes** — DeepSeek per-request thinking/reasoning_effort toggles [S22]; OpenAI `effort: none` [S23]; Qwen `enable_thinking: false` [S24][S25]. This is the vendor-recommended configuration for JSON/tool outputs (DeepSeek's empty-content page is its JSON page).
  - **(c) Two-pass reason-then-answer** — directly expressible as *call 1 with thinking on → call 2 with thinking off, first response in context*, because every vendor now exposes the toggle per request [S22][S23][S24]; OpenAI's reasoning guide additionally instructs carrying reasoning items forward across function-call turns [S23].
- **Implication for RapidTool (confirms the 152–154 retry-ladder work):** the three fixes are complementary, not competing — attempt ladder: (1) thinking-high with generous budget → (2) same JSON envelope with `thinking:{type:"disabled"}`/`reasoning_effort:"low"` → (3) bounded floor; classify empty `content` only after checking `tool_calls`/`finish_reason`/`usage` and salvaging parseable JSON from `reasoning_content` (details and issue-level citations in fixes/154 Q1). All three levers are documented at the API level this pass [S21][S22][S23].

## Q5 — Deterministic-fallback honesty: how real systems stop a degraded path from masquerading as a real result

RapidTool's specific hazard (from fixes/154): if the thinking model returns empty content and the system degrades to a deterministic floor scaffolded from the brief's own nouns, M1..M9 identifier checks are satisfiable BY CONSTRUCTION and the scorecard reads green with zero LLM-produced content. Published mechanisms real systems use:

- **Provenance stamping on artifacts (C2PA)** [S26]: the Coalition for Content Provenance and Authenticity provides "an open technical standard for publishers, creators and consumers to **establish the origin and edits of digital content**… Content Credentials function like a **nutrition label for digital content**, giving a peek at the content's history." Transpose to a factory: every emitted artifact carries a machine-readable record of *which run/tool/model produced it* — floor vs LLM is a first-class provenance field, not an inference.
- **Circuit breakers that fail loud, not plausible** [S27]: Nygard's pattern (via Fowler): "Once the failures reach a certain threshold, the **circuit breaker trips, and all further calls … return with an error**, without the protected call being made at all. Usually you'll also want some kind of **monitor alert if the circuit breaker trips**," plus half-open trial calls to recover. The honesty property: a tripped system returns *errors*, never substitute successes; and the trip is *alerted and recorded*. RapidTool's floor must be wired as a tripped-breaker state (banner + audit stamp), not as an invisible "it worked".
- **No-green-without-producer gates in evaluation practice** [S2][S11]: SWE-bench structurally cannot be gamed by the artifact because the harness owns the tests, and every run is a rerunnable artifact ("logs will be written to…", `--run-id` names the run). The equivalent gate for RapidTool: *an artifact whose producer is not a logged, non-empty LLM synthesis call is ineligible for a green verdict*, and every run must be rerunnable from its run-id log.
- **Verifiable evidence, not claims** [S12]: Codex "provides verifiable evidence of its actions through **citations of terminal logs and test outputs**, allowing you to trace each step" — the scorecard's green must trace to executed log lines, the way the sandbox already produces them.
- **Never let the producer grade itself** [S10]: LLM-as-judge research quantifies self-enhancement bias — "GPT-4 favors itself with a 10% higher win rate; Claude-v1 favors itself with a 25% higher win rate" (also position bias). Any verdict component that is the same model's self-report (including "I verified this") inherits this bias; that is why the executed-test + provenance layer must carry the verdict, and why a model's claim of success in the artifact itself is not evidence.
- **Deterministic canaries for checks-vs-intent** [S8]: HVE/HVTB embed detectable hacks into tasks so that "satisfying a task's checks while violating its intent" becomes automatically detectable, because human/LLM detection "can be unreliable". A factory can embed analogous deterministic canaries (invariant/property assertions the code never sees) as its own black-box layer (see R4).

## Q6 — BOTTOM LINE: 5 concrete, cited recommendations for RapidTool's "produce 100% functional software" bar

**Preamble — the honest answer to the central question.** *Can a self-contained harness turn a brief into executable acceptance tests WITHOUT a human?* **No.** The evidence: real maintainer-written oracles were underspecified/unfair in ~2/3 of instances until humans repaired them [S28]; example-mapping treats unanswered questions as first-class red cards that stall acceptance [S16]; auto-generated white-box tests measurably overfit (21.8–35.9% of resolved instances) and refinement makes it worse [S4]. A machine can *draft* the executable acceptance suite and *run the whole loop to green*; it cannot *certify* that the suite captures the requester's intent. **The honest minimal human input is exactly one review-and-approve pass over the machine-drafted acceptance suite (scenarios + concrete examples + invariants + the flagged red-card questions), after which the factory's run-to-green loop is fully autonomous and its green is machine-checkable functional correctness against a human-confirmed oracle.** Without that pass, the ceiling is "self-tests green" — report it as such (draft + evidence), never as functional.

**R1 — Make the oracle external, frozen, and producer-independent (SWE-bench rule).** Structure synthesis as two actors: stage A ("acceptance") derives an executable suite from the brief — Given/When/Then scenarios, concrete example tables, property invariants [S15][S17][S19][S20]; stage B ("implementation") receives the *frozen* suite and the brief and must make it pass. Stage A's output is stored before stage B runs; stage B never edits it (SWE-bench's test_patch is "unseen" and harness-owned [S2][S11]). This is not cryptographic independence (same model family writes both), but the freeze + black-box split is the operational version of what every benchmark does, and it makes FAIL_TO_PASS-style transitions (red→green per test) the score, not presence of tests.

**R2 — The one human gate is acceptance-suite review, placed BEFORE the green loop.** Ship an "acceptance review" artifact: draft suite + a red-card list of questions the draft could not resolve from the brief (Example Mapping red cards [S16]) + explicit risk flags where examples are sparse. Human approves/edits (minutes, not hours — SWE-bench Verified's own lesson is that oracle quality is the binding constraint, not model effort [S28]). After approval, the machine loop to green is autonomous: run suite → fix → rerun, exactly the loop Codex documents ("iteratively run tests until it receives a passing result") and Claude Code prescribes ("give Claude a check it can run") [S12][S14]. If no human is available for a given job, downgrade the verdict class to "self-tested draft" and say so (see R5) — this mirrors the production-readiness findings of fixes/149.

**R3 — Green must mean executed, sandboxed, and logged — never "present" or "covered".** A verdict of functional requires: the frozen suite ran in a real environment with real inputs/outputs (SWE-bench's Docker harness [S11]; Terminal-Bench's "comprehensive tests for verification" in per-task environments [S5]; Codex's sandbox + "terminal logs and test outputs" citations [S12][S13]); per-test red→green transitions recorded (SWE-bench FAIL_TO_PASS semantics [S2]); rerunnable from a run-id (SWE-bench README [S11]). Disqualify coverage-noun heuristics (brief-derived identifier checks) from carrying functional claims — they are satisfiable by the floor by construction (fixes/154 Q2) and no benchmark treats "the words appear" as correctness [S1][S2].

**R4 — Treat self-authored tests as steering signal, and add a hidden deterministic layer.** Overfitting is measured, and refinement loops increase it (Claude-3.7-Sonnet 21.8→25.5%; GPT-4o 33.0→35.9% [S4]). Therefore: (i) any test the implementation stage generates is for its own debugging only, is never the acceptance suite, and its regeneration count is tracked as an overfit-risk metric; (ii) hold out a canary layer the code never sees — property-based invariants [S19][S20] and deterministic edge-case generators, the machine-usable analogue of HVE's embedded detectable hacks [S8] — and require it green before "functional" is claimable (DryRUN's lesson: self-tests refine, hidden suites certify [S9]); (iii) if a job iterates code-and-tests jointly more than k rounds, force the acceptance-review gate again — the overfitting paper's joint-refinement systems are exactly the ones it flags [S4].

**R5 — Provenance and breaker plumbing: no-green-without-LLM, stamps on artifacts, loud degradation.** (i) Every artifact records provenance — producer run-id, model vs deterministic-floor — in the C2PA "nutrition label" spirit [S26]; a floor-produced artifact is stamped "scaffold — not LLM-produced" and is ineligible for green regardless of M1..M9 scores (no-green-without-LLM gate; the floor satisfying brief-noun checks is the exact silent-failure class fixes/154 warns about). (ii) The LLM path is a circuit breaker: bounded retries → trip → degraded-with-banner, trip recorded with a monitor alert; degraded calls return errors, never silent substitutes [S27]. (iii) Scorecard green must cite executed log/test evidence [S11][S12]; a model's self-report in its own artifact is never evidence, quantified by LLM-judge self-enhancement (+10%/+25%) [S10]. (iv) Empty-content/thinking failures use the documented ladder — raise budget → disable thinking for the JSON envelope → two-pass → floor — with each attempt recorded (DeepSeek/OpenAI/Qwen docs [S21][S22][S23][S24][S25]; companion fixes/154 Q1).
