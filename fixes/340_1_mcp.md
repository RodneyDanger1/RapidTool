## 1. Protocol version + framing (what I implemented, and where it comes from)

**Protocol version: `MCP_PROTOCOL_VERSION = "2024-11-05"`** (`mcp.server.ts:42`). The client
requests it in `initialize` and then reports **the server's own** returned `protocolVersion`
verbatim (`mcp.server.ts:355-396`) — it never relabels the server's answer.

**Framing: newline-delimited UTF-8 JSON-RPC 2.0 — one complete JSON message per line,
**no `Content-Length` header.** This is what the MCP 2024-11-05 *Transports* section specifies
for stdio ("messages are delimited by newlines and MUST NOT contain embedded newlines"); the
`Content-Length:` header belongs to the earlier LSP-derived framing and is **not** implemented
and **not** accepted. I read this from the MCP specification revision named in the constant —
https://modelcontextprotocol.io/specification/2024-11-05/basic/transports (offline citation; no
network call was made or needed). The stub fixture (`src/lib/mcp/stub-server.ts:1-18`) frames the
same way, so the test exercises the framing rather than assuming it.

Transport mechanics in `mcp.server.ts`:
- spawn (`:532-543`) → `initialize` request (id 1) → validate `protocolVersion` / `serverInfo` /
  `capabilities` → `notifications/initialized` (`:385`).
- stdout lines are split on `\n` with a residual buffer (`onStdout`, `:242-263`); an unparseable
  line, an unknown/absent id, a reply carrying neither `result` nor `error`, an oversized line, and
  a JSON-RPC `error` object each **fail the whole client** (reject every in-flight request) — never
  a partial pass.
- one `Map<id, PendingRequest>` correlates responses to requests; the per-request timer is the
  bounded timeout and fires `failAll` (so a hung server cannot strand a later request behind a
  stale id).

### 9.4 Corrected claim (verbatim, `src/lib/mcp.server.ts:18-30`)

```
 *   - The four named refusal conditions — an unparseable line, an unsolicited
 *     id, a duplicate id, and an oversized frame — fail the WHOLE client: each
 *     sets a STICKY fault and rejects every in-flight request, and every later
 *     request refuses with that same coded reason. A malformed / error reply
 *     correlated to a request is likewise a coded refusal — never a partial
 *     pass. Every failure carries a code from `./errors.ts`.
 *   - Honest boundary: a violation that arrives on the stream AFTER a
 *     correlated reply has already resolved cannot retroactively fail that
 *     reply — its bytes arrived first, so `listTools`/`callTool` may still
 *     return `ok:true` for it. The taint is not hidden: it poisons every later
 *     request, and `client.faulted` exposes the original violation, so a
 *     single-call consumer must treat a non-null `faulted` as fatal. The F1
 *     round-trip (`listTools` then `tools/call`) therefore always fails closed,
 *     because its second request cannot slip past the fault.
```

### 9.5 What remains uncaught, and why (honest)

- **An already-resolved reply is not retroactively failed.** If the duplicate/garbage arrives after
  the correlated reply's bytes, the reply resolved first; no client can un-resolve it without
  withholding every reply until the stream is known-drained (which would break padding-free
  streaming and cannot distinguish "done" from "quiet"). The bounded fix is honest exposure:
  `client.faulted` is non-null from the instant the violation is parsed, so a consumer that checks
  it before acting on the resolved reply is safe. A consumer that calls once and ignores `faulted`
  can still act on a tainted reply — that residual is stated in the header, not hidden.
- **Correlated malformed replies (JSON-RPC `error`, or a reply with neither `result` nor `error`)
  reject only their own request and do not set the sticky fault.** They are the response the client
  was waiting for, not a stream-integrity violation; the task's four named conditions
  (unparseable line, unsolicited id, duplicate id, oversized frame) are the ones that fail the
  whole client. A future caller wanting error-reply stickiness would make a different contract.
- **A single-call consumer on the F1 path cannot be forced to observe it** — `connectMcpServer`
  hands back a live client; short of refusing to return `listTools` results at all (rejected above),
  the only honest lever is the exposed `faulted` state plus the round-trip's mandatory second call.

No new error code was minted (`errors.ts` is not mine); the refusal reasons reuse
`RT_E_VALIDATION` for the four protocol conditions and `RT_E_RUNNER_FAILED` for
timeouts/child/transport failures, exactly as §2 maps.
