## 1. Assessment — the loop is WRITE-capable and READ-capable, but OPEN: nothing measures whether memory changed behavior, nothing can falsify a lesson, and nothing on the artifact path can tell floor from software

### 1.1 The write side is real, honest, and mostly engine-deterministic (good)

- **Engine mints lesson rows in-loop, deterministically, no LLM:** L1 vague-brief at the P0
  lattice fallback (engine.ts:491-583, `lesson.capture` log); L2 template-emission on the
  seal path with a byte-parity evidence digest (engine.ts:1171+, `lessonEvidenceDetail`
  L1149-1163 ↔ knowledge.ts:670-684); L5 user-correction from every HITL decision
  (`correctionLesson` knowledge.ts:889-908); L5 run-summary digest at completion
  (knowledge.ts:1188-1221). L3 verify-failure / L4 verified-procedure are minted at the
  verify outcome seam (verify.server.ts:609/628/644/681 via `verifyOutcomeLesson`
  knowledge.ts:1173-1182) — **but that seam is only reachable through the single-module
  verify path** (codegen dispatch: kind-absent ≤8-sig libraries only, codegen.server.ts:1151-
  1158); the chunked tree path (>8 sigs, i.e. every real webapp) has no machine verify and
  says so honestly (codegen.server.ts:61-62 — "trees record no machine-verified lastTest …
  per-file deterministic validation is the … floor; the tree machine-run is the tree-run
  lane's step"). So **L3/L4 cannot exist for the delivery kind that matters most.**
- **Rows are content-addressed, capped, deduped:** `lessonRow` id = `lesson-<class>-<fnv8>`
  (knowledge.ts:619-653), memory rows capped/evicted at 80 with a pressure trigger
  (`pressureAt` threshold 60, knowledge.ts:942-944).
- **Cross-project promotion is human-gated and append-only:** `lesson accept` writes top
  FusionRank rows into the KnowledgeStore with the actor IN the content fingerprint
  (rapidtool-cli.mjs:1526-1543; `acceptedLessonEntry` knowledge.ts:1066-1107); the store is
  append-only + idempotent + merge-on-save against concurrent writers (knowledge.ts:353-374,
  332-347). Read-time evaluation exists: supersede exclusion + counter-evidence decay
  (halve per bump) + retirement at 3 bumps (`findPatterns` knowledge.ts:396-470, 516-529).

### 1.2 The read side is ADVISORY PROMPT TEXT ONLY, scoped to the project's own memory — and its effect is never measured

- The only two production read-back seams are (a) the keyed P6 expansion:
  `lessonLinesForBrief(selectLessons(project.memory, 6, …)) → expandBrief lessons`
  (codegen.server.ts:1115-1118) and (b) the P0 reframe HITL prompt (engine.ts:599-622). Both
  render `[kind score] text` bullets whose governing words are explicit: **"advisory —
  … never overrides the gate"** (engine.ts:620). Nothing downstream records whether the
  model followed the advice, ignored it, or was harmed by it.
- **The cross-project KnowledgeStore never reaches a synthesis prompt.** `injectProven`
  (the store→project advisory seam, knowledge.ts:481-506) is called only by the `packet`
  verb's Ranked-memory display (packet.ts:191-300, display/advisory) and prompt-engine's
  research tier — grep of all call sites: knowledge.test.ts / knowledge.ts / packet.ts /
  prompt-engine.ts / rapidtool-cli.mjs. The engine and codegen expansion read `project.memory`
  only. So years of cross-project lessons can accumulate and never change one line of
  generated code unless a human pastes the packet line into a prompt.
- **Falsification machinery exists but has NO automatic caller.** `bumpCounterEvidence`
  (knowledge.ts:545-555) and `markSuperseded` (knowledge.ts:560-572) are wired only to the
  manual CLI verbs `lesson refute` / `lesson supersede` (rapidtool-cli.mjs:1572-1660).
  `consolidatedRunNote` (the 98 §4.2 pressure-promotion, knowledge.ts:1140-1165) has no
  production caller at all. The comment at knowledge.ts:1111-1113 says machine-initiated
  supersede "is restricted by the caller to the verified-L4-contradiction path (98 §6.2)" —
  **that caller does not exist.** Consequence: an L4 row ("reuse this module shape next
  run") can be refuted by every later run and nothing ever bumps it; an L3 row can be fixed
  and never earns a verified successor. The lesson store is therefore **write-only with
  respect to behavior**: it accumulates, it is quoted, and it cannot be falsified or
  promoted by evidence, so it cannot converge.
- **M7 "learning" is a same-slug non-regression of identifier proxies, and it feeds no
  decision.** `m7Learning` compares this run's M1+M2+M3 against the last history row for the
  slug (maker-score.ts:466-483; prior comes from `research/eval-out/history.json` via
  `priorFor`, run-eval.mjs:218-224, 589-609) — M1-M3 are the identifier/compile/self-test
  proxies 155-SA §5-§6 proved vacuous. No code path anywhere makes a promotion/rollback
  decision from M7; it is a scorecard row.

### 1.3 Eval-gated promotion does not exist; convergence still does not read the gate

- `driveP6Journey` converges on `verdict.ok === true` (a green treeRun over the emitted
  temp dir), records the P6 DoD gate honestly, and **returns `outcome:"converged"` without
  ever reading `gate.passed`** (headless.ts:1374-1397; the return at :1397 is the defect
  155-SA §6 flagged — still open on disk at study time). A red P6 gate is therefore still
  compatible with "converged."
- The scorecard's only promotion-adjacent criterion, **M6 handover, is fs-presence**:
  emitted dir + DEPLOY.md + a `tests/oracle.spec.ts` ≥100 bytes (maker-score.ts:443-463;
  evidence gathered run-eval.mjs:395-427). Nothing asks "did the last change improve
  output," and the one behavioral runner that could (verify.server `runCases`, LLM-authored
  boolean expressions, verify.server.ts:366-451) is single-module-only, LLM-self-authored
  (the overfitting class 155-WF S4), A7-unseeded, and structurally bypassed for every
  declared kind (155-SA §3/§4/§6).

### 1.4 Production-readiness: the emitted artifact cannot prove what it is, and "software" never has to build

- **No provenance on artifacts.** `emitProject` writes the scaffold's files wholesale
  (headless.ts:1018-1039) with no manifest, no run-id, no producer field. The only honesty
  marker is a **prose header line** in DEPLOY.md — `DEPLOY_HONESTY_STAMP` "template derived
  from P9/P12 artifacts — verify credentials before any deploy" (scaffold.ts:99-101) and the
  body's "RapidTool's own P9 approval was a recorded, advisory gate — re-verify before a
  real deploy" (scaffold.ts:1731-1736). Nothing machine-readable ties the dir to its run,
  to `synthesisSucceeded`, to gate verdicts, or to the evidence hash — so a refused run's
  floor emission is **byte-indistinguishable from LLM software on disk** even though the
  scorer now forces M1-M4=0 (maker-score.ts:544-550). The honesty lives in the ledger, which
  ships nowhere.
- **No build gate.** `emit --check` is per-file parse; `emit --run` treeRuns the dir with
  the webapp entry an honest skip (compile-check.server kind smoke); neither is `npm install
  && vite build` — no webapp emission has ever built (fixes/149_a5 C7; 157 P2-1). P9
  "CI/CD & Cloud Deployment Routing" is a HITL phase whose approval is recorded-advisory
  only (phases.ts:77-83; scaffold.ts:1736).
- **Telemetry is real, bounded, and purity-tested but crash-class only.** rt-events v1
  schema + additive event catalogue (rt-events.ts:24-122), bounded ring 200 rows / 64 KB
  (rt-events.ts:218-219), NDJSON runtime log + `diagnose` read-back (runtime-log.server.ts),
  doctrine "telemetry must NEVER change engine behavior." But the catalogue has no
  run-outcome/production events (journey verdict, emit verdict, build verdict, manifest
  producer); nothing monitors the *produced* artifact because the produced artifact is
  never run anywhere (no build, no smoke, local-first DEPLOY.md by design).

### 1.5 The reviewer seat is advisory text, consistent with the loop's honesty — and therefore not a gate

The live-crew reviewer mandate is strong on paper — "PASS requires evidence for every
claimed behavior … never PASS on missing evidence" (crew.server.ts:94-95), reviewer sits at
P4/P5/P6/P9/P12 (crew.server.ts:146-159) — but its output folds back as an `[agent report]`
(crew.server.ts:112-117 STANDING_RULE: "You do not approve, reject, advance, or deploy")
and nothing executes it. Same honest-advisory shape as lessons: correct placement of the
human, not of the machine.

### 1.6 One-paragraph verdict

The slice is **plumbed but open at both ends of the self-improvement loop and at the
artifact boundary**: lessons are written deterministically and read back as advisory text
that nothing verifies, nothing falsifies (counter-evidence/supersede have no automatic
caller), and nothing promotes by evidence (M7 is a proxy non-regression that decides
nothing; the cross-project store never reaches a synthesis prompt); eval-gated promotion
does not exist (convergence ignores `gate.passed`; M6 is file-presence); and the emitted
artifact carries no machine-readable provenance, never has to build, and is never run, so a
floor/refused emission is indistinguishable from shipped software. Every fix below keeps
the existing honesty machinery (append-only store, content-addressed rows, floor
discriminators, bounded telemetry) and adds the missing **deterministic comparators,
evidence-gated promotion, and artifact provenance** — none of which needs an LLM judge.

### S3-1 — [P0, lands WITH 157 P0-1] Close the lesson loop with a deterministic post-run comparator: injection records → evidence-level counter-evidence → automatic refute/retire (the falsification kill-criterion)

**Problem:** §1.2 — lessons cannot change behavior (advisory text), cannot be falsified
(bump/supersede are manual-only), so the store cannot converge.
**Build:** (a) every read-back seam (codegen.server.ts:1115-1118 expansion; engine.ts:599-622
reframe) also appends an **injection record** to the ledger — `{lessonId, seam, phase,
promptHash}` — so the run knows which lessons it actually quoted; (b) a pure post-run
**comparator lane** (no LLM, no judge) maps recorded outcomes onto lesson predictions by
class: an L3 verify-failure row whose named gate/refusal class/unmet set repeats in a later
run ⇒ `bumpCounterEvidence` (the existing writer, knowledge.ts:545-555); a run that goes
green on the exact prior failure ⇒ mint the L4-style verified successor and, per the
existing 98 §6.2 rule that today has no caller (knowledge.ts:1111-1113), `markSuperseded`
the L3 — machine-initiated supersede finally gets its one legal path; (c) **the kill
criterion is the existing retirement threshold**: LESSON_RETIRE_COUNTER = 3 bumps ⇒
`findPatterns`/`injectProven` already exclude the row (knowledge.ts:404-408, 526-529) —
wire nothing new for retirement, only the bumps that feed it; (d) gate the journey loop on
nothing new — this lane is telemetry-plus-writes that never affects the gate (parity with
the rt purity doctrine, rt-events.ts:4-8).
**Why this design:** prompt-text memory is context, not control — Claude Code's own memory
doc says instructions are "context, not enforced configuration" and that blocking requires
a deterministic hook (W6); the deterministic comparator is RapidTool's hook. Metis shows the
two memory forms (text vs code) have real trade-offs and code-memory should be crystallized
"only when justified by repeated reuse" (W1) — i.e., refutation-counting before promotion,
exactly the counter-evidence decay. Evo-Harness's central finding is that raw execution
contexts are "rich but highly noisy," entangling lessons with task artifacts, so
improvement must be driven by isolating what generalizes (W4) — evidence-level bumps are
that isolation; an LLM judge would reintroduce the self-bias 155-WF S10 measured (+10%/+25%).
**Kill-criterion statement for the parent:** *a lesson that accumulates 3 counter-evidence
units is retired from retrieval automatically; a lesson that survives N (start 3) injections
with zero refutations becomes eligible for S3-2 compilation — no lesson is ever promoted on
first sight, and no lesson is ever removed except by the append-only supersede row.*

### S3-2 — [P1] Compile surviving lessons into deterministic canaries ("skill → harness"), the only lessons that may gate or promote

**Problem:** text advice can be ignored with no signal; the only executable checks in the
tree are scaffold self-tests (155-SA §3).
**Build:** extend the KnowledgeEntry schema with `harness?: string` (append-only field,
participates in the fingerprint) and add a `lesson compile` verb + post-run lane that turns
a refutation-free lesson into an **executable probe** — an input→output fixture, a gate-unmet
set predicate, or a refusal-class predicate (identifier-presence checks are banned from
canaries; 155-SA §5). Compiled canaries are emitted into the scaffold's tests/ and run by
treeRun, so "did the lesson hold" becomes a deterministic red/green in the loop. A canary
that fails N runs is un-compiled by appending a supersede row (S3-1 machinery). **Only
compiled lessons may raise M7 or gate promotion** (S3-3); text-only rows stay advisory.
**Evidence:** Evo-Harness frames exactly this — context-to-harness "skill compilation"
turns distilled lessons into reusable, checkable harnesses evaluated across tasks (W4);
L4 verified-procedure (knowledge.ts:863-882) is already Voyager-style commit-on-verify —
the missing step is that the "procedure" is never expressed as a runnable check; Claude
Code best practice is "give Claude a check it can run," not advice it may ignore (155-WF
S14); DryRUN: self-tests refine, hidden/external suites certify (155-WF S9).

### S3-3 — [P1] Eval-gated promotion with a backward-transfer bar — "did the last change improve output" answered only against fixed external fixtures, never self-judged

**Problem:** §1.3 — no promotion decision exists; the only prior-comparison (M7) is a proxy
non-regression (maker-score.ts:466-483) that decides nothing.
**Build:** any store/retrieval mutation that changes what later runs see (accept, supersede,
refute, S3-2 compile) triggers the **same-slug regression check that already exists**
(`priorFor` over history.json, run-eval.mjs:218-224) extended to the whole corpus the change
could affect: promote only when (a) the capability/canary set that was green before the
mutation is still green (PASS_TO_PASS semantics, 155-WF S2) and (b) the mutated slug's
score does not regress. Where S3-2 canaries exist, the gate is FAIL_TO_PASS-style per-canary
transitions; where they do not exist yet, the gate is **"no promotion"** — never the
identifier proxies (the vacuous case 155-SA §5). The scorecard's M7 evidence string then
names the canary counts, not M1-M3 sums.
**Evidence that "did the last change improve output" only works with this shape:** SWE-Bench-CL
measures continual learning with explicit forgetting/backward-transfer metrics and shows
memory-enabled agents must resist catastrophic forgetting — an update that improves task N+1
but regresses task N is not an improvement (W2); Live-SWE-agent's runtime self-evolution is
precisely the dangerous case — evolving the scaffold while solving, with no offline eval net
— and its value is measured on SWE-bench Verified's *held-out* tests (W5); Evo-Harness
validates every improvement factor against held-out tasks across five benchmarks (W4);
self-authored suites overfit and refinement makes it worse (155-WF S4); LLM-judged
"improvement" carries the measured self-enhancement bias (155-WF S10). Fowler's canary is
the production analog: ship the change to a small subset and watch before full rollout (W8)
— the "subset" here is the held corpus slice.

### S3-4 — [P0, lands WITH 157 P0-3] Provenance manifest on every emission: make a floor/refused run un-shippable as "software"

**Problem:** §1.4 — the emitted dir carries no machine-readable record of what produced it.
**Build:** `emitProject` (headless.ts:1018-1039) additionally writes `rapidtool.provenance.json`
into the emitted dir (and a header line into DEPLOY.md beside the existing
DEPLOY_HONESTY_STAMP, scaffold.ts:99-101) carrying: run-id/slug, emission ISO time, the
`synthesisSucceeded` discriminator (the same one the scorer already keys on,
maker-score.ts:122-131, computed in run-eval.mjs:445-448), lastTest evidenceHash, P6/P7/P9
gate verdicts, treeRun/build summary, and `producer: "llm" | "floor" | "floor+repair"`.
**Consumer rule (the actual safety property):** any downstream step — the S3-5 build gate,
the DEPLOY.md "ship" claim, a human handoff, or the repair seam (repairTreeDir, headless.ts:
1427-1434) — reads the manifest and **refuses the "software" label when
`synthesisSucceeded === false` or the P6 gate record is red**; the emission remains
available as scaffold (the artifact-side mirror of the card-level floor gate
maker-score.ts:544-550, which today lives only in the scorecard that ships nowhere).
**Evidence:** SLSA's provenance requirement is exactly this — provenance "MUST …
unambiguously identify the output package by cryptographic digest and describe how that
package was produced," distributed to consumers (W7); C2PA's "nutrition label" framing for
content provenance (155-WF S26); SWE-bench's no-green-without-harness-ownership and run-id
rerunnability (155-WF S2/S11). The manifest's `producer` field makes "floor vs LLM" a
first-class data field instead of an inference — the class of fix 155-WF Q5/R5 demands.

### S3-5 — [P1; the C7 build gate, pulled earlier than 157 P2-1] "Emitted software" must mean "builds and boots": default-on build + entry smoke inside the loop

**Problem:** no webapp emission has ever built (149_a5 C7; §1.4); canary/promotion machinery
is meaningless for artifacts that cannot start.
**Build:** extend `emit` (cli:663-749) and the journey's defaultP6RunTree
(headless.ts:1224-1260) with a kind-appropriate build step — `npm install && vite build`
(webapp) or the kind's equivalent — plus a node smoke that imports the assembled entry and
calls the data layer (replacing the "UI shell — honest skip" entry verdict, the skip
155-SA §6 documents). Red build ⇒ emit exits non-zero with the build log tail in the
envelope (parity with `emit --run` exit-1 discipline, cli:716-740), DEPLOY.md carries no
ship claim, and the S3-4 manifest records `built:false`. Keep the honest boundary: build
and smoke, not deploy — nothing here deploys anywhere (DEPLOY.md framing, scaffold.ts:1691-
1736). Note 157 P2-1 already carries this as a "close the loop" item; this addition moves it
earlier and makes it a **precondition for any artifact that claims "software"**, because the
P0-1 fixture runner needs a runnable tree to execute fixtures against.
**Evidence:** functional correctness is defined by execution, not presence (155-WF S1-S3);
Codex's loop runs the repo's real test/build commands to green (155-WF S12); canary release
presupposes a deployable build (W8).

### S3-6 — [P1] Run-id rerunnable evidence on the dir: emit, tree-run, and repair must agree on which run the dir is

**Problem:** today `tree-run --dir`/`repair` (cli:751-822) hash-check dir vs ledger
(`dirDirty`) but nothing binds the dir to its run-id; a dir from run A can be repaired
against the ledger of run B.
**Build:** after S3-4 the manifest is the binding: `repairTreeDir` verifies the dir's
manifest run-id matches the loaded ledger project before applying any repair write
(headless.ts:1427-1434 seam); a repair that changes tree content re-writes the manifest with
the new per-file hashes (the hash-checked import already computes them, headless.ts:1485-
1499). Persist manifest fields into `research/eval-out/results.json` (run-eval persist,
run-eval.mjs:575-611) so the eval ledger itself is provenance-bearing and every scorecard
row is rerunnable from its run-id — the SWE-bench harness property (155-WF S11) and Codex's
"citations of terminal logs and test outputs" (155-WF S12).

### S3-7 — [P2] Run-outcome telemetry + a degrade breaker that trips on refusal chains — monitoring without touching engine purity

**Problem:** telemetry is crash-class only (§1.4); nothing records journey/emit/build
verdicts as events, and the refusal→floor degrade (which the scorer now handles honestly,
maker-score.ts:544-550) has no live alarm.
**Build:** (a) add additive event names to the existing catalogue (rt-events.ts:124+,
additive-only law) for `p6.journey.converged/failed`, `emit.verdict`, `build.verdict`,
`manifest.producer=floor` — all stamped through the existing bounded ring (200×64 KB,
rt-events.ts:218-219) and NDJSON log, never changing engine behavior (purity doctrine,
rt-events.ts:4-8); (b) wire the refusal→floor transition as a **circuit-breaker trip**:
bounded retries → trip recorded with the RT_E class → the run continues but the UI banner
and the emitted manifest say "degraded — floor scaffold, not software" until a keyed
recovery (S3-4 consumer rule). Trip semantics = errors and loud records, never silent
substitutes + an alert (155-WF S27). Monitoring of the *shipped* artifact stays out of
scope — the scaffold is local-first by design (scaffold.ts:1691-1696); do not add runtime
telemetry to emitted scaffolds without a product decision (declare-or-strike).

### S3-8 — [P1, part of 157 P0-1 step (b)] Wire the human-approve acceptance gate into the UI and CLI by reusing the two existing human-gate patterns

**Problem:** 157 P0-1 requires a human approve pass over the machine-drafted acceptance
suite but does not name the wiring; the repo already has two proven human-gate patterns that
must be reused rather than reinvented.
**Build:** (a) **HITL machinery** — engine `approveHitl` (engine.ts:1515+, forceHuman
refusals, decision rows), store approve/reject with note (store.ts:91-93), the console
awaiting_hitl Approve/Reject panel with the ≥12-char rejection rule (console.tsx:1231-1330,
keyboard 'a' at :971), CLI approve/reject (rapidtool-cli.mjs:456-520); (b) **the lesson-accept
editable-JSON pattern** — the fixture draft is *written like `lesson accept`*: top rows
proposed, human edits/approves in an editable JSON surface, and the accept is a
human-gated, actor-stamped write (cli:1526-1543; `acceptedLessonEntry` knowledge.ts:1066-
1107). Concretely: a `fixtures draft|approve|reject` verb family + a console "Acceptance
suite" panel; approve = human-gated write of `tests/fixtures.brief.json` (the P0-1 corpus,
157 §4) into the project record before the run-to-green loop may claim functional; reject =
note routes back to the drafter (the ≥12-char rule + L5 correctionLesson capture,
knowledge.ts:889-908) so the rejection is itself a lesson. Every approve/reject lands a
`hitl.decision` row + a memory row, exactly like today's gates — the acceptance gate becomes
auditable like every other gate. The human-approve model the web evidence supports: one
review of machine-drafted acceptance criteria before autonomous run-to-green (155-WF R2,
S14/S16/S28 — the human repairs oracle unfairness, 68.3% filtered in SWE-bench Verified).

### S3-9 — [P2] Upgrade M6/M7 to carry the manifest and the canary counts (scorecard honesty follows artifact honesty)

**Problem:** M6 is fs-presence (maker-score.ts:443-463); M7 is proxy non-regression that
decides nothing.
**Build:** M6's evidence must cite the S3-4 manifest fields (`synthesisSucceeded`,
`producer`, gate verdicts, `built:false|true` once S3-5 exists) — a handover dir whose
manifest says `producer: floor` keeps M6=0 (artifact-side floor gate in the scorer itself,
not only in the downstream consumer); M7, once S3-2 canaries exist, compares behavioral
canary pass-counts across the same slug (backward transfer, W2) instead of M1+M2+M3 sums.
Do not rename M6/M7 semantics before the fields exist; sequence: S3-4 manifest → M6 reads
it; S3-2 canaries → M7 compares them.

## 3. Sequencing notes for the parent (157 §5)

1. **P0 wave (with 157 P0-1/P0-3):** S3-1 (comparator lane — pure, keyless, no new gates)
   and S3-4 (provenance manifest — a write in emitProject) are both small and prerequisite:
   S3-1 gives the acceptance gate a lesson trail, S3-4 makes P0-3's "floor un-representable
   as a keyed success" true on the artifact, not just the scorecard.
2. **P1 wave (after the fixture oracle exists):** S3-5 (build gate) must precede S3-3
   (promotion) because promotion needs runnable fixtures; S3-2 (canary compilation) and
   S3-8 (acceptance-gate wiring) are the two halves of "the loop changes behavior with a
   human-confirmed oracle"; S3-6 rides S3-4.
3. **P2 wave:** S3-7 (telemetry events + breaker) and S3-9 (M6/M7 upgrade) — both depend on
   earlier artifacts existing.
4. **The honest end-state claim gains two new sentences:** (a) "every emitted artifact
   carries a provenance manifest whose `producer` field makes floor-vs-LLM a fact, not an
   inference, and downstream build/handoff steps refuse the software label without it";
   (b) "lessons that survive refutation-free injection are compiled into deterministic
   canaries, and only canary-verified knowledge is promoted across runs — the lesson store
   is no longer write-only, and every lesson has a kill criterion."
