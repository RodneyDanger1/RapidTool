## 0. BOTTOM LINE (read first)

- **RapidTool's memory substrate is ahead of its injection.** Episodic/semantic/procedural rows
  with provenance + supersede/retire exist (`MemoryEntry`, types.ts above Project :270;
  engine `mem()` writers; agent-report ingestion report-intake.ts; HITL "human" rows). But the
  two *product* surfaces of memory are thin: the copilot sees only **top-3 by score, no pins**
  (chat.server.ts:196-200) and the UI Memory list is **read-only, insertion-order, first 8**
  (console.tsx:2388-2404). There is **no pin**, no human "add memory row" affordance, and the
  one human-writable standing-instruction field — `Project.notes`, "Operator notes for the
  crew" (console.tsx:2375-2382, setNotes store.ts:1606) — is **injected into nothing**:
  grep of buildChatContext (chat.server.ts:227-243) and prompt-engine.ts shows no `notes` read.
  That is a CLAUDE.md/AGENTS.md equivalent that exists but is inert (168A-1).
- **Long conversations are discarded, never compacted.** The persisted chat thread is capped at
  40 rows by a silent `.slice(-40)` (store.ts:1622), and the UI renders only the last ~12
  (console.tsx:4616) — the oldest rows vanish with no summary, unlike Claude Code's auto-compact
  (168A-2). The chat is also a hard read-only surface (rule 4, chat.server.ts:94), so nothing an
  operator says can ever become memory (168A-4).
- **Delegation is already the most complete of the four areas**: crew has turn retry w/ backoff
  (crew.server.ts:844-860), max-steps + cost-limit stops with honest partial transcripts
  (CrewStopReason), JSON-envelope output validation (crew.server.ts:560-574 round-trip guard),
  and "child reports are not facts" is structurally enforced (advisory `[agent report]` ingest;
  DoD gates never read crew verdicts). Remaining gaps are small: the **run transcript is not
  persisted** (console.tsx:1424-1442 ingests a ≤400-char summary + artifact list; the per-role
  `messages` array dies with the React state) so a partial run cannot be continued with its
  reasoning (168A-5), and **no console cancel/kill** exists for a crew run that can legally take
  12 × 90 s (168A-6). The deterministic swarm critique is **CLI-only** while its module is
  client-pure (168A-7).
- **Persistence is genuinely hardened** (quota-safe storage, corrupt-blob heal, salvage trim,
  persistStorageHealth) — the honest gaps are a **missing beforeunload guard** during any async
  engine op (168A-8) and a **health-aware saved indicator** (168A-9, the complement of 165A-10).
- **Code output is where the product under-delivers most visibly.** The multi-file
  `generatedTree` (A0/codegen) is **never rendered or downloadable in the console** — grep finds
  only `generatedSource` reads (console.tsx:1820, 4529); no file tree, no per-file copy, **no
  zip export** (no fflate/jszip in package.json), **no syntax highlighting** (no shiki/prism/hljs
  in package.json; code blocks are plain mono `<pre>` + caption, console.tsx:3036-3050), and the
  engine-side regeneration/repair deltas (treeReviewContext) never reach the user. README
  generation, by contrast, **already exists** (scaffold.ts:1493-1553, README.md is a real row of
  the emitted tree) — do not rebuild it (168A-10…13).

## 1. MEMORY (Claude Code CLAUDE.md + auto-memory + pinning analog)

### 168A-1 — `Project.notes` is the CLAUDE.md/AGENTS.md equivalent and it is inert: injected into no prompt surface
- **WHAT**: RapidTool already carries a per-project standing-instruction field — `notes: string`
  on Project (types.ts ~:350), editable in the Crew pane ("Operator notes for the crew…",
  console.tsx:2375-2382, setNotes store.ts:1606-1609). Claude Code loads CLAUDE.md into every
  session; Codex auto-loads AGENTS.md. RapidTool's field reaches **zero** LLM surfaces: grep of
  `buildChatContext` parts (chat.server.ts:227-243) has no notes line; grep of prompt-engine.ts
  has no `notes` read (only lesson-tagged memory rows, :308); crew.server.ts prompts cite
  "prior crew artifacts, crew transcript" but not the notes textarea.
- **WHY it matters**: an operator who types "always name generated modules `<domain>.ts`" or
  "this build targets IE11-grade constraints — say so in gate prompts" into the only standing
  field gets exactly zero behavioral effect. The top factories' single most-copied feature
  (project instruction file, auto-loaded) exists here as a dead input.
- **DOES RapidTool HAVE it**: field + editor yes; **injection absent** (grep evidence above).
- **WHERE**: `src/lib/chat.server.ts` `buildChatContext` (parts array :227-243); optionally
  `src/lib/prompt-engine.ts` expansion assembly and `src/lib/crew.server.ts` turn-context
  builder.
- **HOW** (RT-idiomatic): in buildChatContext, after the `memory:` line, emit
  `notes: ${clip(p.notes, 240)}` **only when non-empty** (absence stays byte-identical —
  mirrors the rejectedLine pattern at :204-210 and keeps the F2 determinism/parity pins green).
  For the crew, include the same clipped line in the per-turn context when non-empty. Do NOT
  change the notes editor or the field shape; hydration already tolerates absent notes
  (engine.ts:2208 coerces to ""). Keep clip() small so the instruction-critical tail lines
  (:129-131 invariant) still survive the 2500-char budget.
- **TEST**: chat.test.ts — a project with `notes` set emits a `notes:` context line clipped at
  240 and the byte-parity pin holds for a project without notes; crew.test/crew.server test —
  notes text appears in the assembled turn context; a 10 000-char hostile notes string cannot
  push the context over CHAT_CONTEXT_MAX_CHARS.

### 168A-2 — Chat history is dropped at the 40-row cap with no rollup: no auto-compaction analog
- **WHAT**: appendChatRows caps the persisted thread with a silent `.slice(-40)`
  (store.ts:1616-1622); the engine never appends chatLog (user-owned, store.ts:209-213), and the
  console renders only the last ~12 rows (console.tsx:4616 comment). The oldest 28 rows are
  simply gone — no "earlier conversation" summary row. Claude Code auto-compacts long
  conversations into a summary and keeps going.
- **WHY it matters**: every meaningful conversation about *why* a gate was rejected or *which*
  retry direction the operator picked lives in the oldest rows of long threads — exactly the
  rows the cap deletes. The copilot then re-answers from a thread whose history silently
  contradicts the project state it was grounded in.
- **DOES RapidTool HAVE it**: input-side trimming yes (server caps outbound history to the last
  6 turns, per-turn 800 chars, chat.server.ts:52-56); **persisted-thread compaction absent**.
- **WHERE**: `src/lib/chat.server.ts` (new pure `planChatCompaction(rows, cap)` + optional
  keyed `compactChatRowsServer`), `src/lib/store.ts` appendChatRows (:1616) and a new additive
  `replaceChatRows(id, rows)` action; console sendChat (console.tsx:4704-4726).
- **HOW** (RT-idiomatic, keyless-honest): pure rule — when an append would exceed 40, the oldest
  N (e.g. 16) rows are eligible; if a key is configured, one flash call (maxTokens ~300, same
  seam as chat.server) produces a single assistant-style summary row stamped
  `provenance: "auto-compacted …"` (reuses the existing provenance/staleness machinery,
  chat.server.ts:65-76) and the 16 rows are replaced by it (net −15); keyless fallback is a
  **deterministic** row: `Earlier conversation (N turns before <ISO>) omitted — no key
  configured.` so the honest floor never fabricates. appendChatRows stays sync (persist policy);
  the console calls the server compact fn after appending when the pure planner says a drop is
  imminent, then replaceChatRows. UI: when a summary row is present render it collapsed with an
  expand toggle (reuse MarkdownBody).
- **TEST**: unit — planChatCompaction triggers exactly at the cap, summary row sorts newest,
  byte-parity when under cap; store round-trip — replaceChatRows survives export/import (io
  sanitizer pass-through, mirror chatLog additive handling engine.ts:2065-2068); keyless path
  produces the deterministic row and never calls the LLM seam.

### 168A-3 — No memory pinning: a human-important row can be crowded out of every prompt
- **WHAT**: `MemoryEntry` (types.ts, just above Project :270) has no `pinned` flag; the copilot
  context takes **top 3 by score** with stale-demotion only (chat.server.ts:190-200); the UI
  Memory list shows the first 8 in insertion order with no pin control (console.tsx:2388-2404).
  Claude Code/OpenHands both let the user mark memory that is **always** injected.
- **WHY it matters**: the engine writes high-score rows every phase (mem() templates score
  0.93-0.99, engine.ts:659-736), so a *human* row (source "human" via HITL, or the 168A-4 add
  affordance) competes against engine rows on score and usually loses the top-3 slot exactly
  when the human needs the copilot to hold it ("the client renames this project at P9 — ask
  before deploy").
- **DOES RapidTool HAVE it**: **absent** (grep `pinned` across src/lib/chat.server.ts,
  knowledge.ts, vault.ts → no hits).
- **WHERE**: `src/lib/types.ts` MemoryEntry (+`pinned?: boolean`, additive, legacy-absent —
  same discipline as `source`/`tags`); `src/lib/chat.server.ts` :190-200 (pinned-first sort);
  console Memory section :2388-2404 (pin toggle + badge); `src/lib/store.ts` new
  `pinMemory(id, memoryId, on)` beside setNotes (:1606).
- **HOW**: additive optional field; hydrate copies it through (memory rows already pass through
  hydrate — verify with a round-trip test like chatLog's, engine.ts:2065); io.ts sanitizer
  tolerates unknown optional fields (mirror the chatLog arm, io.ts ~:294-360). buildChatContext:
  stable-sort `pinned` rows ahead of score rows (pinned first, then existing stale-demotion +
  score + id tiebreak), still within the top-3 slice so the 2500-char budget and the tail-line
  invariant (:129-131) are untouched. UI: small pin button per Memory row + "Pinned" badge;
  pinned rows also pinned at the top of the UI list (before slice(0,8)).
- **TEST**: chat.test — a pinned low-score row outranks an unpinned 0.99 row in the context
  memory line; store round-trip — pinned survives export/import and legacy payloads hydrate
  without the field (absent, never false); console — static/manual: toggle flips the badge and
  the persisted JSON gains `"pinned":true`.

### 168A-4 — Nothing in the UI lets a human write a memory row (and chat is hard read-only)
- **WHAT**: memory rows are written only by engine templates, agent-report ingestion and HITL

  explicitly advisory and may never edit the project (rule 4, chat.server.ts:94). Claude Code's
  Auto memory is *agent-written* on top of human corrections — the RapidTool analog of a
  correction becoming durable knowledge does not exist.
- **WHY it matters**: the entire "learns" story (162 Phase C) depends on a loop the operator can
  actually feed. Today the only human channel into memory is approving/rejecting gates.
- **DOES RapidTool HAVE it**: **absent** as an affordance (provenance type `source:"human"` and
  HITL row writing exist engine-side, engine.ts:468 comment).
- **WHERE**: console Memory section (console.tsx:2388) + `src/lib/store.ts`
  (`addMemory(id, {kind, text, phase})` beside setNotes/pinMemory); MemoryEntry.source set to
  `"human"`.
- **HOW**: a two-line "Add note to memory" textarea + kind select appends
  `{id, kind:"semantic", phase: currentPhase, text, score:1, source:"human"}` through a new
  store action (user-owned field, engine never overwrites — same contract as chatLog/notes,
  store.ts:209-213 commit-merge preserves user-owned additions). Keep the honest score: human
  rows get 1.0 so they surface in the copilot's top-3 until 168A-3's pin lands. Do NOT relax
  the chat read-only rule (that would break the 156-E2 action-honesty floor) — the Memory
  textarea is the write surface instead.
- **TEST**: store test — addMemory appends with source "human" and survives an engine commit
  (user-owned merge, store.ts:275-289 pattern); chat.test — buildChatContext includes the new

### 168A-5 — Crew run transcripts are not persisted: partial runs cannot be continued, and reload loses who-said-what
- **WHAT**: after `runCrew`, the per-role `messages` array lives only in transient React state
  (setCrewRun, console.tsx:1413); the ingest payload carries a ≤400-char last-message summary +
  the artifact list (console.tsx:1418-1430). A `max-steps`/`cost-limit` stop is honestly labeled
  "partial" — but the reasoning that produced the partial artifacts is gone the moment the pane
  unmounts or the tab reloads, and a follow-up `runCrew` starts cold (roles from step 0) because
  the transcript is not among the "prior crew artifacts" the prompts reference
  (crew.server.ts:115).
- **WHY it matters**: resume-after-budget is the flagship delegation ergonomics of the top
  factories (OpenHands/Claude Code both continue agent sessions); RapidTool returns an honest
  partial and then throws the context away.
- **DOES RapidTool HAVE it**: ingest summary only — **full transcript persistence absent**.
- **WHERE**: console onSpawnCrew payload (console.tsx:1397-1442); additive Project field or an
  ingested artifact; `src/lib/types.ts`, engine.ts hydrate, io.ts sanitizer (mirror the chatLog
  additive pattern engine.ts:2065-2068).
- **HOW** (choose the smaller): (a) ingest a second `[agent report]` artifact "crew transcript —
  <phase> <ts>" whose body is the numbered role turns (cap ~8 KB with cutMarked, same seam as
  chat.server.ts:56) — no type change, survives export/import automatically, and becomes part of
  the next run's "prior crew artifacts" context; (b) alternatively a typed additive
  `crewLog?: CrewMessage[]` mirroring chatLog (cap 40, user/engine-ownership table). Recommend
  (a) for Phase D size; (b) only if the crew tab needs to re-render the transcript after reload.
- **TEST**: crew flow test — after a partial stop, the ingested transcript artifact exists with
  every role turn and export→import round-trips it; a second runCrew's assembled context
  includes the prior transcript text (crew.server context-builder unit test).

### 168A-6 — No cancel/kill for an in-flight crew (or keyed phase call); worst case ≈ 18 min with no abort path
- **WHAT**: a crew run is one awaited server-fn POST; the console's busy latch only disables
  buttons (busyAction "crew", console.tsx:1144, 1397-1405). Nothing can interrupt the
  crew.server turn loop (crew.server.ts:930 `while (idx < roles.length && step < maxSteps)`)
  short of closing the tab — and 12 turns × 90 s means a stuck first role costs 18 minutes of
  dead UI. Claude Code/Codex both let you interrupt a delegate mid-turn.
- **WHY it matters**: a sub-agent that loops (or a user who spots a wrong direction on turn 2)
  must not be unkillable; "kill a hung subagent" is the one delegation primitive this lane was
  asked to check that is genuinely missing.
- **DOES RapidTool HAVE it**: per-call timeout yes (90 s); **abort between turns absent**.
- **WHERE**: `src/lib/crew.server.ts` driver loop (:930) + a small abort token; console Crew
  pane (Stop button beside Spawn); store action `requestCrewAbort(id)`.
- **HOW** (RT-idiomatic, no client-fetch surgery): persist an abort request as an additive
  project field `crewAbort?: {requestedAt:number}|null` written by a store action before the
  console shows "Stop crew"; the server driver checks the abort token **between turns** (and
  before each retry) and returns the honest partial with a new `CrewStopReason` value
  `"aborted"` (crew.ts:93 union + status string) — the transcript-return path already exists
  for max-steps, so this reuses it. The console Stop button sets the token (not a fetch abort),
  so a mid-turn call still completes/retries once but the loop stops at the next boundary —
  honest and bounded. Engine phase-call cancel (executeAsync) can reuse the same token pattern
  later; out of scope here.
- **TEST**: crew.server unit with injected seam — a run whose token is set after turn 1 returns
  `stopped:"aborted"` with the honest partial transcript and artifacts; console/manual — Stop
  button appears only while busyAction==="crew" and the notice says "(aborted)".

### 168A-7 — The deterministic swarm critique is CLI-only while its module is client-pure
- **WHAT**: `swarmPlan` (swarm.ts:693) is a pure, LLM-free advisory critique (seats per phase,
  markers scan, refinedPlan) reachable only via the `swarm` CLI verb (rapidtool-cli.mjs:1177,
  headless.ts:2396); swarm.ts imports only types + PHASES (swarm.ts:25-34) — it is safe to call

- **WHY it matters**: the operator in the UI never sees the deterministic advisory pass the CLI
  user gets for free — a zero-cost second opinion on the current phase before spending a keyed
  crew run.
- **DOES RapidTool HAVE it**: CLI yes; **console surface absent**.
- **WHERE**: console phase dock (near "Rejection guidance (LLM) · advisory", console.tsx:2812)
  or Crew tab header.
- **HOW**: a collapsible "Advisory swarm critique (deterministic)" block that calls
  `swarmPlan(project)` synchronously on tab open and renders critiques/verdicts/refinedPlan via
  the existing MarkdownBody + list components. No server call, no key, no new deps; must be
  visibly labeled advisory (reuse the exact "advisory — DoD gates keep ruling" wording).
- **TEST**: console static/manual on a mid-run project; a unit test is optional (swarm.ts
  already has 20+ tests; the new code is a render-only wrapper).

### 168A-8 — No beforeunload guard while any async engine op is in flight
- **WHAT**: grep of console.tsx for `beforeunload` → **no hits**. While a keyed phase executes,
  a crew runs, a P6 journey or a wild run is active (busyAction ≠ null, console.tsx:1144; wild
  strip :786-812), closing the tab silently discards the awaited server commit — no warning, no
  "interrupted" record.
- **WHY it matters**: crash-restore in a browser product starts with *not losing the in-flight
  op unknowingly*; the top factories warn on close during active work. (The engine's commits
  are atomic per phase, so nothing *corrupts* — the gap is the user's awareness + a marker.)
- **DOES RapidTool HAVE it**: **absent**.
- **WHERE**: console.tsx root effect (beside the existing mount effects :1166-1175).
- **HOW**: `useEffect` registering `beforeunload` when `busyAction !== null || wild.run?.active
  || crewRunBusy` → `e.preventDefault()` + returnValue string ("A RapidTool run is in progress —
  closing now may discard its result."). Optionally (cheap crash-restore upgrade): a persisted
  `interruptedOp?: {kind, startedAt}|null` marker set before each async op and cleared on
  commit, with a hydrate-time banner when a marker is stale — honest "your last run may have
  been interrupted mid-call; re-run the phase" instead of silence. Marker must never throw into
  the op (telemetry purity rule).
- **TEST**: DOM/manual — start a keyed run, attempt close → dialog appears; idle project →
  close is silent. Marker helper unit test in store.test (set/clear/stale logic pure).

### 168A-9 — The "saved HH:MM" indicator must flip amber on a real persist failure (complement of 165A-10)
- **WHAT**: the header stamp is driven by a `[project]`-identity effect (console.tsx:1172-1175)
  — 165A-10 owns fixing that it can stamp page-open time. The piece 165A-10 does **not** cover:
  when `persistStorageHealth().ok === false` (quota/blocked, store.ts:670-676), the header still
  renders "saved HH:MM" in the normal tone; the failure is only visible by opening the Runtime
  log and clicking Diagnose (PB-02 samples at click time, console.tsx:3213-3220).
- **WHY it matters**: a "saved" stamp next to a failed persist write is the exact honesty
  violation the repo's contract forbids (declare-or-strike) — the in-memory state will NOT
  survive a reload and the UI says it was saved.
- **DOES RapidTool HAVE it**: latch + diagnose yes; **live indicator no**.
- **WHERE**: console.tsx header stamp block (:1668) + the RuntimeLogPane PB-02 code (:3213).
- **HOW**: a tiny store subscription — re-read `persistStorageHealth()` whenever the project
  identity effect fires and on a 3 s interval while mounted; when `!ok`, render
  "not saved — storage failed (see Runtime log)" in the danger tone instead of the clock.
  Pure read, no engine coupling (same rule as PB-02's comment). Coordinate the merge with
  165A-10's fix so both land on the same stamp element without conflict.
- **TEST**: store test — after a forced quota failure the helper returns ok:false; console
  manual/DOM — stub localStorage.setItem to throw, mutate the project, assert the danger-tone
  text appears and "saved" does not.

### 168A-12 — No syntax highlighting in any code view
- **WHAT**: code blocks render as plain mono text (console.tsx:3048 `<pre>` without token
  spans); no highlight library in package.json (grep shiki/prism/highlight.js → no hits).
- **WHY it matters**: cosmetic but high-touch — every artifact pane and (after 168A-10) the tree
  pane shows code; the top factories ship highlighted code as table stakes.
- **DOES RapidTool HAVE it**: **absent** (only the `language` caption, console.tsx:3038-3042,
  which is already parsed per block and can drive the highlighter).
- **WHERE**: console.tsx MarkdownBody code case (:3036-3050) and the 168A-10 tree pane.
- **HOW**: dynamic-import Prism core + a fixed language set (ts, js, tsx, json, md, css, html,
  bash — matching the `language` field values artifacts already carry) inside a `useMemo` when
  `b.lang` is known; tokenize to React spans; **any load/tokenize failure falls back to the
  existing plain `<pre>`** (never a crash, never innerHTML — the 2961 comment rule). Bundle
  impact ≈ 0 until a code block renders, and zero for unknown languages. Alternative if the
  maintainers prefer zero-dep: a hand-rolled 30-line keyword/string/comment highlighter — but
  Prism via dynamic import is the honest, tested route.
- **TEST**: DOM/manual — a ts artifact renders `.token.keyword` spans; an unknown `lang` and a
  network-failed import both fall back byte-identically to the current plain pre (regression
  probe on MarkdownBody output).

### 168A-13 — Regeneration/repair deltas never reach the human
- **WHAT**: the engine already computes what changed between synthesis attempts (diff-aware
  reviewer context `treeReviewContext`, 162 §1; repair tail + treeRepaired token) — but that
  delta is LLM-fodder only. There is no user-visible "what changed since the last attempt"
  anywhere (grep diff in console.tsx → only the advisory disclaimer at :2812).
- **WHY it matters**: a repair/regeneration cycle that flips 3 files and rewrites an API is
  un-reviewable without a diff; the information already exists engine-side at near-zero cost.
- **DOES RapidTool HAVE it**: engine-side delta **yes**; surfaced **no**.
- **WHERE**: console artifacts/tree pane + the codegen commit path that owns treeReviewContext.
- **HOW** (Phase D-sized): when a re-synthesis/repair commits and the engine's delta says N
  files changed, append one `[tree delta]` artifact (kind reuse) listing changed paths with
  +/-/modified markers, capped (same cap discipline as 168A-5's transcript artifact). Full
  inline unified diff is deliberately out of scope — the artifact names the files and the tree
  pane (168A-10) lets the human open the current bodies.
- **TEST**: unit — given before/after generatedTree snapshots, the delta builder emits the
  correct path sets (added/removed/modified) deterministically and caps at N rows; console —
  delta artifact renders in the Artifacts tab.
