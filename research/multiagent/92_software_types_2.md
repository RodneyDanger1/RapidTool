## 1. Embedded firmware / RTOS (STM32/ESP32/Zephyr class)

- **Canonical structure.** Zephyr is "a scalable real-time operating system (RTOS) supporting multiple hardware architectures, optimized for resource constrained devices, and built with security in mind" ✓TODAY [README](https://raw.githubusercontent.com/zephyrproject-rtos/zephyr/main/README.rst). Application layout is **application-centric**: one app directory with its own build; Zephyr's build system is CMake-based and the *application* initiates building the kernel source (✓TODAY [Application Development](https://docs.zephyrproject.org/latest/develop/application/index.html)); board/devicetree files follow `.dts/.dtsi` conventions with Kconfig for configuration (✓TODAY same page). The Zephyr repo root itself shows the CMake+Kconfig spine (CMakeLists.txt, Kconfig, Kconfig.zephyr, boards/…, LICENSE + REUSE.toml + README.license) ✓TODAY [repo contents via API](https://api.github.com/repos/zephyrproject-rtos/zephyr/contents/). ESP-IDF documents its own CMake-based build system with component-style projects (✓TODAY [ESP-IDF Build System](https://docs.espressif.com/projects/esp-idf/en/stable/api-guides/build-system.html)).
- **Build / flash / package.** `west` is Zephyr's "swiss-army knife command line tool": multi-repository management "inspired by Google's Repo tool and Git submodules", **pluggable** — "Zephyr uses this to provide conveniences for building applications, flashing and debugging them, and more" (✓TODAY [West docs](https://docs.zephyrproject.org/latest/develop/west/index.html)). Concrete commands verified: `west build -b <board name>` and the equivalent CMake/ninja invocation `cmake -Bbuild -GNinja -DBOARD=<board> .` + `ninja -Cbuild` (✓TODAY Application Development page). Outputs are board-specific binaries/images; the "build directory" `<app>/build` is the artifact root (same page). ESP-IDF uses its `idf.py` wrapper over CMake/ninja (✓TODAY [ESP-IDF Build System](https://docs.espressif.com/projects/esp-idf/en/stable/api-guides/build-system.html)).
- **Testing conventions.** Twister is the canonical runner: "Twister scans for the set of test applications in the git repository and attempts to execute them", builds each test app "on boards marked as default in the board definition file", and "will run in an emulated environment if available" — qemu/native_sim runs are shown per-test with `-v`; `test_config.yaml` plans + `--level="smoke"` (levels smoke/acceptance/system/regression) gate CI scope (✓TODAY [Twister docs](https://docs.zephyrproject.org/latest/develop/test/twister.html)). Zephyr's own CI badge references a `twister.yaml` GitHub Actions workflow on `main` (✓TODAY README).
- **Quality gates.** The Zephyr README itself displays a CII **Best Practices** badge and an OSSF **Scorecard** badge (✓TODAY README); repo carries `.checkpatch.conf` (kernel-style patch lint), `.clang-format`, `.codecov.yml` coverage config, `.gitlint`, ruff/yamllint configs (✓TODAY repo contents). The CII badge program is a real, fetchable quality-gate standard for OSS projects (✓TODAY [BadgeApp](https://bestpractices.coreinfrastructure.org/en)).
- **Distribution.** Board SDKs + toolchains (Zephyr SDK pinned via `SDK_VERSION` file ✓TODAY repo contents); apps are flashed per-board via west/cmake runners (west "flashing and debugging" conveniences ✓TODAY West docs); shipping to customers usually means pre-flashed firmware images or OTA payloads — no package-manager equivalent exists at the app layer.
- **Licensing.** Zephyr: Apache-2.0 (✓TODAY GitHub API, `license.spdx_id = Apache-2.0`); Zephyr additionally tracks per-file licenses via REUSE (REUSE.toml + LICENSES/ dir ✓TODAY repo contents). ESP-IDF is Apache-2.0 (community-known ⚠ — not fetched this pass; treat as pattern reference).
- **Exemplar — Zephyr RTOS (fetched ✓TODAY).** [zephyrproject-rtos/zephyr](https://github.com/zephyrproject-rtos/zephyr) · ★16,412 · Apache-2.0 · default branch `main`, pushed 2026-09-05. Study: `samples/`+`tests/` split that twister scans; board/ and soc/ trees keyed to hardware; `west.yml` workspace manifests; Kconfig + devicetree as the configuration surface; CI via twister. The README is itself a quality-gate showcase (CII + Scorecard + twister badges).
- **RapidTool scaffold implication.** An embedded scaffold is a **workspace + CMake + config generator, not a code generator**: emit `west.yml` (or CMake project + Kconfig/prj.conf skeletons), `src/main.c` + `prj.conf` + board overlay `.dts`/`.dtsi`, a `tests/` tree with twister-compatible `testcase.yaml` (levels smoke/…/system), and CI wiring that runs `west build -b <board>` + `west twister` with emulation (qemu/native_sim) so gates run without hardware. Board+toolchain matrix (board → `-b` flag) is the scaffold's configuration core; deterministic-rebuild verification maps directly onto RapidTool's evidence-hash gates (binary artifact hash per board).

## 7. Drivers / kernel modules (Linux)

- **Canonical structure.** The Linux kernel source tree (torvalds/linux ★246,854, pushed 2026-09-06 ✓TODAY API). Kernel development process is documented in-tree: development-process docs, **Submitting patches: the essential guide**, coding style, licensing rules (✓TODAY [process docs index](https://www.kernel.org/doc/html/latest/process/index.html), [submitting-patches](https://www.kernel.org/doc/html/latest/process/submitting-patches.html), [coding-style](https://www.kernel.org/doc/html/latest/process/coding-style.html), [license-rules](https://www.kernel.org/doc/html/latest/process/license-rules.html)).
- **Build / flash / package.** Modules are built against a kernel tree/config (kbuild/Makefile conventions — ⚠ not separately quoted this pass; the canonical references are the fetched process docs above and the tree itself). Kernel licensing is enforced mechanically: "License version 2 only (GPL-2.0)" is the kernel's own license identifier, and **MODULE_LICENSE** tags drive loader behavior — e.g. "Proprietary" means "The license is not compatible to GPLv2", taints the kernel with the 'P' flag, and the module loader refuses to link such modules against `EXPORT_SYMBOL_GPL()` symbols (✓TODAY [license-rules](https://www.kernel.org/doc/html/latest/process/license-rules.html)).
- **Testing conventions.** KUnit is the in-tree unit-testing framework ("KUnit - Linux Kernel Unit Testing", ✓TODAY [KUnit docs](https://www.kernel.org/doc/html/latest/dev-tools/kunit/index.html)); kernel docs carry a full testing overview (Testing guide link on the docs index ✓TODAY).
- **Quality gates.** Patch submission rules: `checkpatch` style compliance, sign-off, review via mailing lists (✓TODAY submitting-patches + coding-style pages; exact flags not quoted).
