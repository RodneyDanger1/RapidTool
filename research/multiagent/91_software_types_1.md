## 0. TL;DR

- The web world (SPA / full-stack / backend / extensions / docs sites) has **converged on one toolchain core**: Vite-class bundler + Vitest/Jest + Testing-Library-style user-centric component tests + Playwright/Cypress E2E + ESLint + Prettier + TypeScript, with framework docs officially recommending exactly that stack [S2][S3][S18][S76].
- Native platforms are **store-shaped**: Windows = MSIX-packaged WinUI 3 (Store + enterprise channels) [S25]; Apple = Xcode project + XCTest/Swift Testing + TestFlight → App Review [S35][S36][S37]; Android = Gradle modules + unit vs instrumented tests + Espresso + Play [S50][S51]; the open-source desktop/mobile exemplars are predominantly **MIT/Apache/GPL** licensed [S6][S28][S32][S46][S48][S56][S69].
- Systems languages are **toolchain-standardized but package-eclectic**: Go/Rust have *one* blessed toolchain (gofmt+vet+go test / cargo fmt+clippy+test) [S120–S131]; C/C++ standardize on CMake+CTest+clang-format/clang-tidy but dependencies ship via vcpkg/Conan-class managers rather than one registry [S110–S117].
- **Scaffold bottom line (for RapidTool's codegen):** a quality project of *any* of these 14 types needs (a) the correct official starter (create-vite / create-next-app / nest new / flutter create / yo code / create-docusaurus / create-tauri-app…), (b) the type's canonical test split (unit/component/e2e or unit/instrumented or unit/integration), (c) lint+format+type-check wired into CI *before* build, (d) a license file + README + changelog, and (e) the distribution artifact of the platform (static bundle, container, MSIX/APK/IPA/Store package, crates/npm/PyPI/Maven/NuGet package, or release binaries).

## 1. The 14 application-layer software types

> Field legend: **Structure** = canonical project layout (official docs/starters) · **Build/Pack** = how it compiles & ships · **Tests** = framework + what must be tested · **Gates** = lint/type/CI norms · **Ship** = deployment/distribution · **License** = licensing norms with exemplar evidence · **Exemplar** = the fetched repo · **Scaffold** = RapidTool codegen implication (proposal).

### 1. Web frontend SPA (React / Vue / Svelte)

- **Structure:** de-facto standard is the Vite scaffold — `npm create vite@latest` with `--template vue|react|svelte` (also vanilla/ts variants); a scaffolded project gets `index.html`, `src/`, and default npm scripts `dev`, `build` (`vite build`, production), `preview` [S1]. React's official guidance: for a new app "we recommend starting with a framework" (→ type 3); a framework-less React SPA is built from scratch on tooling like Vite [S5]. Svelte's docs describe the same Vite-based layout [S3].
- **Build/Pack:** SPA builds produce a static bundle (`vite build`) that is framework-agnostic at the HTTP layer; `vite preview` serves the production build locally [S1]. Published component libs additionally ship npm packages (Excalidraw publishes `@excalidraw/excalidraw` [S7]).
- **Tests (what must be tested):** official Vue guide: unit (functions/classes/composables), component (render + user events, prefer `@vue/test-utils`), E2E (Playwright/Cypress) [S2]. Svelte: unit/component with Vitest (recommended with Vite) + E2E (Playwright/Cypress) [S3]. React Testing Library: tests must avoid implementation details and exercise the UI the way users do [S4]. Next.js docs generalize the taxonomy: unit → component → integration → E2E [S18].
- **Gates:** ESLint (pluggable JS/TS linter) [S99] + Prettier (opinionated formatter for JS/TS/JSX/HTML/CSS/MD) [S100] + `tsc` type-check as a separate script — Excalidraw's monorepo runs `test:typecheck` = `tsc` and `test:all = typecheck + code + other + app`; devDeps: vitest (+coverage, jsdom), eslint config, prettier config, husky + lint-staged [S8]. TS/ESLint/Prettier are also the defaults emitted by `create-next-app` [S19].
- **Ship:** static hosting of `dist` (Excalidraw's README credits Vercel as hosting sponsor) [S7]; content/asset pipelines are framework-agnostic.
- **License:** MIT badge on Excalidraw README + GitHub API SPDX=MIT [S6][S7]; general norm: license file in repo root makes the project usable per GitHub's licensing guidance ("for your repository to truly be open source, you'll need to license it so that others are free to use, change, and distribute") [S89].
- **Exemplar (fetched):** **excalidraw/excalidraw** — "Virtual whiteboard for sketching hand-drawn like diagrams"; 131,259★, MIT, TypeScript, default branch `master` (GitHub API ✓TODAY) [S6]. README: open-source collaborative whiteboard, published as `@excalidraw/excalidraw` npm package [S7]. package.json: private Yarn-workspaces monorepo (`excalidraw-app`, `packages/*`, `examples/*`), Vite 5 + Vitest + `@vitest/coverage-v8` + jsdom, `typescript`, per-package eslint/prettier configs, husky + lint-staged, engines node ≥18 [S8].
- **Scaffold (proposal):** for a requested SPA, emit a Vite-based TS project with the chosen framework template; test dirs/spec colocation per framework testing docs (Vitest + Testing Library + Playwright); wire `lint` (eslint), `format` (prettier), `typecheck` (tsc), `test` (vitest run) and a CI job that runs all four before `vite build`; add README/LICENSE (MIT/Apache default per user license choice); make "what must be tested" explicit in the generated test plan: pure logic units, every component's render+interactions, top user journeys E2E.

### 2. Web backend REST / GraphQL

- **Structure:** NestJS (the canonical Node/TS enterprise starter) — `nest new` creates `src/` with core files incl. `src/main.ts` (HTTP bootstrap) and modules; TypeScript by default, `--strict` opt-in [S9]. Python/FastAPI structure is test-function-driven: `TestClient(app)` + `test_*` functions + plain `assert` (standard pytest) [S11]. REST design norms are published as guidelines — Microsoft's REST API Guidelines repo (Azure + Graph service-team companion docs) [S13]. GraphQL: NestJS supports both code-first and schema-first styles on Apollo/Mercurius [S12].
- **Build/Pack:** Node backends: TS compiled (`tsc -b` in the Nest monorepo itself) [S15]; Python: standard package layout + PyPI-style distribution (see L1). Containers are the deployment unit in the microservice world (see type 14).
- **Tests:** NestJS docs: automated testing is "essential part of any serious software development effort"; unit testing with framework testing utilities, e2e testing supported [S10]. FastAPI: use pytest directly; TestClient over httpx; `test_`-prefixed functions; assert status codes/bodies [S11]. What must be tested: request→response contracts, auth/validation, error paths, service logic; e2e against the running app.
- **Gates:** Nest scaffold ships "both a code **linter** and **formatter**" — newly generated projects use **oxlint + prettier**; ESM starters use Vitest by default [S9]. NestJS's own repo scripts: `build` = tsc, `test` = `vitest run`, `coverage`, `test:integration`, `format` = prettier, engines node ≥20 [S15]. FastAPI README shows GitHub Actions test workflow + coverage badges [S16].
- **Ship:** framework-agnostic deployment; Nest apps run on Node HTTP servers (port from `main.ts`) [S9]; FastAPI is ASGI (TestClient built on httpx) [S11]; containers/orchestration norms in type 14.
- **License:** MIT on NestJS package.json (`"license": "MIT"`) and GitHub API [S14][S15]; FastAPI README: "licensed under the terms of the MIT license" [S16].
- **Exemplar (fetched):** **nestjs/nest** — "A progressive Node.js framework for building efficient, scalable, and enterprise-grade server-side applications" (API: 76,587★, MIT, TypeScript, branch `master`) [S14]; repo package.json confirms monorepo (`workspaces: packages/*`), ESM (`"type": "module"`), vitest unit+integration+coverage scripts, prettier format script [S15]. Secondary data point: **fastapi/fastapi** (Python, MIT, CI+coverage badges) [S16].
- **Scaffold (proposal):** for backend requests, emit the framework's official starter (`nest new`-equivalent file set, or FastAPI app + `tests/`); always generate: typed request/response models, health endpoint, a unit test per service, e2e tests over the HTTP API, lint+format+typecheck scripts, CI matrix (lint→test→build), Dockerfile + compose stub for local run, README with run/test commands, LICENSE.

### 3. Full-stack framework app (Next / Nuxt / SvelteKit)

- **Structure:** **Next.js App Router**: top-level folders `app` (routes), `public` (static assets), optional `src`; file conventions `layout|page|loading|not-found|error|route|template…`; dynamic segments `[segment]`, catch-all `[...segment]` [S17]. **SvelteKit**: `src/lib` (+`src/lib/server` for server-only code, enforced), `src/routes`, `src/app.html`, `hooks.client/server.js`, `static/`, `tests/`, configs (`svelte.config.js`, `vite.config.js`, `tsconfig.json`) [S20]. **Nuxt**: opinionated directory structure + conventions (file-based routing via `app/pages/`) [S21].
- **Build/Pack:** `create-next-app` default setup enables TypeScript, Tailwind CSS, ESLint, App Router, Turbopack [S19]; Nuxt: SSR by default, "no vendor lock-in… deploy your application everywhere, even on the edge" [S21]; SvelteKit code can be packaged for distribution (`svelte-package`) [S20].
- **Tests:** Next.js docs: unit (function/hook/component), component, integration, E2E; official guides for Jest (unit + snapshot), Vitest (unit), Playwright (E2E), Cypress (E2E + component) [S18]. What must be tested: per-page render, data-fetching boundaries, user flows E2E (the docs' testing-types list) [S18].
- **Gates:** TS + ESLint on by default in create-next-app [S19]; framework repos self-enforce (Docusaurus repo shows `tests.yml` GH Action + prettier badge as the docs-tool example [S83]; same ESLint/Prettier/TS core as type 1).
- **Ship:** Nuxt edge/everywhere claim [S21]; React docs position full-stack frameworks as the recommended production path [S5].
- **License:** Supabase exemplar is Apache-2.0 (API) [S22].
- **Exemplar (fetched):** **supabase/supabase** — "The Postgres development platform… Firebase using enterprise-grade open source tools"; 108,906★, Apache-2.0, TypeScript, branch `master` [S22]; README lists hosted Postgres, Auth, auto-generated REST + GraphQL + Realtime APIs, edge functions, storage, dashboard — a monorepo product (assets referenced under `apps/www`, `i18n` translations) [S23].
- **Scaffold (proposal):** full-stack scaffolds must pick ONE framework (ask or default Next) and emit its canonical tree (app routes + conventions), SSR/static decision, data layer, env config, the framework's testing recipe (unit w/ Vitest/Jest, e2e Playwright), lint/typecheck (TS+ESLint enabled by default), and deploy target config (edge/serverless/static export per Nuxt/Next claims above).

### 4. Desktop GUI native — Windows (WinUI 3) / macOS (SwiftUI) / Linux (GTK/Qt)

- **Structure:** **WinUI 3**: create via Visual Studio templates or `dotnet new`; app = XAML markup + code-behind, `App.xaml`/`MainWindow` pattern (first-app quickstart) [S24]. **macOS SwiftUI**: declarative UI framework — apps declare structure with the `App` protocol, scenes, `View`-conforming views composed with stacks/lists, modifiers; "share code between apps on multiple platforms" [S34]; Xcode-project-based development (NetNewsWire: an Xcode project with a special no-code-signing community build) [S47]. **Linux GTK**: C + GObject widget toolkit, event-driven; complex UIs recommended via GtkBuilder + its UI markup instead of hand-assembled code [S26]. **Qt**: CMake is the official build path ("Qt CMake manual"; CMake generates Makefiles/Ninja) [S27][S112].
- **Build/Pack:** WinUI 3 apps are **packaged by default** (MSIX): "packaging provides a predictable installation, update, servicing model"; package identity unlocks background tasks, push, extensions; distribution via Microsoft Store + enterprise deployment tools [S25]. macOS: TestFlight/App Store Connect for beta + submission for App Review [S35]. Linux: GNOME exemplar distributes as Flatpak nightly + distro packages [S33].
- **Tests:** macOS: XCTest = "unit tests, performance tests, and UI tests for your Xcode project"; UI flows via XCUITest ("XCUIAutomation") [S36]; Swift Testing (Swift 6/Xcode 16+): `@Test` functions, SPM-integrated, parameterized/tagged/parallel [S37]. Windows/.NET: `dotnet test` w/ MSTest/xUnit/NUnit (see L4). Linux: nautilus shows GitLab pipeline + coverage badges (CI-gated tests) [S33].
- **Gates:** nautilus CI badges (pipeline + coverage on GitLab) [S33]; Apple toolchain lint via SwiftLint (community-standard style enforcer; see L10); no single Windows/Linux gate — platform compilers + CI pipelines (exemplar badges above).
- **Ship:** Store channels dominate: Microsoft Store/enterprise for WinUI [S25]; App Store + TestFlight for macOS apps [S35]; GNOME: Flatpak + distro packages [S33]; Qt: deployment section of the Qt CMake docs [S27].
- **License:** WinUI Gallery MIT (API) [S28]; IINA GPL-3.0 (API) [S30]; GNOME Files GPL-3.0 (API) [S32] — permissive vs copyleft both normal; pick per project goals [S89].
- **Exemplars (fetched, one per platform stack since this type spans three native stacks):** **microsoft/XAML-Controls-Gallery** (WinUI 3 Gallery; 3,632★, MIT, C# — "demonstrates the controls available in WinUI and the Fluent Design System", distributed via Microsoft Store) [S28][S29]; **iina/iina** (macOS video player; 46,233★, GPL-3.0, Swift, branch `develop` — "designed with modern versions of macOS (11.0+) in mind", releases via website/releases) [S30][S31]; **GNOME/nautilus** ("Files"; GPL-3.0, C, GitLab mirror w/ pipeline+coverage badges, Flatpak nightly) [S32][S33].
- **Scaffold (proposal):** native-GUI scaffolding is per-platform and heavy — emit per-OS starters: WinUI3 (packaged MSIX project + XAML pages), macOS (Xcode project or SwiftPM package + SwiftUI `App`/`View` skeleton + XCTest/Swift Testing target), Linux GTK/Qt (CMake + `main`/app files + UI markup); include the platform test target, lint/format config (SwiftLint, clang-format), CI (Windows/macOS/Linux runners), and license file. Codegen cannot build/run these on non-native hosts — verify at CI level only, and state that in the plan.

### 5. Cross-platform desktop (Electron / Tauri)

- **Structure:** Electron: app = Node.js + Chromium, "write cross-platform desktop applications using JavaScript, HTML and CSS"; scaffolded apps install Electron as a devDependency [S39]; VS Code is the flagship product built this way (Electron README: "used by the Visual Studio Code and many other apps") [S39]. Tauri: "framework for building tiny, fast binaries for all major desktop and mobile platforms"; any HTML/JS/CSS frontend, Rust (also Swift/Kotlin) backend logic; `create-tauri-app` templates: vanilla, Vue, Svelte, React, SolidJS, Angular, Preact, Yew, Leptos, Sycamore; can add Tauri to an existing web project [S42][S43].
- **Build/Pack:** Electron docs: package + rebrand; **Electron Forge recommended**; manual paths: prebuilt binaries or asar source archive [S38]. Tauri: scaffold via `create-tauri-app`, official templates + plugin ecosystem [S42][S43].
- **Tests:** same web-stack conventions as types 1/3 for the renderer (unit/component/e2e), plus platform-level packaging CI; Electron CI evidenced by the framework's own GitHub Actions build workflow badge [S39].
- **Gates:** Electron repo: GH Actions `build.yml` badge [S39]; VS Code (Electron app exemplar) develops in-repo with roadmap/iteration/endgame plans public [S41]; lint/format/typecheck per the web core (types 1/2).
- **Ship:** store + direct-download distribution (installers per OS); code signing implied by Electron packaging docs' "rebrand/publish" framing [S38]; VS Code ships as a "distribution of Code-OSS with Microsoft-specific customizations under a traditional Microsoft product license" [S41].
- **License:** Electron MIT [S39]; VS Code repo (Code - OSS) MIT [S40][S41]; Spacedrive uses FSL-1.1-ALv2 (Functional Source License) converting to Apache-2.0 after two years — a source-available-then-open hybrid [S45]; license choice matters for desktop products [S89].
- **Exemplars (fetched):** **microsoft/vscode** (190,972★, MIT, TypeScript — the Electron flagship, product + community dev in one repo) [S40][S41]; **spacedriveapp/spacedrive** (38,913★, Rust-core cross-platform file manager for macOS/Windows/Linux/iOS/Android; README: BLAKE3 content hashing, FSL-1.1→Apache-2.0 license, CONTRIBUTING/adapter docs) [S44][S45]. (Docs cite create-tauri-app as the canonical Tauri starter [S42][S43].)
- **Scaffold (proposal):** for Electron: emit Forge-based app (main/preload/renderer split), `npm start/test` scripts, packaging config, CI per-OS artifact build; for Tauri: emit `create-tauri-app` output + Rust core crate + capabilities/plugin config; always keep business logic framework-agnostic (testable in Node) and treat store signing/notarization as a release-stage gate the generated CI documents but cannot fully exercise without secrets.

### 7. Mobile Android (Kotlin / Jetpack)

What must be tested: domain/business logic units, UI state/handlers, instrumented flows on device profiles (docs discuss running instrumented suites at scale across device profiles) [S51].
- **Gates:** unit + instrumented test suites in CI (the docs' scale discussion implies suite-driven pipelines) [S51]; lint/type gates come from the Kotlin toolchain (detekt/ktlint, see L9); NIA's Play Store presence implies release gates [S49].
- **Ship:** Play Store distribution (NIA `prodRelease` on Play) [S49]; AAB/APK release artifacts via Gradle variant system [S49][S50].
- **License:** NIA: "distributed under the terms of the Apache License (Version 2.0)" [S49]; Apache-2.0 per API [S48]; Google-sample norm.
- **Exemplar (fetched):** **android/nowinandroid** — "a fully functional Android app built entirely with Kotlin and Jetpack Compose… follows Android design and development best practices… intended as a reference"; 21,772★, Apache-2.0, Kotlin, branch `main`; `prodRelease` on Play Store; links to design case study, architecture + modularization learning journeys; Compose compiler metrics docs in README [S48][S49].
- **Scaffold (proposal):** Android scaffold = Gradle (Kotlin DSL) multi-module skeleton (app + core/feature modules), Jetpack Compose UI, version catalog, unit tests on JVM + instrumented test source sets, Espresso/Compose UI test stubs, lint + detekt config, GitHub Actions with Gradle build/test jobs; keep app module thin and feature modules independent so Gradle can build/test them separately [S50].

### 10. Browser extensions (Manifest V3)

- **Structure:** MV3 = one `manifest.json` (`"manifest_version": 3`, integer) + extension pages/scripts; a typical manifest declares an `"action"` (toolbar UI) and a **service worker** for background event handling; service workers "don't have access to the DOM" (pair with offscreen documents); dev install via **Load unpacked** [S60][S61][S62]. ## 2. Top-10 languages — per-language engineering norms

> Language list per mission (fixed); each entry: **Style / Modules & packages / Tests / Lint-format-type / Errors / Release** + a one-line **scaffold note**.

### L1. Python
- **Style:** PEP 8 is the style guide — code layout (indentation, imports order), whitespace, naming conventions are all specified there [S90]; variable-annotation syntax ties to PEP 484/526 (stub files prefer PEP 484-style annotations) [S90].
- **Modules/packages:** import packages are directories with `__init__.py`; **flat layout** (package dirs at repo top) vs **src layout** (importable code under `src/`) are the two documented layouts [S92]; modern packaging is declarative `pyproject.toml` + a build backend (`hatchling`, `setuptools`, `flit_core`, `pdm`…) [S91].
- **Tests:** pytest — test files `test_*.py`, functions `test_*`, plain `assert` with introspection, `pytest.raises` for expected exceptions [S93].
- **Lint/format/type:** Ruff = "an extremely fast Python linter and code formatter" w/ `pyproject.toml` support and Flake8/isort/Black parity [S94]; typing via PEP 484 annotations [S90].
- **Errors:** two error kinds — syntax errors vs **exceptions**; exceptions are "not unconditionally fatal"; built-in exception types; user handling via try/except (tutorial §8.3) [S95]; libraries surface typed exception hierarchies (FastAPI/pytest idioms above [S11][S93]).
- **Release:** build the package with a PEP-517 backend then upload to PyPI (packaging guide's build/upload flow) [S91]; versioning semver-like conventions are registry-agnostic (semver spec [S68]).
- **Scaffold note:** emit `pyproject.toml` + src layout, pytest + ruff config, typing enabled, CI = ruff → pytest → build → publish-to-PyPI (per [S91][S93][S94]).

### L2. JavaScript / TypeScript
- **Style:** Prettier is the de-facto formatter ("opinionated code formatter… removes all original styling… consistent style" across JS/TS/JSX/HTML/CSS/MD) [S100]; ESLint is the pluggable linter [S99].
- **Modules/packages:** ES Modules are the converged standard (`import`/`export`; any file with top-level import/export is a module, scoped not global) [S97][S96]; TypeScript compiles module formats via tsconfig (`module`, `target`, resolution flags) [S97]; npm registry packages defined by `package.json` (name+version required to publish; `files` allowlist; `main`/`exports` entries) [S66][S67].
- **Tests:** Jest — `test()`, `expect().toBe()`, `describe` grouping, mocking, snapshot capability; Vitest is the Jest-compatible Vite-native alternative [S98]; note: transpiler-only TS (Babel) means **Jest does not type-check** — type gates are separate [S98].
- **Lint/format/type:** ESLint + Prettier + `tsc` type-check as its own CI step (Excalidraw `test:typecheck: tsc`; type-fest `test:tsc`) [S8][S74].
- **Errors:** exceptions via `try…catch…finally` (throw → catch runs; finally always runs before control leaves) [S144]; library errors must be surfaced across every supported runtime — axios is "a Promise based HTTP client for the browser and node.js" [S70] and declares per-environment entry points (browser/node/react-native) in its package exports [S71].
- **Release:** `npm publish` to the registry (public by default) [S67]; package hygiene per [S66]; semver for versions [S68].
- **Scaffold note:** TS everywhere by default; ESM output; vitest-or-jest + RTL; eslint+prettier+tsc gates; npm publish CI (per [S66][S67][S98]).

### L3. Java
- **Style:** Google Java Style Guide is the widely-used reference (source file basics, UTF-8, imports, formatting, braces/indentation rules; Javadoc conventions for public API) [S103].
- **Modules/packages:** Maven **Standard Directory Layout**: `src/main/java`, `src/main/resources`, `src/test/java`, `src/test/resources` (+`src/main/webapp`), `pom.xml` + README/LICENSE/NOTICE at top level [S101]; packages mirror the class hierarchy under those roots.
- **Tests:** JUnit (current docs: JUnit = Platform + Jupiter + Vintage; starters for Maven/Gradle/Kotlin) [S102].
- **Lint/format/type:** style enforced via guides/IDE tooling (Google style doc is the contract [S103]); javac typing is the type gate; Maven/Gradle run tests in CI.
- **Errors:** the **Catch or Specify Requirement**: code that may throw checked exceptions must catch them or declare them, else it "will not compile"; `Error`/`RuntimeException` subclasses are exempt [S104].
- **Release:** publish to **Maven Central via the Central Publisher Portal** — OSSRH reached EOL 2025-06-30 and namespaces migrated to the Portal [S105]; Gradle `maven-publish` plugin publishes to Maven repositories [S136].
- **Scaffold note:** Maven or Gradle(Kotlin DSL) project with `src/main|test/java` split, JUnit 5, CI `mvn verify`/`gradle test`; publishing config for Central Portal [S101][S102][S105].

### L4. C#
- **Style:** Microsoft's C# coding conventions are the reference — naming (e.g., Pascal case for record primary-constructor parameters, camel case for class/struct ones), static-member access via class name; enforcement via `.editorconfig` files + code analysis [S107].
- **Modules/packages:** SDK-style `.csproj` per project (`dotnet new classlib` etc.); test projects conventionally mirror `*.Tests`; namespaces mirror folders [S107][S109].
- **Tests:** `dotnet test` runs test projects (VSTest mode and the newer Microsoft.Testing.Platform mode); MSTest, NUnit and xUnit.net are all first-class (docs even show mixed-framework solutions) [S106].
- **Lint/format/type:** compiler analysis + code analysis rules + `.editorconfig` formatting ("Tools can help your team enforce your conventions… enable code analysis… Visual Studio applies rules in `.editorconfig` files") [S107]; `dotnet format`-class tooling is part of that enforcement story (*flag: tool page not fetched; editorconfig/code-analysis claim is from the fetched conventions doc* [S107]).
- **Errors:** exceptions — `try`/`catch`/`finally`; `throw` creates exceptions; sources: CLR, .NET/lib, or app code [S108].
- **Release:** `dotnet pack` produces the `.nupkg` (builds the project automatically), then `dotnet nuget push … --source https://api.nuget.org/v3/index.json` publishes to nuget.org with an API key [S109].
- **Scaffold note:** emit classlib + tests projects, `dotnet test` CI, `.editorconfig`, NuGet packaging metadata + push step [S106][S107][S109].

### L5. C
- **Style/format:** clang-format formats C (also C++/Java/JS/JSON/ObjC/Protobuf/C#); `-i` in-place [S110].
- **Modules/packages:** no standard package manager — headers+`.c` units compiled per project; dependencies via C/C++ managers: vcpkg ("C/C++ dependency manager from Microsoft… declare dependencies with… a manifest that can live with your repo"; 2,866 libraries; consistency between local and CI builds) [S114].
- **Tests:** no single blessed framework; CTest is the CMake-native test driver (`ctest` runs tests registered in the build) [S113]; test executables + assert-style checks are idiomatic.
- **Lint/format/type:** compiler warnings + clang tooling; clang-tidy is documented as a C++ linter (see L6) [S116]; formatting via clang-format [S110].
- **Errors:** POSIX/libc convention: `<errno.h>` defines `errno` — "number of last error" — set by failing library calls and inspected after failure [S111].
- **Build/release:** CMake tutorial is the canonical build-system walkthrough [S112]; ctest for running tests [S113]; release artifacts typically OS packages or vcpkg-registry ports.
- **Scaffold note:** CMake project (C standard pinned), `src/`+`include/`+`tests/`, clang-format config, CTest wiring, vcpkg manifest for deps [S110][S112][S113][S114].

### L6. C++
- **Style:** C++ Core Guidelines (Stroustrup & Sutter, living document, MIT-style license) is the canonical style/design reference [S117].
- **Modules/packages:** CMake is the standard build (tutorial [S112]; Qt also builds via CMake [S27]); deps via vcpkg [S114]; no single registry.
- **Tests:** GoogleTest — tests independent & repeatable, organized into suites sharing fixtures, portable across OSes/compilers [S115].
- **Lint/format/type:** clang-format (formatting) [S110]; **clang-tidy**: "a clang-based C++ linter… diagnosing and fixing typical programming errors, like style violations, interface misuse, or bugs deducible via static analysis", extensible [S116].
- **Errors:** exceptions + RAII are the core idioms — exceptions page: throwing/catching via `throw`/`try`-`catch` [S118]; RAII (Resource Acquisition Is Initialization) is the documented resource-management idiom [S119].
- **Release:** library distribution via package managers (vcpkg [S114]) and system packages; ABI-conscious versioning is community practice (*flag: not covered by a fetched source this pass*).
- **Scaffold note:** CMake + GoogleTest + CTest, clang-format + clang-tidy configs, vcpkg manifest; CI matrix over compilers/OSes [S112][S114][S115][S116].

### L7. Go
- **Style:** Effective Go is the idiomatic-style reference (naming, formatting, program construction) [S120]; formatting is settled by **gofmt** ("The gofmt program… take care of most formatting issues") [S120].
- **Modules/packages:** modules (`go.mod`) are the unit; `go` commands edit `go.mod`; private deps via `GOPRIVATE`/proxies [S124]; packages resolve via module paths (pkg.go.dev).
- **Tests:** standard `testing` package + `go test`: functions `func TestXxx(*testing.T)` in `*_test.go` files; same-package (unexported access) or `_test` package; benchmarks, examples, fuzzing, subtests [S121].
- **Lint/format/type:** `go vet` examines source for suspicious constructs (fmt mismatches etc.), non-zero exit on findings [S122]; formatting = gofmt [S120]; staticcheck/golangci-lint are community layers (*flag: not fetched; only vet+gofmt claimed*).
- **Errors:** errors are values — compare to `nil`, sentinel errors, custom error types; Go 1.13 added `errors.Is/As` + `fmt.Errorf` `%w` wrapping for error trees [S123].
- **Release:** publish modules: `go mod tidy` → `go test ./...` → `git tag` version → users `go get module@version`; never mutate a published tagged version (Go tools return a security error on mismatch) [S125]; binaries via GoReleaser-class tooling [S59].
- **Scaffold note:** module layout (`cmd/`, `internal/`, `pkg/` is community convention — *flag: layout guide not fetched; rely on cobra/gh norms* [S58][S57]); go test + vet + gofmt-check CI; goreleaser release config.

### L8. Rust
- **Style:** rustfmt formats "according to style guidelines" — `cargo fmt`; CI-checkable [S127]; API/style conventions flow from the language docs ecosystem.
- **Modules/packages:** Cargo is the package manager: downloads deps, compiles packages, makes distributable packages, uploads to crates.io [S126]; crates + modules per Cargo conventions.
- **Tests:** `#[test]` functions run by `cargo test` (test runner binary; auto-generated test module on `cargo new`); `assert!`/`assert_eq!`-family macros; `#[should_panic]`/Result-based tests [S129].
- **Lint/format/type:** clippy = "a collection of lints to catch common mistakes", 800+ lints in categories with default levels (correctness=deny; style/complexity/perf=warn) [S128]; rustfmt for format [S127]; rustc types are the type gate.
- **Errors:** recoverable errors via `Result<T, E>` (Ok/Err) + the `?` operator; unrecoverable via `panic!`; choose per severity [S130].
- **Release:** `cargo publish` to crates.io after `cargo login` (API token, GitHub account); published versions are **immutable** ("The version can never be overwritten, and the code cannot be deleted") [S131].
- **Scaffold note:** `cargo new` layout + lib/bin split, unit+integration `tests/`, clippy + fmt checks in CI, semver discipline enforced by crates.io immutability [S126][S127][S128][S129][S131].

### L9. Kotlin

- **Tests:** JUnit is the documented path (Kotlin/JVM tutorial: JUnit tests run via Maven or Gradle) [S135]; kotlin.test-style assertions integrate with JUnit (*flag: kotlin.test API page not fetched; JUnit tutorial is the cited source*).
- **Lint/format/type:** ktlint (lint+format) [S137]; detekt (static analysis) [S138]; compiler null-safety as the type gate [S134].
- **Errors:** "Kotlin treats all exceptions as unchecked by default — you can catch exceptions but don't need to explicitly handle or declare them"; `@Throws` for Java/Swift interop [S133].
- **Release:** Gradle `maven-publish` plugin publishes modules to Maven repositories (e.g., Maven Central Portal [S105]) [S136].
- **Scaffold note:** Gradle-Kotlin project (or Android module per type 7) with ktlint+detekt config, JUnit tests, maven-publish setup [S132][S135][S136][S137][S138].

### L10. Swift
